# Node capability protocol 2.0

This is the implementation contract for the approved node-Skill split. `hs-knowledge-ingest` and `hs-knowledge-lint` identify Workflows only. The 18 Skills are workspace-explore, source-capture, change-plan, view-materialize, governance-handoff, candidate-inspect, confirmation-prepare, confirmation-record, local-check, candidate-revise, apply, recover, index-build, query-regression, publish-handoff, merge-check, maintain, and query; all knowledge names use the `hs-knowledge-` prefix, with `hs-workspace-explore` unchanged.

## Process boundary

Every `scripts/cli.py` accepts `--input REQUEST.json --output RESPONSE.json`, and domain operations also require `--knowledge-root K --rules-digest SHA256`. Optional trusted process arguments are `--catalog CATALOG.json` and `--action ACTION`; they must not be taken from source content. A catalog resolves sibling public CLIs with exact package digest and interpreter. The output is a JSON ResultEnvelope (`schema_version: 2.0`, `record_kind: result`, `status: ok|blocked|error`, `phase`, `data`, `diagnostics`, `tool_identity`, `rules_digest`). Return 0 for handled results, 2 for invalid input and 3 for a blocked prerequisite. A 0 exit code is not approval or completion.

Requests use explicit `operation_id` (safe identifier), and path references are knowledge-root relative POSIX paths. Final outputs/records stay inside their prescribed K subtree. Programs never execute source instructions, install tools, fetch documents, or commit/push. The optional workflow object carries `run_id`, `node_id`, `attempt_id`; each artifact manifest is immutable per attempt and references actual JSON digest, not an Agent assertion.

`tool_identity` is calculated from the actual Skill package and runtime dependency lock. All persisted protocol records use `schema_version: 2.0`, a specific `record_kind`, `operation_id` when relevant, `rules_digest`, `tool_identity`, and a canonical `digest` excluding only the object's own digest field. File digests use exact bytes; object digests use sorted compact UTF-8 JSON with finite numbers. Canonical operation artifacts are `.build/operations/<operation_id>/...`; durable proofs and journals are under `logs/`.

## Pure domain API

The pinned K `governance/contracts` package exports validation, knowledge, source_resources, and records. `validation.load_rules(K, expected_digest)` verifies framework-lock bytes and every listed rule/program digest before importing domain code; no external schema references or duplicate YAML keys are allowed. `validate_shape(kind,payload,rules)` raises `ContractError(code,message,path)` on error. `digest_payload`, `sha256_bytes`, `safe_path(root,relative,allowed_prefixes=None)`, `load_yaml`, `read_json`, `validate_id` are supported pure helpers. Paths reject traversal, absolute/drive/ADS/UNC inputs, Windows reserved names, case aliases, and symlink/junction escape. `knowledge.parse_card(bytes,path,rules)`, `validate_card(card,view,rules)`, `validate_relations(view)`, `match_scope(claim,context,purpose)` own card and scope rules. A parsed card contains `metadata`, `body`, `raw`, `path`; exact raw bytes remain available. `records.seal(record)` adds digest, `verify(record,expected=None)` verifies digest/binding; no write or confirmation happens on import.

## Source, candidate, and view

Capture input has `source_path` (relative allowed docs-raw path), `source_id`, optional `version`, `attachments`, `context_ref`; code capture has `kind: code` and explicit registered code context. Output `data.bundle_ref` points to a capture record with `resources`, `snapshots`, `extractions`, and durable recovery references. A snapshot fixes bytes and locator; logical source IDs never mean latest by implication.

Change-plan input has `bundle_ref`, and an explicit array of `decisions`; each decision has `candidate_id`, `decision` (create/update/merge/split/deprecate/defer), `reason`, `card_inputs` (candidate card file references), and `replaces` where applicable. Every enumerated candidate has one disposition. The Agent authors semantic content; deterministic code checks and freezes it. Materialize takes `plan_ref` and creates an exact final-view of all writes/deletes, including navigation and source-lock updates, with expected-old digest/absent and final bytes/digest. New stable bytes are fixed before review. Production never changes knowledge or source lock.

A view uses `record_kind: final_view`, `writes: [{path,expected_old_digest,final_digest,bytes_b64}]`, `deletes: [{path,expected_old_digest}]`, `review_mode: manual_document|code_gate`, `plan_ref`, `source_refs`, and `context_ref`. `null` expected digest means absent. Relevant cards and source snapshots must validate as a complete final view. Output includes `view_ref`; handoff freezes that view and its digests.

## Confirmation and transactions

Inspect and confirmation-prepare accept `view_ref`. Prepare generates a persisted display package of the complete exact content and a fresh challenge bound to view/source/rules/tool identities. Confirmation-record accepts `display_ref` and `host_event_ref`. A host event must be authenticated by a trusted adapter/public key from the installed catalog. No adapter, unsigned input, an Agent actor, timeout, or silence yields approval. Test adapter identities are explicitly synthetic and accepted only for isolated fixture roots. Partial acceptance requires new operation/view/display. The preparation or record CLI cannot manufacture host consent.

Apply accepts `view_ref` and `proof_ref` (manual_review or local_check). It revalidates exact bytes/bindings, locks `logs/operations/.writer.lock`, CAS-checks the complete write set, fsyncs content-addressed backups and journal, and writes exact bytes using atomic per-file replace. It never silently edits content. Idempotent committed reentry returns the original result. Failures preserve external edits and leave a recovery state. Recover has inspect/rollback/resume modes and reuses apply's public recovery action rather than copying the transaction engine.

## Index, query, maintenance, and code gates

Index-build supports build/verify/activate. It snapshots stable cards, evidence/proofs and validity epoch under the same writer lock; builds normal SQLite tables and immutable same-generation card bytes; activation CAS-checks expected_active, knowledge baseline and event epoch. Query-regression uses fixed candidate generation, public query evaluation and index activation after declared cases pass. Query supports search/read/receipt and local/shared channels; all eligibility and Claim filters precede rescoring/global topK. Title/summary/aliases do not bypass Claim eligibility. Receipts distinguish evaluation from activated user reads. Maintenance owns immutable events, current block state, and separate scan/application watermarks; rollback of an index cannot remove live blocks.

Local-check and merge-check accept only code_gate views and complete code/Target/build evidence; each Claim needs positive supported evidence, not merely zero findings. Merge-check fixes the latest authorized code identity, calls the same public check engine in merge mode, and reads inputs before/after without mutation. Missing real code or semantic reviewer evidence returns incomplete. Pure documents reject code-gate invocation. Publish-handoff only describes verified local results and external CI/committer obligations; it does not fabricate Git merges or install a CI policy.

## Verification boundaries

Public CLI integration tests use copied synthetic domain fixtures. Unit tests, authenticated synthetic host events, static Workflow validation and package invocation do not close real-human, implicit-host-trigger, real-six-Target, real-CI-merge, or access-control acceptance. Those require separate evidence and remain pending when inputs are absent.
