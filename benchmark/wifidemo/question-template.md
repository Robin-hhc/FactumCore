# 评测集出题表（全组协作）

> **目的**：收集迭代开发中 Agent 必须胜任的真实场景，作为工具选型评测的基准题。
> **两类题**：
> - **领域知识→具体代码**：用自然语言描述需求/问题/改动意图 → Agent 定位到具体代码（文件/函数/调用链）
> - **具体代码→领域知识**：给一段代码（函数/模块/调用链） → Agent 讲清业务流程、设计意图、上下游关系
>
> **怎么填**：每人 3–5 题，从你日常开发中**真的会问**的场景出发。「问题原文」写原话即可，不用规范。
>
> **代码仓**：WiFi MAC 驱动（host/device 多仓，chip2/chip8 双 Target，C 代码，函数指针/ops 表/宏/Event-Message 机制）

## 出题标准（先看这里）

### 难度定义

| 难度 | 定义 | 关键点数量 |
|------|------|-----------|
| **简单** | 仅根据**单仓代码索引 + 调用关系**就可以推断出来的结果，整体链路不会太长 | 1 |
| **中等** | 代码流程**较多**且可能**逻辑分散**，需要结合一定**领域知识**才能找全流程给出正确结果 | 2 |
| **困难** | 流程跨度**较大**，可能涉及**多仓调用、软硬件交互**，外加需要分析**具体特性设计文档**才能准确找出所有关键结果 | 3 |

### 出题范围（重要）

- 出题范围**仅限于 `host` 仓与两个 `device` 仓**（chip2/chip8 双 Target）
- 暂时**不要涉及算法/特性等其他仓库**
- 难度为「困难」的题，若涉及多仓调用，请限定在上述仓之间（如 host ↔ device 的软硬件交互）

### 关键点要求

- **关键点数量 = 难度**：简单 1 个、中等 2 个、困难 3 个
- 每条关键点是一个**可验证的独立事实**（"X 在 Y 模块的 Z 环节"、"设计原因是 W"），不要写"大概是这样"
- 打分按关键点命中计：**每命中 1 个关键点 = 1 分**，漏答部分流程也能拿部分分（如难题答对 2/3 关键点 = 2 分）

## 出题参考

**领域知识→具体代码 好题**（有区分度，纯 grep 不一定答得对）：
- 加新功能："给 VAP 配置加 channel width 字段，从配置入口到硬件寄存器经过哪些环节？"
- 修 bug："5GHz 连接后 30 秒断连，跟 beacon 丢失有关，beacon 超时处理在哪个模块？"
- 影响分析："改 TX ring 的 ring size 从 256 到 512，会影响哪些地方？"
- 跨仓（限 host/device）："host 侧 VAP 配置下发后，device 侧哪个环节接收处理？"
- 函数指针："TX ring switch 这个函数指针被谁调用？"（ops 表间接调用，直接 caller=0）

**具体代码→领域知识 好题**：
- 新人上手："解释 TX 主处理函数的完整业务流程，从收到上层数据到 DMA 发出"
- 设计意图："为什么 TX 用 ring buffer 而不是 linked list？ring size 256 怎么定的？"
- 跨模块（限 host/device）："从 VAP 配置入口追踪完整链路，含 host→device 跨仓调用"
- 协议约束："802.11 要求 beacon 间隔 100ms，代码哪里保证？超时怎么处理？"

**避免的坏题**：
- "这个文件有哪些函数？"（纯结构，grep 就能答，无区分度）
- "这个函数是干什么的？"（指 5 行 getter，太简单）
- "项目架构是什么？"（太泛，不可验证）
- "帮我写个 XX 功能"（代码生成，不是代码理解）
