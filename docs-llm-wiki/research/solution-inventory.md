# 面向 Agent 的代码知识图谱建立策略与方案档案

访问截止日期：2026-08-25

## 1. 本文究竟比较什么

本清单不再按内部模块或“架构层”给产品分组，而只比较它们怎样建立 Agent 可用的知识，以及这些知识怎样回答两类问题：

1. **领域问题到代码**：用户用模糊自然语言描述功能、故障或流程，系统怎样找到可核验的具体代码片段？
2. **代码到领域解释**：用户从函数、宏、文件或调用点出发，系统怎样整理出跨文件流程、设计意图和领域含义？

本文把“知识图谱”按作用宽泛理解为：能够显式保存、扩展或查询代码实体及其关系的结构化知识。并非所有候选都使用图数据库，也并非名称中带 graph 的产品就具备同等语义深度。

## 2. 为什么需要“代码知识 + 文档/领域知识 + 代码—文档链接”

这是本文对现有论文与项目的综合结论，而不是某个项目直接宣布的标准架构。

| 证据观察 | 对两类问答的含义 | 证据 |
|---|---|---|
| 仓库检索不存在对所有任务全面占优的单一方法；词法、向量和结构化 RepoMap 各有优势 | 自然语言问题需要多路召回，不能把 embedding 或图查询当成唯一入口 | S001、S002、S003 |
| 结构化代码图能减少 Agent 为架构问题进行的盲目文件探索，但轻量语法图不包含完整数据流、宏配置和领域意图 | 必须保留代码实体、关系和源码位置；复杂行为问题还需更深程序分析 | S005、S007、S015、S039、S042 |
| 代码关系本身不能解释“为什么这样设计”、协议术语和操作流程；Wiki、领域图和生成文档用来补足这一层 | 从代码反推流程、从领域词定位代码都需要文档或领域知识 | S009、S021、S022、S023、S041 |
| RepoDoc、Graphify、Understand Anything 等都把代码结构用于生成或定位解释性资产，并保留不同程度的回链或更新关系 | 代码与文档必须有可追溯链接；仅把两者分别做向量索引不足以形成闭环 | S009、S021、S041 |

由此得到三个后续分析类别：

- **代码知识**：回答“仓库中有哪些实体，它们怎样连接，在当前源码/构建条件下发生了什么”。
- **文档与领域知识**：回答“这些代码在业务、协议、流程和设计意图上意味着什么”。
- **代码—文档链接**：回答“某条解释由哪些代码支持；某段代码变化会影响哪些解释”。

Agent、MCP、Skill 或对话 memory 只是读取这些知识的接口或上下文机制。除非某方案把它们与具体代码/文档节点建立稳定关系，否则不单列为第四类知识。

## 3. 类别一：代码知识

### 3.1 三种深度

| 深度 | 典型事实 | 适合的问题 | 主要缺口 |
|---|---|---|---|
| 文本与符号检索 | 文件、文本命中、定义、引用 | “哪里出现了该术语/符号？” | 不直接证明跨文件行为与路径 |
| 轻量结构图 | AST 实体、调用、导入、继承、社区/模块 | “入口在哪里，相关文件和调用者有哪些？” | 通常不理解编译配置、精确数据流或指针别名 |
| 深度程序分析 | CPG、CFG、DDG、dataflow、taint、slice、构建依赖 | “数据怎样传播，某分支如何到达，漏洞路径是什么？” | 成本更高；需要正确构建配置和更专业的查询 |

三种深度不是互斥产品路线。成熟 Agent 更可能先用便宜的检索与结构图缩小候选，再对少数路径运行深度分析，并最终回到源码位置核验。

### 3.2 轻量代码图与导航方案

#### Codebase-Memory

- **建立策略**：Tree-sitter 抽取代码实体与关系，形成可由 MCP 查询的本地知识图；增量索引保持仓库上下文。
- **自然语言到代码**：Agent 将问题分解为符号搜索、定义、引用和邻接关系查询，再读取命中的源码。
- **代码到流程**：沿调用者/被调用者、文件和符号关系扩展，生成局部调用链或模块解释。
- **证据**：论文与第一方 Benchmark 提供 Agent 探索实验；具体数字只在 S005 的实验条件内使用。
- **可借鉴点**：本地、开源、面向 Agent 的小型图接口；适合作为轻量基线。
- **不能证明**：Tree-sitter 图不自动等于 C 预处理后、Target-specific 的真实调用与数据流。

#### CodeGraph

- **建立策略**：Tree-sitter 抽取符号、调用、导入和继承边，以 SQLite/FTS5 持久化，并增量同步。
- **自然语言到代码**：Agent 通过 `codegraph_explore` 从自然语言或符号起点取得相关源码、定义及跨文件关系。
- **代码到流程**：以函数或文件为起点沿调用图、依赖图和社区关系扩展，减少逐文件搜索。
- **数据**：第一方在 7 个仓库、7 种语言、每库 1 个架构问题、每实验臂 4 次、Claude Opus 4.8 条件下报告工具调用减少 88%、时间减少 53%、处理 Token 减少 62%、成本减少 44%（S007）。
- **可借鉴点**：轻量、本地、增量、SQLite，且对 Agent 暴露高层探索动作。
- **限制**：数据为第一方小样本；不包含 WiFi MAC、宏/Target 或领域知识问答，不能作为效果胜者结论。

#### GitNexus

- **建立策略**：浏览器端解析仓库，建立符号、依赖和社区关系；提供图探索、上下文和影响分析接口。
- **自然语言到代码**：Agent 先通过 MCP/查询取得与概念相关的符号和文件，再沿图读取上下文。
- **代码到流程**：从符号邻域、依赖和社区聚类形成模块视图与影响范围。
- **可借鉴点**：把知识图直接包装成 Agent 的 context、impact 和 explore 操作。
- **限制**：S008 未提供可用于本文排序的 C/Agent 准确率；浏览器内轻量解析仍不证明编译配置与数据流。

#### Serena 与 Sourcegraph MCP / SCIP

- **建立策略**：Serena 通过语言服务器提供 definition/reference/symbol 操作；SCIP 保存定义与引用的语言无关索引，Sourcegraph MCP 将搜索和导航暴露给 Agent。
- **自然语言到代码**：Agent 把描述转换为文本搜索、符号查询、定义/引用跳转。
- **代码到流程**：适合沿符号引用回溯局部关系，但没有 CPG 式 CFG/DDG，也没有领域文档生成。
- **可借鉴点**：它们是必要的“普通代码导航”对照组，可以检验知识图是否真正比成熟符号工具多提供价值。
- **限制**：可调用接口不等于 Agent 效果已独立证明；语言服务器和索引器的 C/C++ 能力决定事实边界（S037、S038）。

#### RIG

- **建立策略**：从 CMake File API、CTest 等真实构建/测试工件抽取组件、依赖和测试关系，并把每条架构事实绑定证据。
- **自然语言到代码**：Agent 可从“哪个组件实现/测试某功能”定位构建目标、源文件和测试，而不是从目录结构猜测。
- **代码到流程**：从文件或目标回溯组件依赖和测试覆盖，解释仓库的构建级架构。
- **数据**：作者在 8 个仓库、每仓 30 问、3 个商业 Agent 的对照中报告平均准确率提升 12.2%、时间减少 53.9%、每个正确答案耗时减少 57.8%（S042）。
- **可借鉴点**：对 WiFi MAC 最重要的启示是 Target、组件与测试关系应来自真实构建工件。
- **限制**：它覆盖构建/依赖架构，不覆盖完整 C 行为、协议领域知识或代码—文档链接；数字尚无独立复现。

### 3.3 深度程序分析方案

#### Joern

- **建立策略**：把 AST、控制流和数据依赖统一为 Code Property Graph，以查询 DSL、切片和 dataflow 语义分析代码。
- **自然语言到代码**：Joern 本身不是自然语言系统；Agent 或上层适配器必须先把问题转换为符号/CPG 查询，再返回源码位置和路径。
- **代码到流程**：从具体方法、调用、参数或赋值点沿 CFG、DDG、dataflow 和 slice 回溯/前向展开，适合解释跨函数传播和路径条件。
- **可借鉴点**：C/C++ 前端、开放 CPG 规范、可扩展 dataflow semantics；比轻量图更接近 WiFi MAC 的行为事实需求。
- **限制**：必须验证编译参数、宏展开、指针和外部语义；没有公开的多 Target WiFi MAC 准确率。复杂查询不能直接交给 LLM 猜测。

#### codebadger

- **建立策略**：不重新发明代码图，而是在 Joern 之上提供高层 MCP 工具，封装切片、污点跟踪、数据依赖和语义导航。
- **自然语言到代码**：Agent 将自然语言意图映射为少量高层分析动作，由工具生成/执行底层 CPG 查询并返回证据。
- **代码到流程**：从具体代码锚点调用 slice/dataflow/taint 工具，组织为可解释路径。
- **数据**：论文报告 GGML、libtiff、libxml2 三个真实案例，其中首个代码库约 8,000 methods；这是可行性案例，不是大规模正确率对照（S039）。
- **可借鉴点**：Joern 的优势可能不在让 Agent 直接写查询，而在提供窄而确定的领域动作。
- **限制**：案例少、作者与实现同源；不证明 WiFi MAC 宏、Target 和 Host/Device 边界的准确率。

#### CodeQL 与 QLCoder

- **建立策略**：CodeQL 把代码编译/抽取为数据库，由声明式查询分析控制流、数据流和安全属性；QLCoder 再用 LSP、RAG 与执行反馈帮助 Agent 合成查询。
- **自然语言到代码**：普通 CodeQL 需要专家写查询；QLCoder 把漏洞描述转为候选查询，通过实际执行结果和语法反馈迭代。
- **代码到流程**：查询结果可给出 source-to-sink、路径和源码位置，适合明确的安全/数据流问题。
- **数据**：QLCoder 在 176 个 CVE、111 个 Java 项目上报告 53.4% 正确查询，对照 Claude Code 为 10%；这是 Java CVE 查询合成，不是 C 代码理解结果（S040）。
- **可借鉴点**：Agent 生成的分析查询必须通过确定性引擎执行和正反例验证。
- **限制**：CodeQL 的许可、数据库构建与 C/C++ 构建模式需单独评估；QLCoder 结果不能外推到 WiFi MAC。

#### Clang/LLVM、Fraunhofer AISEC CPG、SVF、PhASAR、Frama-C、Semgrep

这些项目代表可组合或专用的深度分析能力，而不是当前已证明的完整 Agent 知识图谱：

| 方案 | 主要知识 | 适合作为 | 当前不作为主候选的原因 |
|---|---|---|---|
| Clang AST/LibTooling + LLVM IR | 编译后 AST、类型、宏位置、IR | C/C++ 确定性抽取底座 | 需要自行设计图、查询与 Agent 接口 |
| Fraunhofer AISEC CPG | 多语言 CPG 与 pass 机制 | Joern 之外的 CPG 对照 | Agent 使用与 WiFi C 数据不足 |
| SVF | LLVM 上的指针/值流 | 复杂别名和值流专项增强 | 不是仓库导航或领域知识系统 |
| PhASAR | LLVM 数据流分析框架 | 自定义 interprocedural analysis | 需要开发具体分析与 Agent 封装 |
| Frama-C | C 抽象解释、切片与规范分析 | 高风险 C 性质验证 | 成本和适用问题与通用问答不同 |
| Semgrep CE | 规则化语法/语义模式 | 快速规则与安全检查基线 | 社区版不是完整跨过程行为图 |

它们的共同价值是：当轻量图无法回答某类可验证问题时，为指定关系提供更可靠的专门分析，而不是把所有结果都装进一个“万能图”。证据见 S010、S016—S020。

### 3.4 代码知识类别的阶段性判断

- CodeGraph、Codebase-Memory、GitNexus、Serena/SCIP 都应放在同一“代码知识”大类比较；差别在图关系深度与 Agent 接口，而不是“导航”和“图”两个互斥类别。
- Joern/codebadger 与它们解决相同的两类问答，但能提供更深的行为关系，代价是构建与查询更复杂。
- RIG 提醒我们：多 Target C 的组件与编译事实不能只靠源码 AST 猜测。
- 当前证据不足以判断轻量图加按需深度分析，是否比全量 CPG 更适合 WiFiDemo；该问题留给 Benchmark。

## 4. 类别二：文档与领域知识

代码图可以告诉 Agent “谁调用谁”，但很少直接包含协议术语、设计原因、功能边界和流程叙述。文档类策略可以分为三种。

### 4.1 检索已有文档

- **材料**：README、设计文档、API 文档、ADR/RFC、issue/commit、规范与测试说明。
- **过程**：先按自然语言召回文档段落，再利用其中的符号、路径、链接或版本锚点回到代码。
- **优势**：保留人类明确写下的设计意图和术语。
- **风险**：文档可能过时、没有源码锚点或混入其他 Target；向量相似度不能证明内容仍正确。

Graphify 会把代码旁的 `# WHY:`、ADR/RFC 和文档作为一等知识对象；这使其同时属于本类与下一节的链接类（S021）。

### 4.2 从代码生成仓库文档

#### Understand Anything

- **建立策略**：Tree-sitter 先生成可复现结构图，多个 LLM Agent 再生成摘要、架构层、business domain、flow、step 和 onboarding 资产。
- **自然语言到代码**：用户询问领域或流程，系统在领域/结构图中找到相关实体，再执行文件或函数 explain。
- **代码到流程**：从文件/函数出发生成解释，并把局部实体归入领域和流程。
- **优势**：一套产品同时覆盖代码导航、生成式领域知识和双向探索。
- **限制**：官方没有公开结构边、领域映射或 C/Target 问答准确率；生成解释不能替代源码证据（S009）。

#### RepoDoc

- **建立策略**：构建 RepoKG、聚类模块，再由多 Agent 生成带交叉引用和 Mermaid 图的仓库文档。
- **自然语言到代码**：读者先在模块化文档中理解概念和流程，再沿 API/代码引用定位实现。
- **代码到流程**：从代码图识别模块与依赖，生成跨文件说明；变更后通过双向影响传播只更新受影响文档。
- **数据**：作者在 24 个仓库、8 种语言上报告 API coverage +32.5%、completeness +10.4%、约 3 倍生成速度、Token -85%；增量更新时间 -73%、Token -77%、update recall +10.2%（S041）。
- **优势**：明确研究“图生成文档”和“代码变更驱动文档更新”，与本项目的反向解释问题高度对应。
- **限制**：作者评估，指标定义与仓库混合；未验证嵌入式 C、多 Target 或领域事实真实性。

#### Graphify

- **建立策略**：本地 Tree-sitter 生成代码图，可选 LLM 处理文档/PDF/媒体，输出 `graph.json`、社区、`GRAPH_REPORT.md` 和可选 Wiki。
- **自然语言到代码**：Agent 用 query/path/explain 从概念或文档实体扩展到代码节点。
- **代码到流程**：从代码图社区和路径生成报告/Wiki，并将推断关系与抽取关系区分。
- **优势**：把结构图、领域材料、生成文档和 Agent 查询放在同一项目中；边标记 `EXTRACTED`、`INFERRED`、`AMBIGUOUS`。
- **限制**：公开 memory Benchmark 不测代码—领域链接；没有多 Target C 的链接 precision、过期修复率或问答正确率（S021）。

### 4.3 把仓库知识“编译”为 Wiki

#### LLM-Wiki

- **建立策略**：把检索从一次性的 chunk 搜索改为可演化的 Wiki 结构，使 Agent 在使用中整理、合并和扩展知识。
- **自然语言到代码**：先由 Wiki 导航领域概念，再用其中的证据引用或实体锚点回到代码；若缺少源码锚点，就只能作为解释线索。
- **代码到流程**：Agent 将多次代码探索结果整理为主题页和关系，供后续任务复用。
- **价值**：明确把长期知识组织本身视为推理过程，而不是把对话日志当 memory。
- **限制**：论文研究通用 Agent-native retrieval，不证明仓库代码边、文档事实或版本失效处理天然正确（S022）。

#### WiCER

- **建立策略**：采用 Wiki-memory 的 compile、evaluate、refine 循环，把原始材料编译为可检索知识，并用任务反馈持续修订。
- **自然语言到代码 / 代码到流程**：可作为文档知识组织与质量控制方法；要进入代码问答，仍必须增加稳定源码锚点和 revision/Target 范围。
- **价值**：强调 Wiki 不是一次性生成物，而要评测和精炼。
- **限制**：它不是现成的 C 代码图或代码—文档链接器，不能单独成为本项目方案（S023）。

### 4.4 文档知识类别的阶段性判断

- 仅索引已有文档最保守，但受文档覆盖和新鲜度限制。
- Understand Anything、Graphify、RepoDoc 展示了“从代码结构生成领域/流程解释”的三种具体实现，应在代码类和文档类两边都分析。
- LLM-Wiki/WiCER 适合作为文档知识管理方法，而不是代替代码事实层。
- 独立 Skill 和对话 memory 没有特殊的图谱能力；本轮不再把它们列为候选知识类别。

## 5. 类别三：代码—文档链接

这一类别决定两类问答能否真正闭环。链接至少应回答四个问题：

1. 文档中的某个术语、流程步骤或主张指向哪些具体源码位置？
2. 该链接是解析器抽取、人工声明，还是模型推断？
3. 它适用于哪个 repository revision、Target 和构建条件？
4. 源码移动或语义变化后，哪些文档应失效、重连或重生成？

### 5.1 五种已观察到的链接策略

| 策略 | 代表 | 领域到代码 | 代码到流程 | 主要风险 |
|---|---|---|---|---|
| 文档内显式引用 | ADR/RFC、`# WHY:`，Graphify | 直接沿路径/符号/引用定位 | 从代码找到关联说明 | 人工覆盖不足、重命名后断链 |
| 结构图驱动生成 | RepoDoc、UA、Graphify | 生成文档保留 API/实体引用 | 从模块/调用关系综合说明 | LLM 可能生成无证据主张 |
| 模型语义映射 | UA domain graph、Graphify inferred edge | 把领域词映射到代码实体 | 把代码实体归纳为领域概念 | 推断边不稳定，需要置信度与复核 |
| 影响传播与增量更新 | RepoDoc | 从文档引用回到受影响代码 | 代码变更定位待更新文档 | 更新召回不足会留下静默过期内容 |
| 构建证据锚定 | RIG；Clang compilation database | 从组件/Target 问题到实际参与编译的文件 | 从文件解释构建组件与测试关系 | 只覆盖构建语义，不覆盖业务意图 |

### 5.2 代表项目如何跨类别

| 项目 | 代码知识 | 文档/领域知识 | 链接机制 | 当前证据结论 |
|---|---|---|---|---|
| CodeGraph | 轻量 AST/调用/依赖图 | 无内建领域文档主线 | 主要是源码位置和结构边 | 快速代码探索基线；领域层需外接 |
| Joern/codebadger | CPG、CFG、dataflow、slice | 无内建 Wiki 主线 | 分析路径回到源码位置 | 深行为证据候选；领域层需外接 |
| Graphify | Tree-sitter 图、社区、路径 | 文档/PDF/媒体、报告、Wiki | EXTRACTED/INFERRED/AMBIGUOUS 边，query/path/explain | 三类均覆盖，但链接准确率未知 |
| Understand Anything | 确定性结构图 | domain/flow/step/onboarding | 结构实体与生成式领域图共同查询 | 三类均覆盖，但缺公开效果 Benchmark |
| RepoDoc | RepoKG 与模块聚类 | 交叉引用文档、Mermaid | 双向语义影响传播与增量重生成 | 文档生成/更新证据较强；C/Target 未验证 |
| GitNexus | 符号/依赖/社区图 | 上下文与模块视图 | MCP context/impact/explore | 代码到上下文可用；领域文档能力有限 |
| LLM-Wiki/WiCER | 不负责可靠代码解析 | 可演化 Wiki | 必须外接源码证据锚点 | 只作为文档知识组织方法 |
| RIG | 构建、组件、测试事实 | 架构解释 | 每条关系绑定构建工件证据 | 补强 Target/构建事实，不是完整三类方案 |

## 6. 两类问答的实际过程

### 6.1 模糊自然语言到具体代码

成熟过程不是“对整个图库问一次 LLM”，而是：

1. 从文档/Wiki/领域图解析术语、同义词、组件和可能流程。
2. 用词法、向量、符号和轻量结构图并行召回候选代码。
3. 沿调用、引用、构建依赖或社区关系扩展候选。
4. 对数据传播、路径条件等难题按需调用 CPG/dataflow/slice。
5. 返回带 revision、Target、文件和行号的源码证据；将推断与抽取事实分开。

CodeGraph/GitNexus 主要覆盖第 2—3 步，Joern/codebadger 覆盖第 4 步，Graphify/UA/RepoDoc/LLM-Wiki 类资产补足第 1 步，源码与构建工件负责第 5 步。

### 6.2 具体代码到流程与领域解释

1. 把函数、宏或行号解析为稳定代码实体，并确认 revision/Target。
2. 沿调用、控制流、数据流和构建关系收集局部事实。
3. 找到显式关联文档、领域实体、测试和已有流程页。
4. 将多个事实组织为步骤、分支、角色和因果说明。
5. 每个关键步骤回链源码；没有证据的领域解释标为推断。
6. 代码变化后让链接失效或触发文档重生成。

RepoDoc 最直接研究第 4—6 步，Graphify/UA 展示第 3—5 步的产品形态，Joern/codebadger 可以补足第 2 步的行为关系。

## 7. 当前保留、降级与排除

### 7.1 保留到后续 Benchmark

- **普通工具基线**：ripgrep/符号导航/Serena 或 SCIP。
- **轻量代码图代表**：CodeGraph；Codebase-Memory、GitNexus 作为同类对照或设计参考。
- **深度代码分析代表**：Joern + 高层 Agent 工具思路（codebadger）；必要时用 Clang/LLVM 事实核验。
- **代码 + 文档 + 链接代表**：Graphify、Understand Anything、RepoDoc 分别测试其覆盖能力或借鉴机制。
- **文档知识组织方法**：已有文档检索 + LLM-Wiki/WiCER 式 compile/evaluate/refine。
- **构建事实补强**：RIG 式真实构建工件抽取。

这不是最终产品组合，也不预设最终一定采用 Joern。Benchmark 可以把候选缩减为两套、四套或不同组合。

### 7.2 当前降级为专用组件

SVF、PhASAR、Frama-C、Semgrep、CodeQL 等保留为专项分析或方法学对照，不作为“开箱即用的完整 Agent 知识图谱”候选。需要它们时，应由具体问题和测量结果触发。

### 7.3 当前排除出主线

- 只有通用聊天记忆、没有代码实体和证据链接的 memory 产品。
- 只有提示模板或渐进式加载、没有知识构建与链接机制的 Skill。
- 仅把代码和文档切块放入向量库、无法说明关系来源和失效条件的方案。
- 把全部仓库图一次性塞入 prompt、没有检索预算和证据回链的方案。

## 8. 对 WiFi MAC 的适用性与未知项

WiFiDemo 类仓库会放大通用开源结果未覆盖的因素：宏和条件编译、多个 Target、Host/Device 分离、跨模块消息而非普通函数调用、指针与回调、协议状态和硬件/驱动领域术语。因此所有候选都必须回答：

- 图中代码事实来自原始源码、解析器推断，还是某个 Target 的实际编译工件？
- 同名符号在不同 Target 下是否隔离？
- 文档主张是否绑定 revision、Target、源码位置和生成方法？
- 跨 Host/Device 的流程是否被误画为进程内 `CALLS`？
- 从自然语言到代码以及从代码到流程，分别有多高的证据召回率、事实正确率和最终 Agent 正确率？

公开材料尚未给出这些问题的答案。因此当前结论是**缩小策略范围并明确实验对象**，而不是宣布某一工具胜出。
