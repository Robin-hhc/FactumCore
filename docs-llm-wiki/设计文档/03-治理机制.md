# 细节设计说明书 03 · 治理机制

> **定位**：知识库治理实现细节——双层 lint、check.sh 全库门禁、增量更新、健康度看护。
> **状态**：v0.1 草案，内容自《知识库架构设计-合稿.md》§5 迁移，待按 00-总架构设计 细化。已对照 CANNBot 审阅补充增量复查范围与内容适用性检查（§3）、覆盖-缺口-停止条件（§4）。
> **关联**：00-总架构设计 §5 步骤 3.2、4.2、§3.5（知识契约六项职责约定）；02-LLM-Wiki构建 §3（生命周期门禁）。

---

## 1. 双层检查（lint）

- **脚本检查**（低成本、进 CI 硬门禁）：frontmatter 符合卡契约、tag 合法、链接有效、`conflicts` 字段指向真实存在且两侧互指、新增页面后图谱可构建、锚点校验（见 04-消费与问答 §4）；
- **Agent 检查**（语义层、出检查报告）：
  - **查错**：知识矛盾点发现（跨卡语义矛盾、conflicts 未裁决）、重复概念识别、与代码实际对账（双轨互证，冲突如实报告）、过时声明（新来源已 supersede）；
  - **找缺口**：孤立页（无入链）、重要概念被提到但缺专属页、缺失交叉引用、数据缺口（可补的来源/问题建议）——输出"待补清单"供人工决策，与 §4 数据看板联动。

## 2. check.sh 全库门禁

`bash check.sh` 覆盖：全库知识 Lint + 检索回归 + 单元测试 + 静态检查 + 图谱合成/校验。作为 PR 准入硬门禁；仓库不自动 commit/push/合并/发布。

## 3. 增量更新

- **触发源**：代码 merge（git diff → 受影响符号/锚点）、上游软件栈发新版、spec 变更（git diff 映射 → 只重 ingest 受影响页）、新轨迹批次；
- **流程**：识别新旧版本 diff → 确定受影响页面与新增页面 → 增量编译 → 提交 PR → 触发 check.sh；
- **目标**：每次只重跑受影响子域，不整库重编译；
- **范围（对齐 00-总架构设计 §3.5）**：除卡内直接引用，还考虑公共头文件、宏、消息字段及 OPS 注册等影响；定位不精确时扩大到相关模块并记录不确定性；
- **复查**：分别检查引用有效性与内容适用性，保留来源版本、条件和冲突——函数仍存在不等于业务解释仍适用，只刷新行号不算完成内容更新。

## 4. 健康度看护（长期、双测评 + 看板）

| 机制 | 内容 | 用途 |
|------|------|------|
| **检索测评** | 固定问题 + 相关页面标注，调用检索接口，看 top1 精确率 / 页面命中与召回 / 排序质量 | 已有知识能否被有效检索 |
| **问答测评** | 基于知识库设计选择题，Agent 走真实检索与阅读流程作答；**含信息不足应拒答、信息充分不误拒**两类题 | 知识能否被正确理解与使用 |
| **数据看板** | 页面总量 / 目录与类型分布 / 页面与测评关联覆盖 / 图谱状态 / 最新测评结果与同口径历史趋势 / 逐题结果 | 自动化监测 + 人工巡检，发现知识缺口与质量退化 |

> **覆盖-缺口-停止条件（对齐 00-总架构设计 §3.5F）**：健康度不只计卡片数、链接数与门禁通过率，同时观察**真实问题覆盖**、**冲突/待复查积压**与**缺口关闭**；零命中不等于否定性技术证据，缺口形成后续摄入线索；证据足够、无新证据或预算到达即停止。
