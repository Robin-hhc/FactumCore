# 代码与文档/领域知识如何链接

日期：2026-08-25

状态：研究产物；不构成最终选型

## 1. 为什么“同时索引代码和文档”还不够

本文件只回答一个问题：代码知识和文档/领域知识怎样连接，才能让 Agent 可靠地完成以下双向任务？

- **领域到代码**：从“发送失败后为什么回收描述符”一类自然语言问题，找到当前版本、当前 Target 中的具体函数、分支和源码片段。
- **代码到解释**：从一个函数、宏或行号出发，整理其所在流程、设计原因、消息边界和相关文档。

如果代码和文档只是分别进入向量库，系统最多得到相似候选，不能回答链接是谁建立的、是否适用于当前版本、代码变化后是否仍有效。可靠链接至少应包含：两端对象、关系含义、产生方法、源码/文档证据、版本与 Target 范围、当前状态。

## 2. 两个方向需要的共同链路

### 2.1 领域到代码

```text
自然语言问题
  -> 文档/Wiki/领域实体：解析术语、同义词、流程步骤
  -> 代码候选：文本、符号、向量、轻量结构图
  -> 关系扩展：调用、引用、构建依赖、社区
  -> 按需验证：CPG/dataflow/slice/真实编译工件
  -> 答案：revision + Target + file:line + 证据类型
```

领域知识负责把“业务或协议说法”翻译成代码可检索的概念；代码图负责扩展关系；深度分析负责验证复杂路径。最后一步必须回到当前源码，而不是只返回生成摘要。

### 2.2 代码到解释

```text
函数/宏/file:line
  -> 当前 revision/Target 下的代码实体
  -> 调用、控制流、数据流、构建与测试关系
  -> 显式文档引用、领域映射、流程页
  -> 生成步骤化解释
  -> 每个关键主张回链代码或原始文档
```

反向解释不是把调用图直接改写成自然语言。它需要区分“代码确实执行的关系”“文档明确声明的设计原因”和“模型根据证据作出的归纳”。

## 3. 五种成熟方案中可观察到的链接策略

### 3.1 显式引用

**做法**：在 ADR、RFC、设计文档、代码注释或 Wiki 中直接保存 symbol、path、commit URL、测试名或代码片段引用，并建立反向索引。

**代表**：Graphify 将 `# WHY:`、ADR/RFC 等作为知识对象；RepoDoc 生成带 API 交叉引用的文档（S021、S041）。

**双向过程**：

- 文档到代码：解析引用，定位符号或源码位置。
- 代码到文档：按 symbol/path 的反向索引找到解释和设计记录。

**优势**：含义明确、容易审计，人工文档可以表达代码中不存在的“为什么”。

**风险**：裸 `file:line` 会随编辑漂移，函数重命名会断链；必须同时保存 revision、引用片段摘要或稳定符号身份，并把无法修复的引用标为过期。

### 3.2 结构图驱动文档生成

**做法**：先从代码构建符号、调用、依赖和模块关系，再让 Agent 把这些结构组织为模块页、流程说明、Mermaid 图或 onboarding 文档。

**代表**：RepoDoc 的 RepoKG→module clustering→cross-referenced documentation；Understand Anything 的结构图→domain/flow/step；Graphify 的代码图→report/wiki（S009、S021、S041）。

**双向过程**：

- 领域到代码：生成文档中的 API/实体引用成为下钻入口。
- 代码到解释：从代码实体所属模块及邻接关系生成流程或模块说明。

**优势**：覆盖面可以随代码图自动扩展，适合没有完整人工文档的大型仓库。

**风险**：文档的流畅度不等于事实正确；生成器可能省略宏条件、误把 may-call 写成必然调用，或为代码关系补写不存在的设计意图。

### 3.3 模型语义映射

**做法**：由 LLM、embedding 或聚类把协议术语、Feature、Flow 和代码符号建立候选关系。

**代表**：Understand Anything 的 business domain graph；Graphify 的 `INFERRED`/`AMBIGUOUS` 边；LLM-Wiki/WiCER 式知识编译可整理同义词和主题（S009、S021—S023）。

**双向过程**：

- 领域到代码：以“重传”“功耗管理”等术语召回候选符号和模块。
- 代码到解释：将函数群归纳为领域概念、步骤或职责。

**优势**：能处理领域词与代码命名不一致、文档分散和跨文件综合。

**风险**：这是候选生成，不是确定事实。应记录模型、输入、分数/理由和证据，并要求源码、规则、测试或人工复核后才能支持确定性回答。

### 3.4 影响传播与增量更新

**做法**：保存代码实体到文档段落的反向依赖；代码变更后沿图定位受影响文档，只重建必要部分。

**代表**：RepoDoc 的 bidirectional semantic impact propagation 和 targeted regeneration（S041）。

**双向过程**：

- 代码到文档：由变化实体找出所有依赖说明。
- 文档到代码：由文档引用确认它依赖的代码集合，并验证这些实体是否仍存在。

**优势**：使生成文档具有可测的新鲜度和更新成本，而不是一次性快照。

**风险**：影响召回不足会留下“看起来正常但实际过期”的文档；因此必须同时测 update recall、误更新率和过期内容残留率。

### 3.5 构建工件与确定性规则锚定

**做法**：从真实编译命令、CMake File API、CTest、预处理结果或项目规则生成 Target、组件、测试和 occurrence 关系。

**代表**：RIG 用构建/测试工件产生带证据的 repository intelligence graph；Clang compilation database 提供实际编译输入（S010、S042）。

**双向过程**：

- 领域到代码：从“chip8 host 发送路径”等带配置的问题，只检索该 Target 实际编译的文件和符号。
- 代码到解释：说明某文件属于哪些目标、受哪些宏影响、由哪些测试覆盖。

**优势**：避免把目录中存在但当前 Target 不参与编译的源码当成当前事实。

**风险**：构建关系只能解释组件和配置，不能自动产生协议意图或数据流语义；它应补强而不是替代其他链接。

## 4. 代表项目的完整双向过程

### 4.1 CodeGraph：代码关系快，但领域入口需要外接

**领域到代码**：Agent 把自然语言转成关键词/符号请求，`codegraph_explore` 召回节点和源码，再沿调用与依赖扩展。

**代码到解释**：从函数或文件沿结构边形成局部调用/模块图，由 Agent 总结。

**缺失环节**：没有以领域文档为主线的生成、审核与变更传播。适合作为代码侧基线，不能单独满足完整闭环（S007）。

### 4.2 Joern + codebadger：行为路径更深，领域入口仍需要外接

**领域到代码**：Agent 先通过文本/文档找到候选 source/sink 或入口，再用 codebadger 式高层 MCP 动作执行 Joern slice、dataflow、taint 和 semantic navigation。

**代码到解释**：从具体代码锚点取得跨函数路径和依赖，以源码位置组织行为说明。

**缺失环节**：CPG 不自动知道协议 Feature 和设计原因；自然语言到查询的正确性也需执行反馈。它适合证明“代码怎样运行”，不单独证明“为什么这样设计”（S015、S039）。

### 4.3 Graphify：把代码、文档和生成资产放在同一图中

**领域到代码**：对文档/PDF/媒体做可选语义抽取，使用 query/path/explain 从领域对象走到 Tree-sitter 代码实体。

**代码到解释**：由代码社区和路径生成 `GRAPH_REPORT.md` 或 Wiki，再从解释回链图节点。

**关键策略**：区分 `EXTRACTED`、`INFERRED`、`AMBIGUOUS`，因此 Agent 能知道哪些关系是解析器所得、哪些只是模型推断。

**待验证**：官方没有多 Target C 的链接 precision、过期修复率和最终问答正确率；其通用 memory Benchmark 不能回答这些问题（S021）。

### 4.4 Understand Anything：结构图与领域/流程图并存

**领域到代码**：自然语言询问 domain 或 flow，系统通过生成式领域图定位相关结构实体，再执行文件/函数 explain。

**代码到解释**：以文件或函数为入口，生成摘要、领域归属、flow、step 和 onboarding 资产。

**关键策略**：确定性的 Tree-sitter 结构事实与 LLM 产生的语义资产分层，并用 fingerprint 支持增量更新。

**待验证**：领域映射如何校验、跨版本如何精确失效、C 宏与 Target 如何隔离，公开材料均未给出效果数字（S009）。

### 4.5 RepoDoc：以代码图生成并维护交叉引用文档

**领域到代码**：用户先浏览按模块组织的仓库文档，再沿 API 和代码交叉引用定位实现。

**代码到解释**：RepoKG 与模块聚类为多 Agent 写作提供骨架，生成说明和 Mermaid 关系图。

**关键策略**：代码变化后双向影响传播定位受影响的文档，只对目标段落/模块重新生成。

**证据边界**：24 仓、8 语言的作者评估显示文档覆盖、完整性与增量成本改善，但未证明 WiFi MAC 的领域事实和 Target 链接准确（S041）。

### 4.6 LLM-Wiki / WiCER：文档组织方法，必须接上代码锚点

**领域到代码**：Wiki 负责把术语、历史探索和流程整理成可检索主题；只有主题页保存了 revision/Target 下的源码引用时，才能可靠下钻。

**代码到解释**：Agent 可把一次代码探索编译为主题页，再通过 evaluate/refine 循环改进知识。

**关键限制**：这类方法本身不解析 C，也不提供调用/dataflow。它应作为文档知识组织层与代码图组合，而不是单独候选（S022、S023）。

## 5. 链接证据的最小合同

本阶段不设计完整数据库 schema，但任何进入答案的链接至少应能导出下表字段：

| 字段 | 为什么需要 |
|---|---|
| `relation` | 明确是 implements、explains、produces、constrained-by 还是 mere similarity |
| `code_revision`、`target` | 防止把不同版本或构建变体混为一谈 |
| `code_location` | 允许用户直接核验文件、行号和符号 |
| `document_revision`、`document_location` | 允许核验规范、设计文档或生成页的具体来源 |
| `method` | 区分 parser/compiler、规则、人工、LLM/embedding |
| `generator_version` | 使结果可重建并识别工具漂移 |
| `status` | active、candidate、stale、contradicted、superseded |
| `validated_at/by` | 说明何时、由工具还是人确认 |

建议的权限只有三类，足以支撑本轮比较：

- **确定性事实**：编译器、解析器或固定规则在明确输入上产生；只在该输入范围内成立。
- **人工确认**：领域维护者基于代码与文档证据确认；不能覆盖相反的当前编译事实。
- **推断候选**：LLM、embedding 或聚类生成；可用于召回和排序，不能被 Agent 自行升级为事实。

Graphify 的项目术语可作为参考，但不能直接等同于本研究的统一权限定义。

## 6. 变更后怎样保持新鲜

链接生命周期应由依赖变化触发，而不是依赖 Agent 偶尔发现矛盾：

| 变化 | 必须失效或重算的内容 |
|---|---|
| 源文件内容或符号身份变化 | 代码实体、显式引用、模型映射、生成文档 |
| 编译命令、宏、头文件或 Target 变化 | occurrence、调用/dataflow、Target 范围内的流程说明 |
| 原始文档/规范变化 | 文档主张、领域映射、引用它们的答案与生成页 |
| 解析器、模型、prompt 或规则版本变化 | 对应方法产生的关系及置信度；旧结果保留审计但不得冒充当前结果 |

修复顺序应为：先尝试稳定符号/内容锚点重连；失败则标记 stale；重新抽取或生成；最后再由测试或人工验证。不能静默把旧链接移动到“看起来相近”的新位置。

## 7. WiFi MAC 示例

### 7.1 领域问题到代码

问题：“Host TX offload 在发送失败时怎样回收资源？”

需要的链接链：

1. 文档/Wiki 将 `Host TX offload`、发送失败、资源回收映射到 Feature/Flow 候选。
2. 构建事实把检索限制到启用对应宏的 Target。
3. 轻量图寻找发送入口、错误分支、释放/回收函数和相关消息。
4. 必要时用 CPG/dataflow 验证描述符或 buffer 从分配到释放的路径。
5. 返回每一步的 `file:line`、Target、revision，并把跨 Host/Device 消息标为 Event/Message，而不是伪造进程内 `CALLS`。

### 7.2 代码到流程

问题：“从 `wal_send_data` 出发解释数据发送流程。”

需要的链接链：

1. 在指定 Target 中解析该符号及其 occurrence。
2. 沿调用、回调、消息和数据依赖查找上下游；对未解析指针调用标出不确定性。
3. 关联现有设计文档、测试和生成流程页。
4. 按步骤生成解释，每一步回链代码；设计原因必须引用文档或标为推断。
5. 代码或宏配置变化时，让流程页进入 stale 并重新验证。

## 8. 后续 Benchmark 必须测什么

- 领域术语到 gold code anchors 的 Recall@K、MRR 和无答案拒答。
- 从代码锚点生成流程时，调用/事件步骤 precision、recall 与顺序正确率。
- 每条答案主张的 evidence coverage、Target/revision 正确率和推断误报率。
- 文档变更或代码重命名后的链接修复 precision/recall。
- 代码语义变化后的 stale detection recall，以及过期内容残留率。
- 普通导航、轻量图、深度图、图+文档链接之间的 Agent 正确率、时间、Token 和工具调用差异。

公开证据只能证明这些策略已被项目采用或在其作者实验中有效，尚不能确定哪一组合最适合 WiFiDemo。具体实验计划见 [benchmark-backlog.md](benchmark-backlog.md)。
