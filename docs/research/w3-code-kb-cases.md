## 二、逐案例架构方案详解（大白话）

下面把每个案例「两侧怎么连」讲透。不确定的地方用 **【不确定】** 标出，方便后续自己上网/找作者核实。

### C1 多仓领域 SDD 知识库（某网卡驱动系统，16 仓 4 层）

**两侧各是什么：**
- 代码事实侧：代码索引 CLI 给 16 个代码仓（git submodule 挂进来）建索引，9,817 文件 / 52,031 符号。查询命令 `代码索引 repo query <仓名> --query "关键词" --kind hybrid`（hybrid=语义+精确）。
- 知识文档侧：LLM-Wiki 把设计文档（spec.md/design.md）+ 服务 Wiki 原始文档，编译成结构化知识图谱——13 个实体页（每个核心组件一页）、6 个概念页（横切流程/规则）、28 个源摘要页。核心原则：**代码仓是唯一真源（spec.md/design.md 是 SSOT），Wiki 只是辅助**。

**两侧怎么连（大白话）：**
两侧**没有预建一张统一的图**，代码索引和文档图谱是两套独立的东西。真正的「连接」发生在 **Agent 用的那一刻**，靠两样东西拼起来：
1. **命名对齐**：实体页的文件名就是代码仓名（某组件的实体页对应 codebase/ 下同名代码仓目录），所以 Agent 看到某个实体，天然知道去哪个代码仓查。
2. **AGENTS.md 路由规则**：入口文件里写死了一张「关键词→去哪查」的表。比如问题里出现「驱动升级」→ 读对应的驱动升级概念页；出现「代码/实现/修复」→ 走代码索引查询；出现「设计/规范」→ 读设计文档目录。再配一个加载优先级 P0（知识图谱+代码索引）> P1（设计文档）> P2（原始文档）。

所以 C1 的「联合建图」其实是**「文档图谱 + 代码索引」两个独立索引，靠命名约定 + 路由规则在消费时拼接**，不是引擎自动把文档节点和代码节点连成边。

**【不确定】** 代码索引内部有没有建「代码符号 ↔ 文档实体」的自动映射（比如某个函数自动关联到某段文档），帖子没明说。从描述看更像是 Agent 查询时由 LLM 对齐，而非预建的双向图边。

**效果量化（作者自报）**：跨仓分析 240→15min、设计文档 480→60min、问题定位 180→20min、代码检视 120→25min、千行 Bug 5.2→0.8、新人上手 2-3 周→2-3 天。

### C5 存量代码仓知识库（某内部 AI 研发 Agent 流水线的逆向架构师）

**两侧各是什么：**
- 代码事实侧：`逆向架构师` Agent 对存量代码做深度分析，产出 13 个必选文件——模块结构、API 清单、调用链（Controller→Delegate→Logic→Repository 代码级路径）、数据模型、安全风险、依赖关系、耦合分析、配置扫描、技术栈、数据流、事件流、部署概览。
- 知识文档侧：三层递进文档 `raw/`（代码实证）→ `requirement/`（需求理解：用户故事/旅程/NFR/风险/测试场景）→ `design/`（架构还原：逻辑/技术/部署/可观测架构、交互序列、ADR）。配一套 **GAP 标注体系**：G1 代码实证 / G2 代码推断 / G3 待确认 / G4 逆向推导，可信度递减，G3/G4 必须在风险登记册闭环。

**两侧怎么连（大白话）：**
这是**单向「代码→文档」生成**，不是双向链接。连接机制是**代码证据锚点 + 可追溯矩阵**：
1. **行号锚点**：raw/ 里每引用一个类名/方法名，必须写成 `[类名](相对路径:行号)`，调用链标注密度要求 ≥ 80%。也就是说文档里的每句话都钉在源码的具体行上。
2. **可追溯矩阵**：FR 编号 → raw 来源 → 用户故事 → design 章节，全链路能追回去。
3. **层间引用**：requirement 层基于 raw 层提炼，design 层基于 raw+requirement 还原，**禁止跳层**（不能跳过代码实证直接写架构）。
4. **机器校验**：`code_evidence_verifier.py` 脚本会抽检 raw/ 里声称的类名/方法名在源码里是不是真的存在，不存在就报错。

所以 C5 的「链接」是**文档→代码的单向锚点（行号引用）**，代码是源头，文档是代码的「投影」。它**没有**「代码改了→自动定位哪段文档过期」的反向自动链接——增量靠 `git diff` 识别变更文件→映射到受影响子域→只重跑那些子域的 raw→req→design，未变更子域直接继承上一轮产出（省 50%~80% 工作量）。

**【不确定】** 是否有「代码变更→自动反向定位受影响文档段落」的机制。帖子说的「增量逆向」是 git diff 映射子域后重新分析，不是文档级反向链接。

**效果量化（作者自报）**：10 万行代码完整知识库 2~4 人月→1~3 天（10~40x）；API 契约/调用链/安全扫描 1~2 周→数小时（10~20x）。

### C6 跨仓知识工程（某跨仓知识图谱 CLI 工具，5 微服务仓 394 条跨仓调用）

**两侧各是什么：**
- 代码事实侧：`Tree-sitter` 静态分析（L2 代码逆向通道），提取 API 端点（endpoints.json）、HTTP 客户端调用（clients.json）、Import 语句、包依赖、RPC 客户端、特征点。支持 Java/Python/Go/TypeScript/C++ 五种语言。
- 知识文档侧：`Two-Step CoT 蒸馏`（L2 文档摄入通道），把文档蒸馏成知识原子。

**两侧怎么连（大白话）——这是十二个案例里唯一「真正联合建图」的：**
核心思想是**「知识原子化」**：代码和文档**都不保留原貌**，而是被「打碎」成统一格式的小知识块（叫 KnowledgeAtom，21 种节点类型、27 种边类型），全部丢进**同一个图数据库**（三库协调：SQLite 主库存原子、graph.db 存图结构、LanceDB 存向量）。

连边的关键在 **L3 知识图谱层**：
- **自动链接推理引擎（AutoInferenceEngine）**：这是核心。它不是人工去连，而是**引擎自动推断「原子 A 和原子 B 之间是什么关系」**，把边连上。比如推断「这个 API 端点原子」和「那段文档描述原子」其实说的是同一个东西，就连一条边。
- **KnowledgeGraph**：提供 BFS/DFS 图遍历，Agent 可以从一个原子出发沿着边走。
- **ConflictDetector**：检测连出来的边有没有矛盾（比如两处文档说法冲突）。

连完的图再用 **L4 多层级结构**组织成不同视角：
- **特性树（L1-L4）**：把业务能力按层级组织（顶层业务→子能力→具体特性）。
- **MOC（Map of Content）**：自动生成导航页，像 wiki 的目录。
- **4+1 视图**：从逻辑/进程/部署/实现/用例五个角度切同一张图。

跨仓场景走**五阶段 Pipeline**：单仓扫描 → **跨仓匹配**（三层级：Tier1 HTTP Method+归一化 Path 完全相等=高置信；Tier2 靠 Host 变量/服务名推断目标仓=中；Tier3 Path 前缀+模糊匹配=低）→ 图分析（networkx 检测循环依赖、算入出度、自动分类仓库角色 hub/server/client）→ 依赖图 → 全景视图。

**【不确定】** ① 自动链接推理引擎具体用什么算法推断边（规则匹配？LLM 判断？向量相似度？），帖子只说「自动推理」，没展开。② Two-Step CoT 蒸馏的「两步」具体是什么，帖子没细说。这两点建议找作者或查该 CLI 工具源码确认。

**对照评测（作者自报，5 仓 394 条跨仓调用，某大模型）**：有知识库 vs 无知识库，Token 278K vs 2.09M（7.5x 省）、工具调用 21 vs 52 次、定量准确率 100% vs 50%。但 Q7 陷阱题暴露盲区：基于 URI 匹配的跨仓链接**抓不到走服务发现（nacos/etcd）动态路由的调用**，知识库说「不存在」时 Agent 若盲信就会漏报——作者结论是「知识库查定量 + 源码验证定性」的混合推理。

### C9 知识库+代码双轨（某云安全项目密钥管理业务）

**两侧各是什么：**
- 代码事实侧：`CodeGraph`（SQLite 代码知识图谱，一次调用返回相关符号的源码/调用路径/影响范围）+ 仓级语义索引。代码=实现真相源。
- 知识文档侧：`LLM Wiki`，把散落在各内部文档/设计系统的异构文档，重组为**原子化概念节点**，用 `[[wikilink]]` 双向链接成知识图谱，持续重编译 + 冲突消解（录入时 + 巡检时两阶段拦截矛盾）。

**两侧怎么连（大白话）：**
两侧**各自独立建图、平时不连**。连接发生在**问答的那一刻**，靠双轨问答技能做**双轨问答编排**：
1. 派**知识库 Agent** 去查 LLM Wiki，回答「Why」（业务背景、设计决策、历史方案）。
2. 派**代码 Agent** 去查 CodeGraph/仓级语义索引，回答「How」（实际接口路径、字段命名、索引覆盖）。
3. **主 Agent** 把两边答案交叉印证：对得上就信；**发现冲突就如实报告**（比如知识库记接口是 `/api/v1/keys`，代码实际是 `/api/v2/keys`，主 Agent 会报出来，不静默忽略）；发现缺失就建议归档。

两侧能「对上」的前提是**架构元素名对齐**：工作空间里 `code/<架构元素名>/`、`knowledge/<架构元素名>/`、`design/<架构元素名>/` 三个目录都按某主数据平台的架构元素名组织，`config.yml` 记录「哪个架构元素对应哪些代码仓 + 哪个知识库」。这样两个 Agent 才知道自己查的是同一个业务对象。

**知识复利**：人确认过的高质量答案会归档回流到 LLM Wiki，知识库越用越完整（这是它比「RAG 只读不写」最独特的地方）。

**【不确定】** 主 Agent 判断「冲突」的具体算法（语义比对？规则匹配？阈值？），帖子只说「如实报告」，没给判定逻辑。

**效果（作者自报）**：需求澄清 13 轮问答 41 个问题挖出 4 个架构决策 + 5 张新表；双轨互证消除接口 URL/字段命名/索引覆盖的跨章节不一致。

### C11 三维一体架构（LLM-Wiki + 静态分析 + 引导文件，与 C6 同作者）

**两侧各是什么（其实是三层）：**
- 第一层「确定性地图」（代码事实侧）：`Tree-sitter + CodeGraph` 静态分析（**完全不用 LLM**，保证 100% 准确），生成三张图——类继承图、模块依赖图、接口实现图。用某自研代码扫描工具的 `scan <目录> --graphs` 命令，输出 JSON（机器读）+ Mermaid（人看）双格式。
- 第二层「语义化索引」（知识文档侧）：`LLM-Wiki` 思想改造版，LLM 扫代码核心模块 + 注释 + git commit 历史，**自动编译**出五类文档——ARCHITECTURE.md（为什么这么分层）、domain-models/（业务术语→代码包映射）、design-decisions/（为什么用分布式锁而不是本地锁，含决策/原因/替代方案/影响范围四段式）、api-contracts/、data-models/（实体/ER 图/Schema）。
- 第三层「认知引流」：项目根目录一个 ≤200 行的 `AGENTS.md` 引导文件。

**两侧怎么连（大白话）：**
**三层递进，下层给上层打基础**：
1. 第一层用编译器技术画出 100% 准确的代码拓扑（谁调谁、谁继承谁、谁实现谁）——解决「代码**怎么连**」。
2. 第二层让 LLM 读代码+注释+git 历史，把「**为什么**这么设计」写成文档。**关键：第二层文档里会引用第一层的具体代码位置**（比如 design-decisions 里写「影响范围：某服务方法 (src/service/某文件.java:45)」）——这是文档侧和代码侧的**锚点连接**。
3. 第三层 AGENTS.md 是「导游图」，用**指针式导航**把场景串起来：「修改某模块：先读 domain-models/某模块.md，再查 class-hierarchy.mmd 确认影响范围」。Agent 启动只读这个 200 行文件，被指派任务时再顺着指针**按需**去读对应的文档片段和代码——解决上下文溢出。

**查漏补缺**：专门设计了「第二双眼睛」步骤，五维检查（API 端点/数据模型/接口实现/模块依赖/设计决策遗漏），用 codegraph 系列查询去对比 scan 产物，发现遗漏就补，生成 gap-report.json。按优先级采样（P0 核心入口 100%、P1 数据层 ≥80%、P2 工具配置 ≥50%），不逐文件扫。

**【不确定】** ① 第二层文档和第一层图谱之间有没有**自动反向链接**（改代码→自动更新对应文档），帖子把「增量更新（监听 git diff）」列在「后续演进方向」，说明当前是**全量生成**、还没有自动反向失效。② 自研扫描工具的 scan 具体实现细节帖子没展开。

### C12 大型 C 代码仓 Function-Skeleton 知识图谱（某内部技术大赛已入围）

> 这是增量搜索补进来的，**C 代码 + 函数指针断链**最贴我们 WiFi MAC 驱动场景，单列。

**两侧各是什么：**
- 代码事实侧：`tree-sitter` 静态扫描 C 代码仓，把**函数名当实体（Entity）、函数调用关系当边（Relation）**，输出两个文件——`nodes.ndjson`（实体，带属性：函数声明、所在路径、签名、起止行、callee 列表、用到的枚举/结构体/全局变量）+ `edges.ndjson`（关系，边类型有 `calls`/`uses_macro`/`uses_struct`/`impl_in`/`decl_in` 等）。
- 知识文档侧：**没有独立的文档图谱**。架构/领域信息（所属架构分层、是否对外 API、是否外部依赖）作为**属性挂在函数节点上**，依附在调用树里，而不是单独建一张文档图。

**两侧怎么连（大白话）：**
核心是**「代码调用骨架图为主，领域信息挂属性」**，分生成和消费两步：
1. **生成**：tree-sitter 扫出所有函数节点和调用边。但 C 语言有个老大难——**函数指针/宏包装的调用 tree-sitter 解析不到（「断链」）**，比如 `func_ptr(para1, para2)` 不知道 func_ptr 指向谁、`FUNC_CALL(func_name, ...)` 宏把函数名藏起来了。作者给两条路：单领域用**穷举 + 正则**（简单但通用性差）；通用做法是**用预编译（compile_commands.json）展开宏定义**，再模式匹配 `func_ptr()` 调用，进一步通过符号分析/全局搜索/AI RAG 辅助找指针真实指向。
2. **消费**：从顶层 API 建调用链（向上查 caller、向下查 callee），然后**剪枝**——用 **TF-IDF 思想**（一个函数被越多调用树共用就越「普通」、越该剪；在本树内出现越多就越「关键」、越该留），保留关键骨干、去掉次要细节，最后包成一个 Skill 给 AI 消费。

**和我们场景的关系（重点）：**
- 它**正面解决了我们 CPG 的边界问题**——函数指针/ops 表间接调用「直接 caller 为 0」。作者明确把「断链」列为方案核心难点，并给了 compile_commands.json 展开宏 + 符号分析 + AI RAG 辅助的解法。这和我们真实代码仓里函数指针/ops 表经分发表调用、CPG 直接 caller 为 0 的场景**完全对应**。
- 它的「文档图谱侧」很轻（只是节点属性），所以严格说**不是完整的「代码事实图谱 + 知识文档图谱」双图**，而是「代码图 + 属性」。但它的**代码事实侧对 C 代码的处理深度**（函数指针断链、宏展开、TF-IDF 剪枝）是十二个案例里最强的，对我们 K2（Joern 深分析）和 CPG 边界问题最有参考价值。
- 代码已内部开源（某内部代码仓的 C 解析引擎目录），有百万行级 Demo 和调用链可视化网站，**可联系作者拿源码**。

**【不确定】** ① 函数指针断链的自动修复**覆盖率**多少，作者没给数据（大赛评委意见也明确要求补这个）。② 与纯 RAG 方案的对比评测，作者也没做（评委同样要求补）。这两点建议找作者确认。

**两侧各是什么：**

1. 代码侧和文档侧**都挂到同一个限界上下文**上——代码特性挂主责上下文，业务文档也粗挂到上下文，于是「问某条特性影响什么」先落到主责上下文，代码和文档在同一坐标下对齐。

4. **按限界上下文全链路逆向**：每个限界上下文都要把「页面→中台→数据集成写入→引擎→数据集成读回」五段核完。

- 它的「限界上下文」主轴和我们 paper 里「领域模型作为代码/文档共同锚点」的思路一致，且给了**双轨互证的具体编排**（冲突两边都记、以代码为准），可直接借鉴。

**【不确定】** ① 12 个限界上下文 + 59 条特性的**维护成本**（代码/文档变更后怎么增量更新），帖子提到「新文档只做增量、不重跑初始化」，但代码侧增量机制没展开。② 五仓初始化的「同名率不低于 85%」这个验收指标怎么算的，帖子没给细节。

### C8 知识是对信息的压缩—产品知识库为什么只认五种原子？（产品知识库设计复盘·第二篇）

> 这是第四轮扩展搜索（关键词「知识原子」）补进来的，**「两库彻底分离 + 单向引用」**是十二个案例里对「代码侧和文档侧边界」讲得最干净的一个。

**两侧各是什么：**
- 代码事实侧：**sys_kl 系统逻辑知识库**，由**自研代码逆向工具**从代码逆向生成，含 7 种节点——Context（限界上下文）、Aggregate（聚合）、Invariant（不变量）、Policy（策略）、CodeAnchor（代码锚点）、APIEndpoint（接口）、DataEntity（数据实体）。
- 知识文档侧：**biz_kl 业务知识库**，由**自研业务知识库构建工具**从业务文档（详细设计等）压缩融合生成，含 **5 种知识原子**（Entity 实体 / Rule 规则 / Process 流程 / Configuration 配置 / Term 术语）+ **7 种有类型关联**（约束 Rule→Entity、触发 Process→Rule、操作 Process→Entity、依赖 Rule→Configuration、包含 Entity→Entity、衍生自 Entity→Entity、前置于 Process→Process）。

**两侧怎么连（大白话）：**
核心是**「两库彻底分离 + 单向引用」**：
1. **两库分离**：sys_kl 和 biz_kl 不合并。理由有三——演进节奏不同（业务规则一年改两次、代码一周改两次，混在一起 Health Check 没法独立判断）；消费视角不同（产品经理读 biz_kl 关心「业务是什么」、开发者读 sys_kl 关心「代码在哪」）；生产路径不同（biz_kl 由自研构建工具从业务文档融合、sys_kl 由自研逆向工具从代码逆向，两条生产线交叉会让调试归因困难）。
2. **单向引用**：biz_kl 的 Entity 通过 CodeAnchor 引用 sys_kl 的 Aggregate、Rule 引用 sys_kl 的 Invariant、Process 引用 sys_kl 的 Scenario（验收场景），**反向禁止**——「代码是事实，业务是解读」，倒过来会让 sys_kl 的客观性受污染。
3. **cross-validate 第三方校准层**：站在第三方位置做校准，前提是「被校准的几方独立」（biz_kl、sys_kl、代码三方独立），漂移类型才能被清晰分类；如果合并，校准退化为「自检」，价值大跌。

**和我们场景的关系：**
- 它的「**代码是事实，业务是解读**」单向引用纪律，和我们 paper 里「代码事实侧是底座、文档侧是解读层」的 2+1 模型高度一致，且把「为什么不能反向依赖」讲得很透，可直接借鉴。
- 它的「5 原子 + 7 关联」是**文档侧知识图谱的最小可遍历 schema**（三轮减法收敛，少一种走不通、多一种冗余），对我们「文档侧节点类型怎么定」有直接参考价值。
- 它的 cross-validate 三方独立校准，和我们「代码+文档互验」思路一致，且强调了「被校准方必须独立」这个前提。

**【不确定】** ① 自研逆向工具从代码逆向出 sys_kl 的 7 种节点，**具体用什么解析技术**（AST/调用图/符号图）帖子没展开（系列其他篇可能有）。② 5+7 的可迁移性作者自己标注「集中在企业级供应链软件，换一类业务覆盖度可能不一样」，对我们 C 驱动场景是否适用需验证。

### C13 双库融合驱动：LLM Wiki + Graphify 协同的安全问题单自修复实践

> 这是第五轮扩展搜索（关键词「Graphify」）补进来的，**第一个用开源工具（Graphify + LLM Wiki）在真实代码仓上落地双图**的案例，且**明确论证了「为什么不全量用 Graphify」**——直接命中我们「代码图+独立文档 vs 双图一体」的选型问题。

**两侧各是什么：**
- 代码事实侧：**Graphify** 从某安全组件代码仓建图。两轮提取——第一轮 AST 确定性提取代码结构（不依赖 LLM，快且准），第二轮 LLM 语义提取文档/论文/图片；Leiden 社区发现（不依赖向量库）识别功能社区（加密/脱敏/审计/过滤器等），提供组件的 Maven 依赖、Java 导入、配置要求、使用示例。SHA256 缓存增量更新，查询 Token 降低 71.5 倍。
- 知识文档侧：**LLM Wiki**（Karpathy 方法论 + Obsidian 双向链接）安全知识库，按 concepts（概念）/features（功能）/troubleshooting（排查）/comparisons（对比）四类组织，单页含完整的问题原因+修复步骤+代码示例+依赖配置+注意事项，Ingest/Query/Lint 三操作维护。

**两侧怎么连（大白话）：**
核心是**「异构混合 + 消费时两步定位」**，且作者专门对比了「全量 Graphify」方案并明确拒绝：
1. **分工**：LLM Wiki 管「为什么/用什么」（问题解决方案、推荐哪个安全组件），Graphify 管「在哪/怎么写」（组件的 Maven 依赖、导入、配置、用法）。
2. **消费时两步定位**：先查 LLM Wiki 锁定目标组件（如「该用某安全组件的 XX 脱敏组件」），再查 Graphify 拿组件的准确引入路径和用法，融合成完整修复方案——「代码引用零幻觉」（组件用法来自真实代码）。
3. **为什么不全量 Graphify（关键论证）**：作者对比了「异构混合」vs「全量图谱（万物皆节点）」——全量方案把自然语言描述和代码实体强行拉平到同一维度，跨维度路径（需求描述→具体函数）计算开销大、易迷失；维护上任何文档改动都可能触发图谱关系重建。异构混合则「语义与结构解耦」：文档更新只重索引 Wiki 页、代码更新只重建 Graphify 图，互不影响。**这和我们 C8「两库分离」的结论一致，但 C13 用的是两个独立开源工具、C8 是自研两库。**

**和我们场景的关系：**
- 它是**唯一用开源工具（Graphify + LLM Wiki）落地双图的案例**，正好对应我们 w4 选型里「Graphify（P3）+ LLM Wiki（文档侧）」的组合路线，可作为部署参照。
- 它的「**为什么不全量 Graphify**」论证，直接支持我们「代码图 + 独立文档层」而非「双图一体」的倾向——和我们 paper 2+1 模型一致。
- 它的「消费时两步定位」（Wiki 锁定组件→Graphify 定位用法）是一种**消费时路由**的变体，和 C1 的「路由规则拼接」同类，但更结构化（两步固定流程）。

**【不确定】** ① 代码仓是 Java（某安全组件），**不是 C 语言**——Graphify 对 C 驱动仓（函数指针/宏/ops 表）的解析质量帖子没验证，需我们 ut_agent 实测。② 帖子没给「修复成功率/准确率」等量化指标（实践效果部分是截图，未读全），双图带来的净收益缺数据。③ LLM Wiki 和 Graphify 之间**没有图级链接**（是消费时 Agent 两步查，不是图内连边），严格说「链接」是流程编排而非图结构。

### C14 SDD × 深度代码知识库 × CodeAgent CLI 知识驱动设计实践（某电信云产品，417 仓）

> 这是标准放宽复审补进来的，**「深度代码知识库驱动 SDD 设计」**，是十二个案例里代码知识库侧最「重」的一个（4+1 视图+六件套+跨仓契约），且文档侧是知识库自动生成的结构化知识页（不是独立领域知识库，但比 C16 的 SDD 过程产物更知识库化）。

**两侧各是什么：**
- 代码事实侧：**某深度代码知识库工具**（内源）。417 个 Git 子模块 ingest、20 个核心子系统深度分析，知识模型是 **4+1 视图**（用例/逻辑/实现/运行/契约）+ **流程六件套**（调用树/主干流程/分支/跨边界数据流/数据结构/自查报告）。每个子模块生成 6 类制品（overview/architecture/api-surface/data-models/constraints/specifications + flows/）。
- 知识文档侧：该工具自动生成的结构化知识页 + 跨仓知识——**26 份跨仓契约**（REST API、RPC 协议、ZooKeeper HA 等）+ **15 个业务领域定义** + **5 个端到端跨域用例**（VM 创建、热迁移、网络开通等）。

**两侧怎么连（大白话）：**
核心是**「KB-First 查询」**——设计时 Agent 不先问用户，而是先查知识库：
1. **query skill**：CodeAgent CLI 原生集成，设计 Agent 遇到需求澄清问题时，先查知识库（架构/契约/流程/数据模型），能答的自动答，答不了的才问用户。实测 4/6 澄清问题由 KB 自动回答。
2. **信息池机制**：所有 SDD 步骤（需求澄清→SRS→SID→任务规划→代码生成）共享一个信息池，避免「查了又忘」「前后矛盾」。
3. **validation.md 跨文档校验**：设计文档生成后自动做跨文档一致性校验，遗漏在生成阶段就被发现，而非等到编码/测试阶段。
4. **增量更新**：通过 git diff 映射变更到受影响知识页，代码仓 merge 后自动触发。

**效果量化（作者自报）**：设计文档生成效率提升约 70%；知识检索从「人工翻阅 4-8 小时」变为「KB 自动查询分钟级」；需求澄清从「10/10 人工回答」变为「7/10 KB 自动回答」。

**【不确定】** ① 该深度代码知识库工具是内源工具，**具体解析技术**（AST/调用图/符号图）帖子没展开，只说「深度语义分析」。② 417 仓中只有 20 个核心子系统做了深度分析，非核心仓查询无结果（作者自己标注「覆盖度不足」）。③ 文档侧是知识库从代码 ingest 自动生成的，**不是独立领域知识库**——和 C5 同性质（代码→文档单向），但 4+1 视图+六件套比 C5 的三层递进更结构化。

### C15 百万行代码仓鸿蒙迁移实践总结（某笔记应用，安卓→鸿蒙 ArkTS）

> 这是标准放宽复审补进来的，**「跨仓依赖图驱动迁移 spec」**，是十二个案例里代码规模最「大」的一个（126 万行 4 仓），且效果最「硬」（迁移准确率 10%→80%）。文档侧是迁移 spec（从代码反向抽取），不是独立领域知识库。

**两侧各是什么：**
- 代码事实侧：跨仓调用图/依赖图/隐式调用分析。126 万行 4 仓（App 50 万行/Core 30 万行/Render 5 万行/Shared 1.4 万行 Java/KT + 37 万行 C++），**1790 跨仓调用点/216 跨仓符号**，收敛 5 条主依赖边（Core→Render 最密 1051 调用点，仅一个渲染符号就有 495 调用点）。
- 知识文档侧：迁移 spec（从代码反向抽取的功能级 spec：功能点/接口/数据/边界/验收条件），区分 what（功能描述/验收标准/接口定义）和 how（实现细节）。

**两侧怎么连（大白话）：**
核心是**「代码依赖图决定 spec 粒度（弹性压缩）」**：
1. **跨仓依赖图驱动 spec 拆分**：跨仓依赖图决定哪些功能点需要跨仓 spec（一个功能常同时改 3-4 个仓），spec 粒度按依赖边密度调整。
2. **弹性压缩**：百万行仓下上下文装不下，spec 要区分「哪些只写 what（功能描述/验收标准/接口定义）、哪些必须写 how（实现细节）」——粒度分错，模型就翻译错。
3. **spec 指导 AI 翻译**：spec 是 AI 翻译的「参照系」，AI 按 spec 逐功能点翻译，跨仓符号语义对齐靠 spec 约束。
4. **撤销/重做一致性**：~40 种独立操作每种含做/撤销/重做三态，spec 要覆盖三态一致性。

**效果量化（作者自报）**：迁移准确率 10%→80%（此前自动翻译从未真正针对百万级代码仓做过迁移）；参照系：iOS→Android 人工迁移 3 人半年。

**【不确定】** ① 代码侧的「跨仓调用图/依赖图」具体用什么工具建（tree-sitter/CodeGraph/自研），帖子没展开。② 文档侧是迁移 spec（为完成迁移而写），**不是独立领域知识库**——和 C5 同性质（代码→文档单向），但 spec 粒度更粗（功能级，不是行号级）。③ 37 万行 C++ 的跨语言桥迁移细节帖子没展开。

### C16 CodeAgent3.0 基于Graphify知识图谱与SDD工作流的自动化开发实践（某迭代评估系统，Java 109 文件）

> 这是标准放宽复审补进来的，**「Graphify 图谱驱动 SDD 上下文工程」**，和 C13 都用 Graphify，但 C13 文档侧是 LLM Wiki（独立知识库）、C16 文档侧是 SDD 过程产物（SRS/SID/tasks）。纳入后可对比「Graphify+独立文档」vs「Graphify+SDD 过程产物」两种组合。

**两侧各是什么：**
- 代码事实侧：**Graphify** 建图。109 个源码文件（约 141,335 词），**5715 节点/15988 边/249 社区**（88% 直接提取 + 12% 推断，平均置信度 0.8），识别迭代评估树配置/迭代基础服务/迭代结论/缺陷分析/版本信息/风险评估/通知推送等功能社区。
- 知识文档侧：SDD 过程产物（SRS 需求规格说明书/SID 实现设计说明书/tasks 任务规划），为完成「迭代评估自动启动与一键完成」需求而写，**不是独立领域知识库**。

**两侧怎么连（大白话）：**
核心是**「上下文工程」**——SDD 各阶段优先查 Graphify 知识图谱定位相关代码：
1. **SRS 生成**：通过 `graphify-out/` 知识图谱快速定位现有迭代评估相关代码结构（基础服务、结论实体等），生成包含 6 个 UseCase 的标准化 SRS 文档。
2. **SID 生成**：基于 SRS 和知识图谱中的调用关系分析，设计 6 个功能点的实现方案，定义类结构/接口定义/调用关系/状态流转。
3. **任务规划**：按 TDD 原则拆解 7 个 Task（数据模型→指标检查→自动启动→自动完成→定时任务→Controller→集成测试），按依赖顺序排列。
4. **代码生成**：按任务逐一生成代码，调用 Java 规范 skill 确保符合规范。新增/修改 17 个文件，共 2002 行变更。

**效果量化（作者自报）**：Token 消耗 80,679 input tokens（建图）；代码生成 17 文件/2002 行；SDD 全流程（需求澄清→SRS→SID→任务规划→代码生成→Git 暂存→UT 测试→测试修复）端到端完成。

**【不确定】** ① 代码仓是 Java（某迭代评估系统），**不是 C 语言**——Graphify 对 C 驱动仓（函数指针/宏/ops 表）的解析质量帖子没验证，需我们 ut_agent 实测。② 文档侧是 SDD 过程产物（SRS/SID/tasks），**不是独立领域知识库**——和 C5/C15 同性质（代码→文档单向），但更「过程化」（为完成某个需求而写，不可复用为知识库）。③ 帖子没给「需求完成度/代码质量」等量化指标（效果部分是开发过程描述，未读全）。

**对我们（WiFi MAC 驱动，host/device 多仓 + 宏/函数指针/Event-Message）的启示：**
1. **没有一家是「纯文档」或「纯代码图」**——全部是代码事实为底座 + 某种文档层，区别只在文档层是「联合建图」（C6）还是「独立管理」（C1/C9）。这印证了我们 paper 的 2+1 模型。
2. **链接时机分两派**：C6 是「建图时预建边」（重，但查询快）；C1/C9/C11 是「消费/问答时拼接」（轻，但每次要 Agent 对齐）。我们 K0–K2 实验可以分别测这两派的增量价值。
3. **C6 的自动链接推理引擎**是我们 paper 里「模型语义映射只能先进候选层」的内部工程实现，值得重点研究它怎么控制连边精度（ConflictDetector）。
4. **C5 的 GAP 四级标注**和我们「三类权限标注 / may-must 区分」思路一致，可直接借鉴其标注体系 + 代码证据抽检脚本。
5. **C9 的双轨互证**是我们 2+1 模型中「代码+文档互验」的内部实践，「冲突如实报告」的编排可直接参考。
6. **C11 的三层分工**（确定性地图/语义索引/引导文件）和我们「轻量图打底 + 文档层 + AGENTS.md 路由」的组合过程高度吻合，可作为 P1（K*+基础架构 Skill）的参照。
7. **C12 的 C 代码函数指针断链解法**（compile_commands.json 展开宏 + 符号分析 + AI RAG 辅助找指针真实指向）直接对应我们 CPG 的函数指针/ops 表边界问题（直接 caller 为 0）。它的「文档图谱侧很轻、领域信息挂属性」也提示我们：**对 C 驱动场景，代码事实侧的深度（断链修复）可能比文档图谱侧的丰富度更关键**——这和我们 paper「先选代码工具 K*，再叠文档层」的两阶段设计一致。建议联系作者拿源码，重点看断链修复覆盖率。
8. **C7 的「限界上下文」共同主轴 + 双轨互证编排**：代码特性和业务文档都挂到同一个限界上下文，文档吸收时拿代码核对、冲突两边都记以代码为准。这给我们「代码/文档怎么对齐到同一坐标」提供了一个比 C9「问答时印证」更前置的方案（建图时就对齐，而非消费时对齐），且「冲突两边都记、以代码为准」的编排可直接借鉴。
9. **C8 的「代码是事实，业务是解读」单向引用纪律**：biz_kl 只能引用 sys_kl、反向禁止，保证代码侧客观性不被业务解读污染。这和我们 2+1 模型「代码事实侧是底座、文档侧是解读层」一致，且把「为什么不能反向依赖」讲得很透；它的「5 原子 + 7 关联」是文档侧知识图谱的最小可遍历 schema（三轮减法收敛），对我们「文档侧节点类型怎么定」有直接参考价值。
10. **C13 的「异构混合 + 消费时两步定位」是开源工具落地双图的参照**：用 LLM Wiki（文档侧）+ Graphify（代码侧）两个独立工具各管一侧，消费时「Wiki 锁定组件→Graphify 定位用法」两步查。它**明确论证了「为什么不全量 Graphify 万物皆节点」**（跨维度路径开销大、维护耦合），和 C8「两库分离」结论一致——这给我们「代码图+独立文档层 vs 双图一体」的选型提供了内部实证支持。注意它是 Java 场景，C 驱动仓上 Graphify 的解析质量（函数指针/宏/ops 表）需我们 ut_agent 实测。
11. **C14 的「深度代码知识库 + KB-First 查询」是代码知识库侧最「重」的参照**：4+1 视图+六件套+26 份跨仓契约+15 业务领域+5 端到端用例，是十二个案例里代码知识库侧最结构化的。它的「KB-First 查询」（设计时先查知识库、答不了才问用户，4/6 澄清问题 KB 自动回答）+「信息池机制」（所有 SDD 步骤共享信息池避免前后矛盾）+「validation.md 跨文档校验」（遗漏在生成阶段发现）三个机制可直接借鉴。注意该工具是内源工具，具体解析技术帖子没展开，且 417 仓中只有 20 个核心子系统做了深度分析。
12. **C15 的「跨仓依赖图驱动迁移 spec + 弹性压缩」是大规模迁移场景的参照**：126 万行 4 仓、1790 跨仓调用点，跨仓依赖图决定 spec 粒度（哪些只写 what、哪些必须写 how），迁移准确率 10%→80%。它的「弹性压缩」思路（百万行仓下上下文装不下，spec 要区分 what 和 how 的粒度）对我们「大仓怎么拆 spec」有直接参考价值。注意文档侧是迁移 spec（一次性产物），不是独立领域知识库。
13. **C16 的「Graphify 图谱驱动 SDD 上下文工程」和 C13 形成对照**：C13 是「Graphify+LLM Wiki（独立知识库）」、C16 是「Graphify+SDD 过程产物（SRS/SID/tasks）」，两者都用 Graphify 建图（都是 Java），但文档侧性质不同。C16 的「SDD 各阶段优先查图谱定位相关代码」是一种轻量的上下文工程，适合「没有独立知识库、只有代码仓」的场景。注意它是 Java 场景，C 驱动仓上 Graphify 的解析质量需我们 ut_agent 实测。
