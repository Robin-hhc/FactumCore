## 三、关键观察

1. **两条路线内部都有人走，且都有量化收益**：
   - "重文档/一体化"路线：C1（Wiki×代码仓联合建图，千行 Bug 5.2→0.8）、C3（DeepWiki 自进化）、C8（图谱→Skill 文档）
   - "代码图谱+独立文档"路线：C2（纯代码图谱）、C4（仓内 `.repo-knowledge/` 版本化）、C6（六层图谱+自动生成文档产物）、C9（双轨互证）、C10（文档自动生成）
   - 没有案例是"纯文档"或"纯图谱"——全部是代码事实为底座 + 某种文档层，区别只在文档层是"联合建图"（C1）还是"独立管理"（C4/C9）。
2. **驱动/底层场景已有直接对标**：C1（某网卡驱动 16 仓 4 层）、C2（底软驱动隐性调用链：函数指针/中断延迟调用）——C2 的"隐性调用链静态查询"与我们 CPG 的函数指针/ops 表边界问题直接对应，可联系其技术负责人获取详情。
3. **文档保鲜是共同痛点，解法趋同**：C3（源码核实+自进化闭环）、C4（推断标注置信度+未知改动同步场景）、C5（增量逆向省 50%~80%）、C9（持续重编译+wiki-lint 冲突消解）——都采用"代码变更触发文档更新 + 不确定性显式标注"，与我们 5.3 页保鲜标准（四类变化+修复顺序）方向一致。
4. **有对照评测的先例**：C6 做了"有/无知识库"两组 Agent 对照（4 道跨仓理解题）——我们"以 grep 为基准逐层加能力"的实验设计有内部先例支撑，且 C6 的六层架构（L1 原子→L5 GraphRAG→L6 MCP）可作为分层加能力的参照系。
5. **工具选型内部共识与 R2 架构结论一致**：tree-sitter 解析层 + SQLite/图存储 + MCP 接入 = 主流；CodeGraph 在性能/Token/协议（MIT）上被内部评价最高（R1/R3）；Graphify 的多模态是独家能力但 AGPL 协议对商用是硬约束（R1）；跨仓联邦图谱是下一前沿（R2），C1/C6 已各自给出工程实现。
6. **可立即借鉴的具体资产**：C4 的 `.repo-knowledge/` 目录结构 + 5 场景提示词（可直接抄）；C5 的代码证据校验脚本 + GAP 标注体系；C6 的跨仓三层级匹配策略（HTTP Method+Path 归一化）；C9 的双轨问答编排（知识库 Agent+代码 Agent+主 Agent 冲突上报）；C1 的 SDD 工作空间创建 Skill（帖内附获取方式）。
