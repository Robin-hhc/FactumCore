# WiFi MAC 代码知识架构选型研究设计

日期：2026-08-13
状态：待用户复核

## 1. 研究目的

本研究面向与 WiFiDemo 结构相似的工业 WiFi MAC C/C++ 代码仓，从零选择最合理的代码知识与领域知识架构。研究不考虑 WiFiGraph 既有实现、迁移成本或可复用资产，也不预设必须采用单一知识图数据库、Joern、SQLite、MCP 或任何具体工具。

核心问题是：

> 面对宏密集、多 Target、Host/Device 分离、Hook 和 Event 大量存在的 WiFi MAC 代码仓，哪种知识表示、事实提取、领域知识管理和 Agent 检索架构，能够最可靠且经济地支持工程分析？

当前阶段只完成基于公开证据的架构选型，不开展工具实现、WiFiDemo 对比实验或完整生产系统建设。现有证据无法裁决的关键差异必须明确记录为证据缺口，并转入后续独立的 Benchmark 与实验开发工作。

## 2. 研究对象与客观约束

研究从 `目标代码仓注意事项.md` 提取问题特征，但不继承其中对 Metadata、Joern 或 Agent 职责的既有划分。

目标代码仓的关键特征包括：

- 百万行级 C/C++；
- 多芯片、多产品、多 Target，Target 集合开放；
- Host/Device 分离并拥有不同编译环境；
- 公共源码在不同 Target 中具有不同的实际 occurrence；
- 数百个宏和大量条件编译；
- ops、Hook、callback 和函数指针；
- Event 可能具有多个 producer、consumer 和 Target-specific handler；
- 同名函数、日志字符串和 `file:line` 定位；
- Agent 上下文、工具调用和查询延迟受限；
- 工程知识可能缺失、错误或随代码演进而失效。

## 3. 研究原则

### 3.1 结论开放

允许最终结论是单一图、多个图、CPG 与结构化索引组合、Wiki/Skill/RAG 与代码事实分层，或其他混合架构。不得把“必须建设一张完整知识图谱”作为前提。

### 3.2 证据优先

只将以下材料作为主要依据：

1. 论文原文及其公开实验材料；
2. AI 相关公司发布的官方技术文章和产品工程资料；
3. 开源项目官方文档、设计说明、Benchmark 和可复现实验材料。

社区评论、营销转述和二手摘要只能用于发现线索，不能支撑核心结论。

### 3.3 时间相关性按具体情况判断

近期材料用于观察当前解决方案、Agent 工作方式和最新实证结果，原则上优先检索最近半年。时间窗口不是硬性排除条件：

- Joern、CPG、程序切片、静态分析等长期技术可以引用更早的经典论文或官方资料；
- 旧资料必须仍能解释当前技术能力，且应说明其持续相关性；
- 工具性能、产品架构、模型效果和项目成熟度属于高时效信息，应优先使用近期版本；
- 不用多年前的性能数据证明当前版本一定更优；
- 若旧结论已被近期实验重新验证，优先引用近期验证，同时保留必要的经典定义来源。

### 3.4 数据可审计

每个数值结论应尽量记录：

- 样本量和代码仓数量；
- 语言与项目类型；
- 固定 commit 或数据版本；
- 使用的模型和 Agent 框架；
- 对照基线；
- 指标定义；
- 是否为项目第一方数据；
- 实验限制和可能的利益相关性。

不同定义的 accuracy、coverage、pass rate、F1、Token 和 tool calls 不直接合并比较。

## 4. 研究问题

- **RQ1：代码事实表示。** 源码检索、符号索引、语法结构图和语义 CPG 分别能够可靠回答哪些问题？
- **RQ2：构建视角。** 哪种方式能正确表达 Target、宏和条件编译后的实际代码视角？
- **RQ3：间接关系。** Hook、ops、callback、Event 和 Host/Device 跨边界关系应如何表达，并如何避免把候选关系冒充确定事实？
- **RQ4：领域知识。** Feature、Flow、协议约束、设计原因和 Known Edge Cases 应进入代码图、独立知识层、Wiki/Skill，还是保留原始资料按需检索？
- **RQ5：检索架构。** 单一大图、Target-specific 图、分层索引和 Agent 渐进检索之间如何权衡？
- **RQ6：知识生命周期。** 如何表达 provenance、置信度、版本、人工修正、过期和重新验证？
- **RQ7：工程代价。** 各方案在索引、增量更新、查询、上下文、工具调用、部署和维护方面的成本如何？

## 5. 候选架构族

研究先比较架构族，再将具体工具映射到架构能力，避免把版本差异误认为架构结论。

### 5.1 源码与文本检索

包括 grep、符号索引、RepoMap、BM25、向量检索、GraphRAG 和原始文档检索。它们构成最低复杂度基线，也用于判断图结构是否真的带来增益。

### 5.2 语法结构图

以 Tree-sitter、AST、import、symbol、direct-call 和 community discovery 为主。重点考察索引速度、增量更新和 Agent 导航收益，同时验证宏、Target、CFG、数据流和函数指针边界。

### 5.3 语义程序图

以 CPG、CFG、控制/数据依赖、程序切片和 taint/dataflow 为主。重点考察 C/C++ 事实深度、预处理配置、资源成本和面向 Agent 的高层查询接口。

### 5.4 分层混合架构

将代码事实、构建事实、工程元数据、叙事领域知识和 Agent Workflow 分为不同层。研究重点不是默认其正确，而是验证分层是否比单一大图更准确、经济并易于更新。

## 6. 证据组织方式

### 6.1 当前解决方案调查

优先罗列近期有代表性的解决方案，回答：

- 它解决什么问题；
- 代码事实来自编译器、Parser、LLM 还是人工；
- 是否区分代码事实与领域知识；
- 如何向 Agent 暴露检索；
- 是否提供公开数据；
- 数据是论文、独立实验还是项目自测；
- 对宏密集、多 Target C/C++ 是否有直接证据。

候选至少覆盖 CPG/Joern 类、Tree-sitter Code Graph 类、代码与知识混合图类、Wiki/Memory/Skill 类，以及不使用知识图谱的代码检索基线。

### 6.2 横向证据矩阵

统一记录以下维度：

- Target 与宏正确性；
- 直接调用、间接调用、CFG 和数据流；
- Host/Device 与 Event 表达；
- `file:line` 证据与 provenance；
- 歧义、不确定性和 abstention；
- 索引时间、增量成本与查询延迟；
- Agent 最终正确率、Token 和工具调用；
- 人工维护和知识过期成本；
- 离线部署、开放性与复现难度。

### 6.3 证据等级

证据按用途区分，而不是简单混为一个排名：

1. 独立、可复现、与目标场景接近的实证研究；
2. 同行评审或公开预印本中的受控实验；
3. AI 公司官方的大规模生产实践或明确技术设计；
4. 开源项目公开 Benchmark；
5. 项目功能说明和案例展示。

公司实践适合证明架构正在被采用，项目案例适合证明可行性；二者不能单独证明准确率优于其他方案。

## 7. WiFiDemo 的使用边界与后续实验议程

### 7.1 WiFiDemo 在本研究中的角色

本研究只从 WiFiDemo 提取目标项目的结构特征和可引用的代码示例，不运行候选工具，也不将 WiFiDemo 上未经对照实验验证的观察写成性能结论。

WiFiDemo 可用于解释：

- Host 共代码与 Device 按芯片编译的结构差异；
- 同一源码函数在不同 Target 中是否实际参与编译；
- 宏开关如何改变 HCC、DPA 和 HMAC TX 路径；
- ops table、Hook 和 function pointer 如何表达运行时芯片差异；
- Host producer、HCC/FRW 传输与 Device consumer 如何形成跨编译单元流程；
- Event 多候选、公共代码归属、同名函数和日志定位为什么要求证据与歧义表达。

引用 WiFiDemo 代码时必须给出仓库路径、文件、符号和行号，并明确它是说明目标工作负载的案例，而不是证明某个候选工具有效的 Benchmark 数据。

### 7.2 本研究不开展实验

以下证据缺口不会在当前论文中临时用小规模实验补齐：

- 缺少宏密集、多 Target 嵌入式 C/C++ 的直接证据；
- 不同项目的第一方数据冲突；
- 关键能力只有案例，没有统计对比；
- Target preprocessing、Hook、Event 或 Host/Device 等问题未被现有 Benchmark 覆盖；
- 候选架构在文献矩阵中无法拉开差异。

遇到这些情况时，正文应将结论写成条件性判断，明确哪些能力尚未被证明，不能用功能列表或架构推演代替实验数据。

### 7.3 后续 Benchmark 研究议程

论文应单列后续需要实验验证的问题，作为下一阶段独立项目的输入。未来 Benchmark 优先以 WiFiDemo 为内部有效性样本，将事实、证据、链路完整性和反事实分别评分，至少包含：

- Target occurrence 与宏条件；
- direct call 与 function pointer/ops；
- Host/Device Event producer-consumer；
- 公共代码与芯片归属；
- 日志到函数、调用链和源码证据；
- 领域标签与真实执行路径的区分。

未来外部有效性验证可筛选 Zephyr、RIOT、Contiki-NG 或其他公开嵌入式项目。论文当前阶段只记录候选数据集及其可能覆盖的结构；正式纳入 Benchmark 前，必须确认其具有研究所需的构建变体、条件编译、函数指针或跨组件结构，不能仅因其属于嵌入式项目而使用。

## 8. 决策方法

代码事实正确性、Target correctness 和证据可追溯性属于硬门槛，而不是能被低成本或高速度抵消的普通加权项。

对其余维度建立显式权重和敏感性分析，但只对有可比公开数据的指标计分。缺少数据的能力标记为 `unknown`，不得擅自换算为零分或根据功能说明填入准确率。若合理范围内调整权重会改变推荐结论，或关键候选存在大量 `unknown`，论文必须报告结论不稳定，并将相关问题列入后续 Benchmark。

最终结论应包含：

- 推荐的知识表示和系统边界；
- 每层必须具备的能力，而非只给出产品名称；
- 可以替换的工具候选；
- 论文、公司实践和开源项目数据分别支撑了什么；
- 仍未被证据解决的风险；
- 在什么条件变化下应重新选型。

## 9. 论文结构

1. 摘要；
2. 研究背景与问题定义；
3. 研究方法、检索协议和证据等级；
4. 目标代码仓工作负载模型；
5. 当前解决方案与实证结果；
6. 候选架构族比较；
7. WiFi MAC 场景适配分析；
8. 证据缺口与后续 Benchmark 研究议程；
9. 决策矩阵、敏感性分析与推荐架构；
10. 有效性威胁与未解决问题；
11. 结论。

摘要在完成证据分析和选型后撰写，不能预先写入结论。

## 10. 完成标准

- 每个核心结论至少有一种允许类型的直接证据；
- 所有关键数字能够追溯到原始来源和实验语境；
- 第一方数据、独立数据和工程判断明确区分；
- 不因近期材料不足而排除仍然有效的经典技术；
- 不因项目知名或功能丰富而把未经验证的能力写成已证明结论；
- WiFiDemo 只用于目标结构与代码案例，不产生本次候选工具性能数据；
- 所有需要实验裁决的问题都进入后续 Benchmark 清单；
- 最终推荐能够明确回答为什么适合 WiFi MAC，而不只是为什么该工具流行。
