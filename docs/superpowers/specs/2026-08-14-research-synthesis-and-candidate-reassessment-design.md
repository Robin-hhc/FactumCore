# WiFi MAC 代码知识架构调研综合与候选重评设计

日期：2026-08-14
状态：待用户复核

## 1. 背景与问题

现有 `research.md` 已分别调查代码导航与检索、语义程序表示与深度分析、代码与领域知识链接、领域知识管理与 Agent 上下文，并建立了证据等级、WiFiDemo 工作负载和后续 Benchmark 清单。这些内容提供了足够的材料，但正文从四条独立调研线直接跳到 L1、L2、L3 三个候选架构族，缺少以下中间论证：

1. 成熟方案共同解决了什么问题；
2. 它们在哪些关键设计选择上不同；
3. 一个完整的代码知识架构通常包含哪些职责；
4. 具体项目只覆盖其中哪些职责；
5. 为什么若干组件能够组成一个候选架构；
6. 为什么某些项目只能作为组件或参考，而不能独立成为完整候选。

旧候选还混合了不同抽象层级：L1 和 L2 主要描述程序事实主干，L3“轻量发现 + 编译器核验”主要描述查询与成本优化方式。三者并非互斥的同级架构族，因此不应继续作为论文的最终分类。

## 2. 重构目标

本次重构不选择最终赢家，而是重新建立从公开证据到实验短名单的完整推导链：

> 独立调研结果 → 共同规律与差异 → 工具无关的职责骨架 → 项目按骨架归类 → 决策轴 → 候选架构生成 → 统一比较 → 待实验裁决问题

重构后，读者应能在接触候选名称前理解整个系统由哪些部分组成，并能逐项解释每个候选用了什么、没有用什么、为什么这样组合、已有证据支持到哪里。

## 3. 不变约束

以下内容是所有候选都必须满足的硬约束，不再用来区分架构族：

- 代码事实绑定 repository、revision、Target、build profile 和 source span；
- 同一源码在不同 Target 中的编译 occurrence 可以分别表达；
- 确定性事实、规则推导、人工断言和模型推断具有不同类型与权限；
- 每个领域断言都具有 provenance、confidence/review、冲突和生命周期状态；
- 源码、构建参数或领域来源变化后，可以检测 stale、invalid 并触发重新验证；
- Agent 获得有预算、有边界、可回到原始证据的上下文，并允许返回 unknown 或 abstain；
- Host/Device 之间通过 Event/Message 等跨边界实体连接，不制造跨二进制 `CALLS`；
- 词法、向量或 LLM 候选不能未经核验升级为确定性程序事实。

这些约束构成后续 Benchmark 的硬门槛。一个项目即使速度快、项目热度高或 Agent 接入方便，也不能抵消 Target correctness 和证据可追溯性的缺失。

## 4. 工具无关的八层职责骨架

论文新增一个工具无关的参考骨架。骨架不预设单图、图数据库、CPG、SQLite、MCP 或具体产品，只定义系统必须承担的职责。

### 4.1 输入与快照

接收 Repository、Revision、Target、Build Profile、编译命令和生成物，形成可复现的分析快照。该层回答“正在分析哪一份代码以及哪一种真实编译视角”。

### 4.2 身份与基础索引

建立 Source Entity 和 Target Occurrence 的稳定身份，提供文件、符号、定义、引用、文本和结构导航。源码实体身份与 Target-specific occurrence 必须区分。

### 4.3 语义分析提供者

按问题提供直接调用、调用候选、CFG、控制依赖、数据流、切片、污点或其他深度程序分析。不同问题可以使用不同分析器，不把“图结构存在”误写成“语义精度已经得到保证”。

### 4.4 领域原始来源

保存规格、设计文档、Issue、日志、测试、历史记录和人工知识。原始来源是引用与复核对象，不能被 Wiki、摘要或模型记忆替代。

### 4.5 版本化来源注册

管理领域来源的原文、版本、位置、时间和许可信息，使领域断言能够指回准确来源，并支持来源更新后的失效分析。

### 4.6 断言与链接层

连接代码事实与领域知识，保存 typed edge、evidence、provenance、confidence、review、conflict 和 lifecycle。代码事实流与领域知识流在该层连接，但不必写进同一个物理数据库。

### 4.7 查询编排与证据装配

根据问题选择基础索引、深度分析或领域来源，合并和限制结果，显式报告截断、歧义、不确定性与证据等级。该层负责将多个提供者转化为稳定的任务级操作。

### 4.8 Agent 交付

通过 MCP、结构化 Context Packet、Wiki、Skill 或 Memory 向 Agent 交付知识。Wiki、Skill 和 Memory 是派生的交付物，不是程序事实或领域事实的权威来源。

### 4.9 横切能力

八层共同受快照一致性、provenance、invalidation、evaluation、license、security 和 observability 约束。

## 5. 按骨架而不是项目名称分类

每个成熟项目使用统一卡片描述：

- 覆盖的骨架层；
- 输入、内部表示和输出；
- 程序事实来自编译器、Parser、规则、模型还是人工；
- 是否绑定 revision、Target 和 source span；
- 向 Agent 暴露的接口与操作粒度；
- 实测数据、样本、基线和指标；
- 第一方、独立或同行评审证据；
- 对 C/C++ 和目标工作负载的直接证据；
- 可直接采用、组件候选、架构参考或排除；
- 已知局限与需要实验的事实。

同一项目可以出现在多层，但必须明确其主要职责，不能因为具有可视化、图存储或 MCP 就被描述为完整架构。

## 6. Agent 结合证据门槛

项目与 Agent 的结合按以下等级记录：

- **A：受控 Agent 证据。** 论文或可复现实验报告最终正确率、Token、工具调用、延迟或成本，并给出样本和对照；
- **B：真实 Agent 工作流。** 官方 MCP、Agent Skill、Coding Agent 集成或公开真实案例，但缺少充分受控对照；
- **C：社区包装或演示。** 可以运行，但成熟度、维护或效果证据有限；
- **D：仅可推测接入。** 只有 API、查询语言或“可以包装”的可能性，没有实际 Agent 使用证据。

进入 Agent 交付与查询编排短名单的项目原则上应达到 A 或 B。编译器、索引器和静态分析引擎等底层事实生产者可以不直接达到 A/B，但必须通过 A/B 级接口或我们定义的有界高层接口服务 Agent。

论文需要强调：MCP 的存在只证明可连接性，不证明工具能提高 Agent 正确率。高质量 Agent 接口还应避免要求模型生成复杂的 Cypher、CPGQL 或分析器内部 DSL，优先提供 `find_references`、`trace_data_flow`、`get_program_slice` 等任务级操作。

## 7. 重新评估后的项目角色

### 7.1 身份与导航

- Serena 作为 Agent 原生 LSP 语义导航的重要候选，正式支持 MCP、C/C++ 和符号级查询；其公开评估属于项目第一方 Agent 自评，需与独立 Benchmark 区分。
- Sourcegraph MCP/SCIP 证明精确代码索引能够直接服务 Coding Agent；SCIP 的开放表示值得研究，Sourcegraph 整体产品的开放性和部署边界单独评估。
- grep、BM25、RepoMap 和向量检索保留为基础召回或对照，不承担 Target-specific 程序事实。

### 7.2 轻量结构发现

- Codebase-Memory 的论文报告 31 个真实仓库上 83% answer quality，对照逐文件 Agent 为 92%，同时约减少 10 倍 Token 和 2.1 倍工具调用。该数字支持其进入成本与导航实验，不证明 Target、宏或调用边准确性。
- CodeGraph 等本地结构图项目可作为增量索引、Context Packet、proof label 和 Agent 生命周期设计参考；第一方指标不得写成跨项目普遍结论。
- Tree-sitter 图只作为发现或加速层，不能未经编译器或深分析核验成为代码事实主干。

### 7.3 深度程序分析

- Joern/CPG 不再因缺少 Agent 接入而降为纯后台工具。2026 年 codebadger 已通过 MCP 将 Joern 的切片、污点、数据依赖和语义导航暴露给 Agent，并给出 GGML、libtiff 和 libxml2 三个真实案例。
- codebadger 的案例能够证明可行性和任务价值，但不是大规模受控对照，也没有直接证明 WiFiDemo Target correctness；因此它提高 CPG 路线的 Agent 成熟度，不直接决定最终选型。
- QLCoder/CodeQL 等研究证明 Agent、LSP 反馈和静态分析查询可以有效组合，但其实验任务、语言与许可边界使 CodeQL 更适合作为参考或实验 oracle，而非默认开放核心。

### 7.4 代码与领域知识

- Graphify 与 Understand Anything 已实际通过 Skill、MCP 或多 Agent 工作流关联代码、文档和领域解释，证明“代码结构 + 领域视图 + Agent 交付”是活跃方案方向。
- 它们公开材料尚未证明多 Target 编译 occurrence、领域置信度校准和完整失效传播，因此不作为程序事实主干。
- 值得吸收的内容包括结构提取与模型解释分离、EXTRACTED/INFERRED 标识、领域流程视图、渐进式 Agent 交付和可视化；这些设计必须放入独立断言层并强化 provenance 与生命周期。

## 8. 真正的架构决策轴

项目分类完成后，论文只使用能够改变系统边界的决策轴生成候选：

1. **程序事实主干：** 联邦编译器/语义服务，或物化的 Target-specific CPG；
2. **查询拓扑：** 直接查询事实主干，或增加轻量发现加速层；
3. **分析时机：** 预先物化、查询时按需计算，或二者组合；
4. **断言层物理组织：** 与代码事实逻辑分离，允许同库不同 schema 或独立存储，但不得混淆 provenance 和生命周期。

词法、向量、RepoMap、Tree-sitter 图、Wiki、Skill 和 Memory 是可附加能力，不再作为与程序事实主干同级的架构族。

## 9. 两个核心架构族

### 9.1 A：Agent 原生的联邦语义服务骨架

数据流：

```text
Target/编译快照
  → Clang/clangd/SCIP 身份与导航
  → Serena 式高层 Agent 接口
  → 按需深分析提供者
  → 独立领域断言层
  → 查询编排与 MCP Context Packet
```

优势：

- Agent 语义导航已有较成熟的实际项目；
- 分析器可替换，适合开源组合；
- 可以按任务逐步增加分析深度；
- 不要求把所有关系复制进一个统一图。

风险：

- 多提供者之间需要统一 stable ID 和 Target occurrence；
- 深度分析结果的 schema、缓存和生命周期需要自建；
- 默认没有一套统一的跨 AST、CFG、IR 和领域断言查询模型；
- 编排层的工程量可能较高。

### 9.2 B：Target-specific CPG 主骨架

数据流：

```text
每个 Target 的编译快照
  → 独立 Joern/Fraunhofer CPG
  → codebadger 式高层 Agent 分析工具
  → 独立领域断言层
  → 查询编排与 MCP Context Packet
```

优势：

- AST、CFG、调用和数据流共享可遍历表示；
- 复杂跨函数分析、切片和污点任务更自然；
- codebadger 提供了 CPG 与 Agent 结合的近期直接证据；
- 可将常用复杂查询封装成稳定高层工具。

风险：

- C/C++ frontend 对真实 compdb、宏、函数指针和共享源码 occurrence 的行为仍待验证；
- 索引、存储、增量和多 Target 隔离成本可能较高；
- codebadger 等 Agent 包装仍较新，公开受控 Benchmark 不足；
- 组件许可证和再分发路径需要单独审计。

## 10. 两种查询部署模式

每个核心架构族都可以使用以下模式：

- **0：直接模式。** Agent 通过有界高层工具直接查询程序事实主干和断言层；
- **1：轻量发现加速模式。** Agent 先用 Tree-sitter 图、Codebase-Memory/CodeGraph 或其他低成本索引寻找候选，再回到程序事实主干或源码核验。

因此后续实验对象为 A0、A1、B0、B1 四个部署变体，但论文应明确它们只包含两个核心架构族。加速层是否值得存在由 Token、工具调用、延迟、错误候选率、核验成本和一致性成本共同裁决。

## 11. 代码与领域知识的共同链接模型

所有候选共享同一链接模型，避免用领域层差异掩盖程序事实主干差异。断言按权限分为：

- `EXTRACTED`：源码、配置或领域来源直接明示；
- `RULE_DERIVED`：由有版本的确定性规则推导；
- `INFERRED_CANDIDATE`：由 LLM、embedding 或启发式产生，只能作为候选；
- `CURATED`：经过人工复核的领域断言。

每条断言至少携带：subject/object stable ID、repository/revision/Target 范围、predicate、source citation、source span、producer、method/version、confidence、review state、created/validated time、lifecycle state 和 invalidation reason。

Agent 可以读取所有允许状态并提出 `INFERRED_CANDIDATE`，但不能把候选直接升级为确定性事实。源码重命名、Target 变化、编译命令变化或领域来源更新时，系统按依赖关系将相关断言标记为 stale，重新验证后才能恢复有效状态。

## 12. 论文重构顺序

`research.md` 重构为以下论证顺序：

1. 摘要；
2. 研究问题、方法、时间窗口与证据等级；
3. WiFiDemo 工作负载；
4. 四条调研主线的独立结果；
5. 从成熟方案学到的共同规律；
6. 成熟方案的关键差异；
7. 八层工具无关参考骨架；
8. 按骨架分类项目与 Agent 结合证据；
9. 代码与领域知识链接模型；
10. 真正的架构决策轴；
11. 两个核心架构族与四个部署变体；
12. 统一优缺点和 WiFiDemo 工作负载覆盖矩阵；
13. 排除项、组件候选与架构参考；
14. 后续 Benchmark；
15. 有效性威胁与阶段性结论。

旧第 4 至第 7 节的调查材料尽量保留，但增加综合章节作为候选推导的桥梁。旧 L1/L2/L3 表格和基于该表的结论删除或重写，不为保持旧结论而扭曲新分类。

## 13. 统一比较与表述规则

每个候选使用相同模板：

- 架构图与端到端数据流；
- 八层骨架中的组件映射；
- Agent 可调用的高层操作；
- 对 WiFiDemo W01-W08 的覆盖；
- 已有证据支持的能力；
- 结构上可满足但尚未验证的能力；
- 明确缺失或不适用的能力；
- 性能、资源、许可证和维护风险；
- 最适合的任务与不适合的任务；
- 后续 Benchmark 的可证伪条件。

能力状态只允许写成：

- `supported by evidence`：有直接公开证据；
- `architecturally accommodated`：设计能够容纳，但未被实验验证；
- `unknown / benchmark required`：当前证据不足；
- `not satisfied`：与硬约束冲突或缺少必要机制。

不得把项目 README 的功能列表等同于效果证明，也不得用架构推演替代 WiFiDemo 实验。

## 14. 保留与修改边界

- 保留 `目标代码仓注意事项.md` 的历史原文，不把本次结论回写成原始设计意图；
- 保留现有 evidence ledger、source audit、tool matrix 和 benchmark backlog，按新分类补充或修正交叉引用；
- 不开展 WiFiDemo 工具实验，不产生新的本地性能数字；
- 可以引用 WiFiDemo 源码说明工作负载，但必须继续给出路径、符号和行号；
- 新增来源只允许论文、AI 公司官方文章、开源项目官方材料；
- 近期项目优先使用近期材料，经典程序分析项目允许使用仍然有效的旧论文与官方资料；
- 第一方数字、同行评审结果和架构推断必须分别标注。

## 15. 完成标准

正文重构完成后必须满足：

1. 候选出现前已经解释共同规律、差异和八层骨架；
2. 每个项目都能定位到一个或多个骨架层，不再按项目热度平铺；
3. Agent 结合证据具有 A-D 分级，MCP 不被当作效果证明；
4. 旧 L1/L2/L3 被两个核心架构族和两种部署模式取代；
5. A0、A1、B0、B1 使用同一模板和工作负载矩阵比较；
6. Graphify、Understand Anything 等项目的领域设计被吸收，但不被误写为 Target-specific 程序事实核心；
7. codebadger 等近期证据改变 Joern/CPG 的 Agent 成熟度判断，但不会绕过 Target correctness 实验；
8. 代码与领域知识如何双向链接、核验、失效和重验证有完整说明；
9. 所有数字保留样本、基线、指标、证据性质和局限；
10. 结论只缩小到待实验短名单，不宣布未经 Benchmark 证明的唯一赢家；
11. `git diff --check`、链接检查和文档一致性检查通过；
12. 原始注意事项文件继续保留并纳入提交。

## 16. 预期阶段性结论

重构后的论文预期只得出以下强度的结论：

- 成熟 Agent 代码知识系统普遍采用确定性结构或语义工具、渐进检索、高层工具接口和受限上下文，而不是让模型无约束读取全仓或直接操纵底层查询语言；
- 对多 Target WiFi MAC C 项目，Target-specific 编译事实、来源定位和断言生命周期是所有方案的共同硬门槛；
- 当前公开证据足以将完整候选缩小为联邦语义服务和 Target-specific CPG 两种主骨架，并分别评估是否增加轻量发现层；
- 代码与领域知识应通过独立、带证据和生命周期的断言层连接；混合图项目可提供设计参考，但尚不能替代编译事实主干；
- 当前证据仍不足以在 A0、A1、B0、B1 中确定唯一赢家，最终选择必须由后续 Benchmark 裁决；若效果接近，再以开源、离线、开放格式和可维护性作为 tie-break。
