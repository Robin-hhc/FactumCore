# 面向 Agent 的代码知识图谱策略调研重构设计

日期：2026-08-25

## 1. 背景与问题

当前论文按“代码导航与检索、语义程序表示与深度程序分析、代码与领域知识链接、领域知识/Wiki/Skill/memory”四条研究线展开，随后推导八层职责、A/B 骨架和 A0/A1/B0/B1。该结构混合了三种抽象层次：完整产品、产品内部事实引擎、通用 Agent 基础设施。结果是同一个产品被拆散分析，CodeGraph 与 Joern 看起来像不同问题，Graphify 与 Understand Anything 的跨类别能力也不容易理解。

本轮不再设计我们的实现架构，也不预选数据库、CPG 或工具组合。研究只回答：成熟方案使用什么策略建立知识，以及这些知识怎样帮助 Agent 完成两种双向问答。

## 2. 两种核心问答

### 2.1 模糊自然语言到具体代码

研究完整过程：

```text
模糊自然语言问题
→ 领域术语或代码概念转换
→ 候选文件/符号召回
→ 调用、引用、数据或依赖关系扩展
→ 当前代码中的文件、符号、行号和片段证据
```

重点不是某个查询 DSL 的细节，而是方案怎样缩小搜索空间、连接自然语言与代码身份、扩展相关关系、控制候选噪声，并让 Agent 回到源码核验。

### 2.2 具体代码到流程与领域知识

研究反向过程：

```text
具体代码片段或符号
→ 调用、控制、数据、事件或依赖关系扩展
→ 模块/社区/流程边界识别
→ 流程步骤、架构概念或领域说明
→ 可复用且能返回代码证据的文档知识
```

重点是高层知识来自确定性抽取、规则、图聚类、LLM 综合还是人工维护，以及生成结果能否追溯、更新和纠错。

## 3. 分类前的证据论证

论文必须在“两种核心问答”之后、三个类别分析之前增加独立论证，不把分类写成作者主观设定。

该论证综合三类一手证据：

1. **代码检索与 Agent 上下文研究**：Agent Retrieval Bench、CORE-Bench 和 ContextBench 表明，词法、embedding、RepoMap 与 Agent 轨迹各有不同优势，单一检索器不能稳定完成候选召回、上下文利用和错误拒答；最终仍需当前代码证据。
2. **代码图与程序分析项目**：CodeGraph、Joern、codebadger、CodeQL/QLCoder 等表明，结构关系和更深的调用/控制/数据关系能够减少文件扫描或支持更深查询，但这些代码事实本身不解释业务与领域含义。
3. **代码—文档与 Wiki 项目**：Graphify、Understand Anything、RepoDoc、LLM-Wiki/WiCER 等表明，成熟方案会索引原始文档或从代码图生成模块、流程、领域和 Wiki 资产；生成知识必须保留来源、代码锚点和更新路径，否则只是不可核验摘要。

由上述证据推出“2+1”能力模型：

- **代码知识**负责定位、结构扩展和程序行为证据；
- **文档与领域知识**负责术语解释、背景、流程叙事和跨文件综合；
- **代码—文档链接**负责两类知识之间的双向导航、证据落地和更新一致性。

Agent 查询编排是检验三项能力能否共同工作的观察视角，不另立为第四类知识。Target、版本、provenance、增量成本和不确定性保留为比较字段或 Benchmark 条件，不再组成八层架构。

## 4. 三个分析类别

### 4.1 代码知识建立策略

代码知识是一个大类，内部按事实深度比较，不再拆成互不相干的研究主线。

#### 4.1.1 轻量结构索引

代表包括 CodeGraph、Codebase-Memory、GitNexus，以及作为辅助导航设施的 SCIP/Serena。分析源码如何经 AST、符号、引用、调用、imports、框架规则和全文索引形成轻量图；重点比较索引速度、增量更新、自然语言入口、图扩展、源码片段返回和公开 Agent 效果。

#### 4.1.2 深度程序分析图

代表包括 Joern、codebadger、CodeQL/QLCoder、Fraunhofer CPG，以及必要的专门分析对照。分析 AST/CFG/call/dataflow/slice/taint 等事实怎样服务同一套 Agent 导航任务，以及更深事实相对轻量索引增加了什么问题能力、资源成本和语言/构建依赖。

codebadger 和 QLCoder 作为 Agent 使用深度引擎的策略分析，不被描述成独立的底层建图类别。

### 4.2 文档与领域知识建立策略

内部区分：

1. 索引已有 README、ADR/RFC、设计说明、协议规范及其他原始资料；
2. 由代码图、社区聚类、规则或 LLM 生成模块、架构、流程和领域文档；
3. 由 LLM-Wiki/WiCER 类方法把多文档编译为可检索 Wiki。

Graphify、Understand Anything、RepoDoc 和 GitNexus 的 process/community 能力可在本节再次出现。LLM-Wiki/WiCER 作为文档管理和知识编译策略保留，但明确它们不能独立替代代码定位与程序分析。

### 4.3 代码—文档链接策略

分别比较：

- 文档显式引用代码实体；
- 由调用、数据、依赖或聚类关系派生流程步骤；
- 由目录、宏、命名、事件注册等规则建立领域链接；
- 由 LLM 生成候选领域映射；
- 文档 claim/source/citation 与代码文件、符号、行号、revision/Target 的证据链接；
- 代码变化后的链接重算、失效和人工纠正。

链接必须支持两种方向：领域/流程知识返回代码证据，以及代码实体反查所属流程、文档和领域解释。

## 5. 项目允许跨类别重复出现

分类对象是能力和策略，不是互斥产品桶。每个项目可以在多个章节出现，但每次只分析该类别对应的能力：

| 项目 | 代码知识 | 文档/领域知识 | 代码—文档链接 |
|---|---|---|---|
| CodeGraph | 重点：轻量结构索引与 Agent 定位 | 无核心文档生成能力 | 仅代码内部结构关系 |
| Joern | 重点：CPG、调用/控制/数据查询 | 无核心文档管理能力 | 可作为生成链接的代码证据源 |
| codebadger | 重点：把 Joern 高层能力交给 Agent | 无核心文档管理能力 | 分析结果可支撑流程步骤 |
| Graphify | 代码结构图、路径和社区 | 文档/PDF/报告/Wiki | 代码、文档、引用及 EXTRACTED/INFERRED 边 |
| Understand Anything | 确定性结构图 | 摘要、architecture/domain/flow/step | 结构与 LLM 生成知识分层连接 |
| RepoDoc | RepoKG | 模块化交叉引用文档 | 图聚类和代码实体支撑文档生成 |
| LLM-Wiki/WiCER | 不提供代码知识 | 重点：多文档编译、评估与修正 | 需与外部代码图组合后才有代码链接 |

最终矩阵必须允许同一项目在多个类别获得独立、有证据约束的描述，不能用一个总标签掩盖其跨类别能力。

## 6. 统一项目分析卡片

每个项目或论文统一回答：

1. 输入哪些代码、构建信息、文档或历史资料；
2. 生成什么图、索引、数据库、报告或 Wiki；
3. 自然语言问题怎样收敛到代码候选和最终源码片段；
4. 从代码锚点怎样扩展并形成模块、流程或领域说明；
5. 高层知识是抽取、规则、聚类、模型推断还是人工维护；
6. 代码和文档通过什么实体、边、citation 或路径连接；
7. 代码或文档变化后如何增量更新、失效和纠错；
8. Agent 通过 MCP、CLI、Skill 或其他接口怎样使用，但接口本身不算知识能力；
9. 有哪些论文、官方材料、公开数据和适用限制；
10. 对 C/WiFi MAC 两种问答有什么已证明能力、合理推断和 unknown。

## 7. Skill 与 memory 的范围

通用 Skill 是工具选择、步骤编排和按需上下文加载机制；通用 memory 是历史观察或经验存储。二者没有稳定代码实体、可扩展关系和代码—文档链接时，不属于本轮知识图谱方案。

因此删除原论文中独立的 Skill/memory 方案分析。只有当具体项目用 Skill 暴露图查询，或将 memory 明确链接到代码/文档节点时，才在该项目 Agent 接口或辅助输入中说明，不单独设章、排名或候选。

## 8. 新论文结构

1. 研究问题：两种双向问答；
2. 证据论证：为什么成熟知识图谱需要代码知识、文档/领域知识和代码—文档链接；
3. 代码知识建立策略；
4. 文档与领域知识建立策略；
5. 代码—文档链接策略；
6. 跨类别项目能力矩阵；
7. 逐项目的两条 Agent 使用过程比较；
8. 对 WiFi MAC 的适用性、明显缺口和当前可排除项；
9. 后续 Benchmark 与有效性威胁；
10. 结论。

正文不再以八层职责、A/B 骨架或 A0/A1/B0/B1 为结论主线。历史设计规格和执行计划保留为过程档案，不回写成当前结论。

## 10. 验收标准

1. 第一章清楚定义两种问答，不再先讲工具层或数据库层；
2. 两种问答与三类分析之间存在独立、来源可追踪的证据论证；
3. 三个类别分别回答知识如何建立、怎样被 Agent 使用、怎样更新；
4. CodeGraph 与 Joern 在同一“代码知识”大类中比较事实深度；
5. Graphify、Understand Anything、RepoDoc 等跨类别项目在相关章节重复出现；
6. LLM-Wiki/WiCER 作为文档知识策略保留，通用 Skill/memory 不再单列；
7. 每个重点项目都描述“自然语言到代码”和“代码到流程/领域”的实际过程；
8. 现行论文、方案档案和矩阵不再以八层、A/B 或 A0/A1/B0/B1 组织；
9. 效果数字紧邻样本、对照、指标、来源性质和限制；
10. 未运行 WiFiDemo 候选实验时仍保持 `unknown / benchmark required`，不提前宣布赢家。
