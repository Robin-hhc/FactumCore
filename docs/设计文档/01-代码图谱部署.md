> **状态**：v0.2，已同步 2026-09 评测结果（《codegraph_vs_grep_评测报告.md》）；待细化项见文末。
> **关联**：00-总架构设计 §4.1（选型概要）；config.yml 映射初稿属本说明书配套；评测原始数据在 评测集/ 目录。

## 1. 工具选型结论

- **首选部署**：CodeGraph（tree-sitter AST → 符号/调用图 → SQLite+FTS5，CLI/MCP 双接口，本项目查询用 CLI `-p` 指定代码仓索引，文件监听增量）；codebase-memory-mcp 为等价备选；
- **选型策略（2026-09-20 调整）**：两个代码图谱工具功能等价、可随时替换安装部署，**不再做完整工具比选**；先按 CodeGraph 能力部署，后续如不满足需求换装等价工具即可；
- **Graphify 仅作对照基线**，验证"B 类在复杂业务 + 多仓 + C 语言上效果不佳"，不承担主链路；
- 部署细节按 CodeGraph 能力写（tree-sitter AST → 符号/调用图 → SQLite+FTS5，MCP 暴露查询工具，文件监听增量）；若换工具，替换为等价机制，架构不变。

### 1.1 评测验证（2026-09，HWDL 收发详细设计场景）

> 评测设计：8 题（Q1~Q8）每题并行启动 2 个全新子 agent（零记忆零上下文、互不通信、禁读评测 md），grep-only（纯文本检索）vs toolbox（Grep+Read+Bash+codegraph 可选）两路对照；Q8 端到端大题按设计文档第五章 15 修改点（有效 14 节点，节点 1 CLAT 跳过）逐节点判分。

**最终数据（8 题 16 路）**：

| 题目 | grep-only | toolbox | 用时差（toolbox 相对） |
|------|-----------|---------|------------------------|
| Q1~Q5（分题） | 全对 | 全对 | -13.1% ~ +16.1%，无一致方向 |
| Q6 | 全对 | 全对 | +42.8%（慢因见下，非工具因素） |
| Q7 | 全对 | 全对 | — |
| **Q8（端到端大题）** | **6/14** | **12.5/14** | +32.8%（grep-only 更快） |
| **合计** | **20/28** | **26.5/28** | +18.2%（toolbox 慢） |

**结论：codegraph 可用但非必需。**

- **分题（Q1~Q7）两路一致**：7 题 14 路全部满分，工具路线差异不体现——单点符号定位、调用查询等基础能力 grep/Read 同样覆盖；
- **端到端大题（Q8）拉开差距**：差距来自 grep-only 在"TX 阶段 1 偏移 ×4"与"RX 帧体还原"全漏（6/14 vs 12.5/14），本质是**函数体精读深度与帧体偏移全局意识**差异，非工具链能力差异；toolbox 唯一丢分项（device 通路 `mac_get_data_type_inner` 变体未点名，0.5）与索引能力无关；
- **Q6 慢归因澄清**：toolbox +42.8% 慢的实测大头是 794s 并行大调用（Agent 子任务 + 全仓 grep），因果链为 codegraph 如实返回 mp17c 路径 → agent 先入为主误判异常 → bash grep 正则转义失效加剧不信任 → 派子任务+全仓 grep；**是 agent 检索策略问题，不是 codegraph 索引配置问题**；
- 支持 2026-09-20 的"评测降级为按需验收"调整：不再做完整工具比选，CodeGraph 按能力部署，后续按需验收即可。

### 1.2 评测方法论启示（指导后续验收设计）

- **分题判别力弱，端到端题判别力强**：Q1~Q7 单点查询题两路全对、无法区分工具路线；只有 Q8 这类"完整通路 + 逐节点严格判分"的题才拉开差距 → 后续按需验收应**出端到端大题、按修改点逐节点判分**，不要依赖分题型；
- **prompt 约束有效**：v6 重测修正（禁 Bash grep -rn 全目录扫、mp1x 多芯片共仓提示、禁读评测 md）显著改善行为——评测/验收 prompt 需显式声明工具边界与仓结构，减少 agent 策略漂移；
- **Q4 输出循环教训**：grep-only 路出现过 101 次调用循环，说明纯文本检索路线的 agent 更容易陷入重复检索；索引查询（毫秒级精确命中）天然收敛，是稳定性的隐性收益；
- **多芯片共仓（mp1x 下 mp17c/mp1x 两子目录）是 agent 的常见误判源**：codegraph 返回全量信息（含 mp17c 路径）是正确行为，agent 需结合 config.yml 仓映射做范围判断，文档侧应显式提示"多芯片共仓，先确认目标芯片目录"。

## 2. 索引部署

1. **codebase 镜像挂载**：codebase/ 是 `ut_agent/main` 的镜像（build/device/drivers/host 等真实结构并列），初期只纳入三个代码仓源码（device 侧 `device/wifi/mp1x`、`device/wifi/mp12`，host 侧 `drivers/wifi`），经 config.yml `repos` 登记代码仓路径与索引路径；`alg`、`features`、`mp12c` 等其它仓按需增补；
2. **代码仓内建索引**：按 wifi-codegraph skill 的索引位置规则——device 侧每个代码仓一个索引（`main/device/wifi/<project>/.codegraph/`，mp1x / mp12 / alg / features…各建一个），host 侧固定一个索引（`main/drivers/wifi/.codegraph/`，覆盖全部 host 代码）；固定基准 revision 全仓索引；符号表计数、hybrid 查询（语义 + 精确）口径按 C1 参照；
3. **增量同步**：文件监听自动增量（防抖）；代码 merge 触发 git diff → 定位受影响符号/锚点 → 增量重索引 + 锚点校验（见 04-消费与问答 §4）；
4. **跨仓查询**：host（drivers/wifi）↔device（device/wifi/mp1x|mp12）调用链能否串起来是验收点（config.yml 记录仓间映射）；单仓查询用"实体页名 = 仓名"限定范围，避免跨仓误匹配。

## 3. C 语言断链专项（本项目核心难点）

C 驱动的已知断链点及对策：

| 断链点 | 现象 | 对策 |
|--------|------|------|
| **函数指针 / ops 表**（如 hmac_ops） | 直接 caller = 0，callers/impact 给不出间接调用链 | 落地期验证两工具差异；对 ops 表分发点建 concept-flow 卡（`concept-flow-ops-dispatch`），记录表结构、注册点、分发语义，由文档侧补代码图断链 |
| **宏** | 宏展开后符号不可见 | 树外维护宏→函数/常量的映射表（concept-rule 卡），消费时走语义→符号映射通道 |
| **隐式/间接调用**（中断、回调、硬件触发） | 静态图不可见 | 用轨迹 Runbook 与通路概念卡显式编译"谁在什么时机被调"，代码图管静态事实、文档图管动态语义 |

> 原则：代码图保证静态事实 100% 准确；**动态跳转、设计意图由文档图谱补**，两侧消费时互证，不强行让代码图做它做不到的推断。

## 4. 查询接口

- 查询**一律用 `codegraph` CLI 的 `-p <索引路径>`** 指定代码仓索引（host 固定一个、device 每仓一个），如 `codegraph query -p codebase/drivers/wifi <symbol>`、`codegraph callees / impact -p codebase/device/wifi/mp1x <symbol>`；MCP server 的 workspace root 指向 codebase 根无索引、无法指定子目录，故不用 MCP；
- 调用约定：`实体页名=仓名` 限定范围 → 符号表精确查询（区分同名、返回 file:line + 签名 + 调用边）→ 需要时沿 callers/callees 遍历；
- 与 grep（K0 基线）区分：符号查询走索引查找（毫秒级），grep 仅作工具增益对照下限。
