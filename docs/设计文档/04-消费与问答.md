## 1. Query 五步法

1. **明确问题目标与决策对象**——确定要回答的实体与支持的工程决策，不混多目标；
2. **限定边界**——domain（wifi-mac）/ technology / platform（chip2|chip8）/ 生命周期；
3. **高密度信息精准检索**——实体名/API 名/错误码/日志短语/关键约束；精确匹配用 literal、描述性用 text；最窄范围；
4. **深读正文与来源**——按 local_path 打开卡，核对适用条件/失效边界/验证方法；需要更强证据时打开 sources 固定来源，**不凭摘要下结论**；
5. **形成可验证结论**——结论 + 适用范围 + 依据 + 潜在冲突/缺口 + 仍需编译/测试/真机验证的部分；先判定问题属**已覆盖 / 冲突 / 证据不足 / 缺口**（零命中 ≠ 否定性技术证据，缺口登记为摄入线索，不擅自扩大芯片/版本范围，对齐 00-总架构设计 §3.5F）。

## 2. 渐进式披露（对应 w4 P0–P3）

```
P0 index.md/检索索引（查询第一步：先读 index 或走检索定位候选）→ 候选摘要 + Frontmatter ──筛选──▶ P1 命中卡正文 ──需要证据──▶ P2 sources 原始来源
P3 沿 related 关系探索相关卡（不进检索语料，只做导航）
```

> 查询总是**先经过 index.md 或检索索引定位候选页，再钻取正文**——这是"编译一次、按需展开"而不是"每次从原始材料重新拼凑"的关键，也是避免引入 embedding RAG 基础设施的原因（index 在 ~100 源/数百页规模下足够）。

## 3. 双轨问答（C9 编排）

- **wiki Agent 答 Why**：业务背景、设计决策、流程语义（查知识文档图谱）；
- **代码 Agent 答 How**：接口、调用链、代码实际（查代码事实图谱）；
- **主 Agent 交叉印证**：两侧冲突如实报告，代码侧是对账基准（文档标注可能过时，代码图结果优先）。

## 4. wiki → 代码链接四通道

| 通道 | 机制 | 落地 |
|------|------|------|
| **符号精确解析** | 文档写函数名 → 消费时走代码图符号表查询（非 grep） | `实体页名=仓名` 限定仓库，`[hmac_tx_process](codebase/drivers/wifi/hmac/tx/hmac_tx.c:234)` 锚点 |
| **语义→符号映射** | 业务术语 ↔ 代码包/符号映射表沉淀在文档（"特殊帧"→具体函数名） | concept-rule 卡 + config.yml 维护映射 |
| **确定性调用图遍历** | 文档给入口符号 + 意图，代码图沿 callers/callees/impact 自动串上下游 | 消费链上发生，不逐函数标注 |
| **双 Agent 对账** | wiki 答 Why / 代码答 How / 主 Agent 互证 | 见 §3 |

**锚点校验门禁**：代码 merge 触发 git diff → 校验文档声称的符号在源码真实存在（`[函数名](路径:行号)` 抽检）→ 失效即定位并重跑受影响子域（实测可省 50–80% 重跑量）。

## 5. Search Receipt（复杂任务检索留痕）

每项决策保存不可覆盖的检索记录：查询请求、目标范围、索引来源、知识卡路径及相关指纹 → 形成固定检索状态（retrieval state）→ 决策有据后过 **ready** 校验、可重放核验 → 工程验证完成后用 **outcome** 关联实际结果与产物指纹。形成"问题与决策 → 知识检索 → 决策依据 → 工程验证"完整链路，支持追溯、重放与审计。

> **回填走统一摄入入口（对齐 00-总架构设计 §3.5D）**：消费侧只提出新增 / 纠错 / 补证**建议**，实际回填走统一摄入与修订入口（ingest，含查重、候选修订与治理），通过后再成为共享知识；待审修订不提前覆盖已发布正文，原始问答与模型判断不因回填而升级为证据。

## 6. wiki 内检索机制与输出形式

**检索机制（两级）**：
- **一级：index.md**——规模小（~100 源/数百页）时 index 足够，查询先读 index 定位候选（见 §2）；零额外基础设施；
- **二级：本地搜索**——规模增长后引入 markdown 本地搜索引擎（如 **qmd**：hybrid BM25/向量 + LLM 重排、全本地、提供 CLI + MCP 两种调用方式），或自建 naive 搜索脚本。搜索只作用于 wiki 页内，与代码图符号查询（01-代码图谱部署 §4）是两套索引，互不替代。

**输出形式**：Query 的答案按问题类型落成不同产物并回填到对应 concept/entity 卡（起步无 outputs/ 目录，集中沉淀需要时再引入）形成复利——
- markdown 页（综合/分析）、对比表（ring 方案、desc 队列策略横向对比）、时序图/流程图（通路时序，对接绘图技能）、幻灯片（分享/评审材料）；
- 判断标准：一次性问答留在会话里，**可复用的综合、对比、连接发现必须回填 wiki**（否则消失在聊天历史中）；
- 回填走统一摄入与修订入口（见 §5 对齐 00-总架构设计 §3.5D）：先查重、读旧卡再决定新建或融合，待审修订不提前覆盖已发布正文。
