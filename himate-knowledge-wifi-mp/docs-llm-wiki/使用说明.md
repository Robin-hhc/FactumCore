# HiMate 使用说明

以下操作以 `himate-knowledge-wifi-mp/`、`AGENTS.md.example` 和 `config.yml` 已放入真实代码仓为前提，后两个文件位于仓根；配套 Skill／Workflow 按宿主既有方式安装，实际是否可调用、是否已加载须在宿主核对。接入时保留业务仓已有的 `AGENTS.md`，仅合并示例中的 `main/`、`config.yml`、知识根及设计文档四项说明和 `hs-knowledge-explore` 入口指针，不覆盖原有业务内容。没有 `AGENTS.md` 时才将示例改名为该文件，并按真实业务仓补全；未知部分保留大纲与 `...`。本开发仓的根 `AGENTS.md` 仅本地维护，分发文件为 `AGENTS.md.example`。下文 `K` 指实际 `config.yml` 解析出的知识根，允许安全嵌套。

使用顺序：**配置连接信息 → 按需首次准备 → 按任务选择 ingest、lint 或 query**。知识库统一入口为已安装的 `hs-knowledge-explore`；入库通过 OpenFlow 执行 Workflow，独立检查和查询通过 Agent 调用对应 Skill。已有知识可直接查询；手动或周期检查代码引用变化时，另行启动只读 lint 巡检 Workflow。

<a id="配置项目代码架构"></a>

## 1. 两个配置文件

| 文件 | 位置与用途 |
|---|---|
| `config.env` | 位于 Agent 已安装的 `hs-knowledge-explore/` 内，保存本机 SSH 连接配置和服务器代码仓位置，由 Windows 用户配置，不上库。 |
| `config.yml` | 位于实际代码仓根目录，由项目维护者手工维护并上库，使用者沿用仓内配置。 |

Windows 用户先找到已安装的 `hs-knowledge-explore/` 文件夹，将其中的 `config.env.example` 复制为同目录的 `config.env`，再按模板注释填写：

| 配置项 | 填写内容 |
|---|---|
| `EXECUTION_MODE` | 代码仓在服务器上时填写 `ssh`。 |
| `REMOTE_PROJECT_ROOT` | 服务器上的实际代码仓根路径，该目录应包含业务仓 `AGENTS.md` 和 `config.yml`；填写服务器原生路径。 |
| `SSH_HOST`、`SSH_USER`、`SSH_PORT` | 服务器地址或已有 SSH 别名、登录账号和端口；账号可沿用已有 SSH 设置，默认端口为 `22`。 |
| `SSH_IDENTITY_FILE` | Windows 本机已有私钥文件的路径；已有认证可沿用时可留空。 |
| `PYTHON` | 服务器现有全局 Python 的命令或路径。 |

`config.env` 位于 Agent 的能力目录，不放到代码仓中。代码仓与 Agent 在同一台机器时，将 `EXECUTION_MODE` 设为 `local`，由 Agent 在当前代码仓执行，无需填写 SSH 参数。

<a id="首次准备运行依赖"></a>

## 2. 首次环境安装

真实根 `AGENTS.md` 已按业务仓维护、配置完成且首次需要准备环境时，发给 Agent：

```text
请使用 hs-knowledge-explore 完成当前知识库的首次环境准备。
读取本 Skill 的 config.env（存在时），按配置进入项目；同机时使用当前代码仓。
读取项目根 AGENTS.md、config.yml 和知识根入口，
在项目所在机器使用已有全局 Python 运行本 Skill 的 setup.py，按需安装缺失依赖。
再按 config.yml 的 code_root 和 modules，使用执行端已有的 CodeGraph 逐仓初始化，已有可用索引直接复用。
最后报告项目位置、依赖结果和逐仓初始化结果；遇到缺项时说明具体原因。
```

setup 只检查依赖和项目配置，不自动复制、改名或合并示例；只读发现读取真实根及领域 `AGENTS.md`，不会以 `.example` 代替。此后按 explore 指引直接使用下面三个日常任务；新会话找不到项目时才调用只读发现，不需要重复安装。

升级前，先按原配套工具和规则恢复旧版未完成事务；再安装完整九包及匹配规则，移除已迁移的旧包，保留历史工件原字节。source-scan 的旧 `prepare` 已退役，改用 source-prepare；change-plan 的旧字节请求及 `verify/rederive` 不再生产或复验写入清单，字节输入交 view-materialize，内容审阅交 lint。这些入口不会自动转发兄弟 CLI。

CodeGraph 初始化由 Agent 按 explore 指引执行，不在 `setup.py` 内。Agent 只处理 `config.yml` 已配置的真实代码仓，空 `modules` 列表不扫描或初始化整个 `main/`；跨机器时通过既有 harness SSH 在源码所在端执行。执行端缺少 CodeGraph CLI 时报告缺项。CodeGraph MCP 由宿主／harness 提供，是否可用按实际接入核对；setup 不安装 CodeGraph 或配置 MCP。

## 3. 日常使用

| 任务 | 类型与使用方式 | 适用情况 |
|---|---|---|
| `ingest` | Workflow：通过 OpenFlow 运行 `hs-knowledge-ingest`。 | 原件入库、增量更新、已有知识修订或中断续办。 |
| `lint` | Skill：向 Agent 提出检查要求，指定 `hs-knowledge-lint`。 | 独立只读检查正式库或明确候选，获得实际问题报告。 |
| `query` | Skill：向 Agent 提问，指定 `hs-knowledge-query`。 | 检索知识、精读同代内容与来源，并追查实际代码。 |

巡检正式知识的来源／代码引用时，在 OpenFlow 中选择同名 `hs-knowledge-lint` **Workflow**；它与上述 lint **Skill** 分属 Workflow／Skill 目录，不改变原 Skill 的默认检查行为。

ingest 已包含 P5 审阅与质量检查、P7 索引与检索验证；独立 lint 和 query 按需使用。当前公开能力共 9 个 Skill：explore、source-scan、source-prepare、change-plan、view-materialize、lint、apply、query、maintain，名称均带 `hs-knowledge-` 前缀。Workflow 另有 ingest 和只读 lint 巡检两条，不是同名终端命令。

<a id="2-加入文档后怎么入库"></a>

### ingest：通过 OpenFlow 执行入库 Workflow

1. 将原件放入知识根 `docs-raw/` 对应目录：`conventions/`（约定）、`chips/`（芯片）、`storys/`（需求）、`specs/`（规格与设计）、`protocols/`（协议）或 `troubleshooting/`（问题定位与排查经验）。
2. 确认 OpenFlow 已加载 `hs-knowledge-ingest` Workflow，9 个配套 Skill 及 `coder`、`reviewer` 角色已接入，然后在 OpenFlow 中选择并运行该 Workflow。
3. 查看 Workflow 返回的处理范围、知识更新、检查与查询结果。未完成时按实际停点和材料缺口续办。

问进度或要求继续时，Agent 使用 source-scan 的只读 `status`，同时查看扫描的 `actionable_unit_ids` 和 `finalization_pending`：原件／维护待办需要备料，已落位内容的收尾只续办索引、查询或启用。`status` 读取已保存事实和真实活动指针链，不重新全验索引；标为 unknown 的阶段仍需核实。无变化、无修订要求且无待办时直接结束，不产生新的正式记录或让下次扫描重新提炼。

历史用途卡保留其确切旧依据。旧证据仍可恢复时，当前源码升级不会单独制造该历史 Claim 的修订待办；原件真实变化、旧证据缺失或明确的语义／适用性问题仍需处理。

日常 ingest 恰好 7 个节点。以下 Skill 名省略 `hs-knowledge-` 前缀；P5 由独立 reviewer 执行，其余由 coder 执行，角色与上下文隔离由宿主安排。

| 节点 | Skill／动作 | 输入与本职结果 |
|---|---|---|
| P1 扫描 | source-scan／`scan` | 观察原件指纹差分、共享处理历史、必要来源／代码状态和本机停点，保存真实清单；不捕获完整材料。 |
| P2 备料 | source-prepare／`prepare` | 按选定扫描单元或显式目标准备新旧原文、附件、旧卡、代码／配置、差异与缺口，返回确切材料引用；可独立调用。 |
| P3 决定内容 | change-plan／`plan` | 作者阅读材料，固定逐单元处置、卡与旧 Claim 去向、记录动作和本批查询预期，保存语义计划。 |
| P4 保存稿件 | view-materialize／`run` 或 `revise` | 组织作者提供的卡稿、导航、来源锁、写删集合、处置预览和输入快照；只保存候选，不改正式库。 |
| P5 审阅与检查 | lint／`review` | 独立阅读计划、完整稿件及证据，审内容、归卡、实质 skip 和适用代码依据；无内容阻断后，同次执行一次完整固定检查。 |
| P6 转写记录 | source-scan／`record` | 机械复制计划及处置预览中已定的动作、卡／Claim 引用和欠账，保存待入库记录，不重新决定内容。 |
| P7 落位与收尾 | apply／`batch` | 核实际输入与写入安全，将内容和记录一同落位，再完整验证真实索引、执行冻结查询及同代精读，并按原活动指针基线启用。 |

P5 缺材料回 P2，作者判断或归卡有误回 P3，稿件问题回 P4。已有冻结稿时，返工使用新 `operation_id`，显式带原 `previous_view_ref` 和真实 `revision_reason`；P2 补料另带旧稿精确绑定的 `existing_material_ref` 及明确补充目标，只补缺口，不默认重扫全库。原扫描及单元身份保持不变，后续记录保存实际 `origin_scan_operation_id`；旧材料、计划、稿件和审阅不覆盖、不重签。仅退回 P4 时，可精确采用前序稿未变的计划与材料，新稿仍须重新交 P5。实际采用来源、旧卡、配置或规则已变时，按诊断回 P1 更新受影响范围。

P4 只核生产所需的一致性，P5 承担知识质量和代码语义复核。P7 的 `batch` 检查输入快照、原版本、路径、锁、CAS、备份、journal 和实际回读，不重跑 P5 完整质量检查，也不读取 passed 票据放行。内容批只有实际返回 `phase: completed`、`data.batch_complete: true`，并完成该批索引、冻结查询及启用后才结束；事务 `committed` 只说明内容已落位。仅记录批审处置和适用项，保留暂缓／失败／未覆盖事实，返回 `recorded` 和 `batch_complete: true`，不夹带失败稿件、不建索引，也不把欠账说成已提炼。

中断或响应不明时，先核原执行端进程、journal、batch 停点、查询报告和实际活动代。新 batch 沿原操作重入 P7，已 committed 的内容只核事实并续办索引／查询／启用，不再次写入；保留最初的 `expected_active`，包括真实的 null。旧 `run` 事务使用配套版本和原恢复入口，不改投 batch 重放。内容已入库但有误时，用新操作修订，保留原事实。九包同进程复用公共函数，不启动兄弟 Skill CLI；宿主 API、SSH 和进程故障按真实诊断处理，旧版本 `SIBLING_TIMEOUT` 按原配套版本处理，不据此改卡或自建 runner。

只处理部分材料时，向 Workflow 提供来源范围，例如 `docs-raw/troubleshooting/`；修订已有知识时，提供目标卡片和修改要求，原件未变也可修订。问题定位经验可按模块建立子目录，材料宜写清现象、环境与触发条件、排查过程、根因或当前判断、解决方法和验证结果，保留未解决、未验证部分。

显式给出的来源路径不存在且没有已知删除历史时，扫描会明确报告范围不存在，先核对路径；默认六类原件目录为空仍是有效扫描，已登记原件被删除则按历史来源的缺失处理，不自动删知识卡。

ingest 完成本地知识更新；Git 提交和上库由人后续处理。按本批清单一起检查卡与各级导航、来源锁、采用的 `docs-raw/` 主件及附件、`logs/ingest/` 处理记录和有效的 `logs/events/` 使用限制；被引用旧版须能从 Git 历史或同组持久位置恢复。不要只提交新卡，也不要把来源锁仍为空或只指向原机私有副本的批次当作可供他人消费的结果。

完成操作的 `.build/`、`logs/operations/`、`artifacts/` 和 `logs/evidence/` 下 `objects/`、`checked-code/`、`extractions/`、`locators/` 四类缓存不上库；清理前先确认没有未完成事务、待办事件或索引／查询收尾，并确认原版仍可恢复、提取和定位仍可重建。`logs/ingest/`、`logs/events/` 及显式采用的其他证据文件按用途保留，不能按“日志”整删。具体目录和旧版材料条件见[保存与提交边界](知识库详细设计.md#64-哪些内容上库哪些用于本机执行)。

其他用户拉取仓库后，先完成本机能力与依赖准备，取得 `config.yml` 声明的真实代码及被采用的构建／运行材料，再让 Agent 检查正式库和来源。由 apply 的 `index-build` 构建并完整验证候选代，保留返回的 `generation_ref` 和原 `expected_active`；用 `regression` 执行明确的目标查询与同代精读，通过后按该基线启用本机索引。随后可用 query 的 `search`／带原 `receipt_ref` 的 `read` 核对内容与回源，再全扫确认已处理原件无重复提炼义务。消费副本不继承生产端的私有恢复或收尾义务，无需原机 `.build/`、事务日志、复核记录和索引；本机缺索引只说明需要本机重建。旧版原件或业务材料缺失时保留真实缺口，浅克隆和只复制最新文件不保证历史引用完整。

<a id="4-怎么单独检查"></a>

### lint：使用 Skill 独立检查

向 Agent 提出检查要求，同时选择或注明 `hs-knowledge-lint` Skill。例如：**“使用 hs-knowledge-lint 检查当前知识库。”** 需要限定范围时，一并说明。

默认 `--action lint` 检查正式完整库（formal／full）；候选检查须明确 `mode: candidate` 和确切 `view_ref`，局部检查须明确范围，其结果只说明所选范围。Agent 读取报告的实际状态、完整性和问题位置；退出 0／1／2 分别表示完整无阻断、有阻断、输入或运行不可用。lint 只检查和报告；需要修复时，将问题交回 OpenFlow 的 ingest Workflow 修订后再检查。ingest 的 P5 另用 `--action review`，同时承接内容审阅和适用固定检查。

需要检查“源码变了而知识未更新”等情况时，确认实际执行端已安装配套 Skill、OpenFlow 已加载 `hs-knowledge-lint` Workflow，再运行该 Workflow。它只有两个节点：`check_formal` 显式调用 lint 的 `lint` 动作检查正式完整库；`audit_references` 调用 maintain 的只读 `audit-references`，消费实际 `lint_report_ref` 并生成 `audit_ref` JSON 和 `report_ref` Markdown。报告列出卡／Claim、来源或代码文件、原定位、旧 hash 与当前 hash、差异及材料缺口，并区分历史／指导性用途。原报告为 failed／incomplete 时仍汇总实际可检查项；无有效报告的规则或运行故障留在原节点处理。按返回的真实报告路径交付产物，不把“已出报告”当成“检查通过”。具体节点见[详细设计 §3.1](知识库详细设计.md#31-lint-的检查流程)。

周期执行由外部调度系统触发同一 Workflow，部署后需核实宿主加载、执行端路径与实际报告；知识库不另建 runner 或内置定时器。巡检只写报告，不改卡片、来源锁、事件／水位或活动索引。历史引用与当前代码不同不直接表示引用错误；需要修复时，将报告和明确的卡／Claim 修订要求交给 ingest，原件未变化也可修订。

<a id="3-怎么查询和追代码"></a>

### query：提问并使用 Skill 检索分析

向 Agent 提出问题，同时选择或注明 `hs-knowledge-query` Skill。例如：**“使用 hs-knowledge-query 分析：<你的问题>。”** 可补充目标芯片、版本或关注范围。

Agent 使用 `search` 检索正式活动代，再用原搜索 `receipt_ref` 和 `card_id` 调用 `read`，即使活动代后来变化也精读原来命中的同代内容与合格 Claim。涉及具体实现时，继续沿来源定位和 `config.yml` 模块映射追查所问版本的实际源码，给出结论、依据位置和仍不确定的部分；历史／背景知识不直接证明当前实现。已有材料不足时说明缺口，需要补充材料再通过 ingest 入库。

来源、同代正文或当前材料不可用时读取真实诊断，先补齐材料或处理运行问题，不据此修改卡片或宣布没有命中。


### 独立备料、恢复、索引与提交核对

下表列出同一批已安装 Skill 的独立用途，名称省略 `hs-knowledge-` 前缀。使用其 `scripts/cli.py --action <动作> --input REQUEST.json --output RESPONSE.json --knowledge-root K`；规则默认从实际锁读取并核验，也可用 `--rules-digest` 固定。请求、报告和材料路径按实际执行端解释，相对业务引用以 K 为基准；不要求 catalog 或上游通过票据。

| Skill | 动作 | 使用边界 |
|---|---|---|
| source-scan | `status` | 只读查看指定操作或本机可见历史；正式共享记录不证明另一台机器的索引健康。 |
| source-prepare | `prepare`（默认） | 可传真实 `scan_ref`，也可传明确 `targets`、旧卡 ID／主题／代码材料独立备料，不伪造扫描；补料沿前述新操作和旧稿绑定。 |
| source-prepare | `capture`、`resolve`、`resolve-source` | 捕获已落地原件或配置内代码，校验确切 bundle，或恢复指定来源快照及原定位；缺旧版保留缺口，不用当前新版替换。 |
| view-materialize | `describe` | 只读描述已保存的确切候选、来源与基线，不运行内容审阅或质量检查。 |
| lint | `record-review`、`code-check`、`code-recheck`、`verify-evidence` | 分别保存审阅声明、核对逐 Claim 代码依据、复查当前材料或按 current／historical 用途复验已有证据；独立动作不表示完整 P5、CI 或角色认证通过。 |
| apply | `run`（默认）、`inspect`、`resume`、`rollback`、`verify-result` | 兼容原事务用途；`run` 保留完整固定检查，只完成事务。恢复遵守原 journal，保留外部修改；`verify-result` 核实际写入字节。日常 ingest 须显式使用 `batch`。 |
| apply | `index-build`、`index-verify`、`index-activate` | 独立构建并完整验证、复验或启用索引；沿确切 `generation_ref` 和原 `expected_active`。独立启用只证明该次启用，不替代某批冻结查询和完整收尾。 |
| apply | `regression`、`regression-verify` | 传确切代和非空查询预期；`regression` 通过后尝试按原 CAS 启用；`regression-verify` 依据 `report_ref` 重跑原案例，不启用，也不能改代次、案例或基线。 |
| apply | `prepare-submission`、`verify-submission` | 整理本批精确文件与删除清单；后者按明确 `commit_sha` 只读核真实 HEAD、commit／blob、删除和变更范围，不执行 Git 提交／推送／合入。 |
| maintain | `inspect-context`（默认）、`status`、`audit-references` | 分别观察受影响 Claim、读取限制／未完成事件、生成只读引用报告，不自动修订或登记事件。 |
| maintain | `register-source-change`、`register-code-change`、`recover-events`、`advance` | 显式登记来源／代码变化、恢复 pending 事件或复查来源一致性限制；这些动作会写维护状态，不属于只读巡检。 |

维护事件 pending 缺少原 payload 或确切证据时，保留限制并阻断恢复。`advance` 不能绕过未完成事件，只能在实际卡／Claim、来源和配置已满足条件时清除机械的来源一致性限制；语义／适用性限制继续保留。raw 捕获发现已登记来源变化时会登记事件，代码捕获不隐式登记代码变更；需要显式登记时使用上表维护动作。
