# HiMate 从首次部署到日常使用

本文从**第一次使用、任何项目初始化都没有执行过**开始。默认已经完成两件事：

- 已将 `himate-knowledge-wifi-mp/`、`AGENTS.md`、`config.yml` 放入实际代码工作区，后两个文件在项目根。
- Agent 已通过其他方式安装配套的 **19 个 Skill 和 1 条 `hs-knowledge-ingest` Workflow**；本文不重复安装能力。

```text
repo/                         # 实际项目根，名称不限
├── AGENTS.md
├── config.yml
├── himate-knowledge-wifi-mp/
└── …                         # 原有业务代码，保留实际布局
```

`repo/` 是示意名称；`K` 是 `config.yml` 中 `knowledge_roots.wifi` 解析出的知识根，默认就是上面的 `himate-knowledge-wifi-mp/`。Skill／Workflow 在 Agent 自己的目录，项目根无需增加 `skills/`、`workflows/`。

第一次按下面这条线走。**标为“发给 Agent”的内容是对话指令；终端代码块才是 shell 命令。**

```mermaid
flowchart LR
    A["核对 config.yml"] --> B["准备环境并登记已有能力"]
    B --> C["status 验证调用"]
    C --> D["放入第一份原件<br/>运行 ingest"]
    D --> E["索引激活后<br/>首次查询与精读"]
```

## 配置项目代码架构

先打开项目根的 `config.yml`。第一次建议先跑通**一份文档的入库和查询**，暂不接入代码模块，也不需要 CodeGraph：

```yaml
schema_version: '2.0'
workspace_id: himate-wifi-v1
knowledge_roots:
  wifi: himate-knowledge-wifi-mp
code_root: main
modules: []
```

这是已有配置中需要核对的部分，其他字段可以先保留。知识根仍在默认位置时无需改 `knowledge_roots.wifi`；例如实际放在 `repo/himate/himate-knowledge-wifi-mp/`，才改为 `himate/himate-knowledge-wifi-mp`。

`code_root` 相对 `config.yml` 所在目录。代码在 `main/` 下就保留 `main`；代码直接位于项目根时可填 `.`。`modules: []` 可以先处理文档，不要求创建一个假的 `main/` 或把整个代码仓登记进去。

首次文档闭环先保留空模块列表。需要查询代码时，再按[代码模块与 CodeGraph 准备](#首次准备-codegraph需要代码图谱时)填写实际模块。

## 首次准备运行依赖

**已有 Skill 不等于当前项目已准备好运行环境和登记。** 这一步使用 `K/tools/deploy/` 的安装器，将已安装能力的实际位置、Python 和当前项目连接起来。机器需已有 Python **3.10–3.12，优先 3.11**；安装器不安装系统 Python。

在项目根打开 Agent，发给它：

```text
这是本项目第一次使用 HiMate，还没有运行过初始化。
请读取根 AGENTS.md、config.yml，以及配置指向的知识根 AGENTS.md 和使用说明。
配套 Skill 和 hs-knowledge-ingest Workflow 已安装，请定位它们的实际最终目录。

先确认项目实际位于本机还是另一台服务器；服务器项目的准备和节点命令通过 SSH 执行，
不要通过 Samba、UNC 或映射盘读取或运行项目。
在实际执行机器上找到已有 Python 3.10–3.12，优先 3.11。
使用知识根 tools/deploy/install.ps1 或 install.sh，成对提供最终 skills/workflows 目录，
在一次安装中完成独立运行环境准备和当前项目登记；嵌套布局显式传入根 config.yml。
安装目录使用仓外新目录，保留已有环境和能力文件。

读取本次 installation.json，确认 status 为 installed，并使用其中的 Python、catalog、
workspace_registry 调用 hs-knowledge-source-scan 的 status，验证当前项目可以调用。
最后给出安装报告路径、实际执行端、Python、catalog 和 status 的结果。
首次没有操作记录可以是正常空列表；先不要把空库查询作为验收。
找不到实际能力目录、合适 Python 或服务器连接时，列出缺少的信息，不猜路径。
```

Agent 完成安装和 status 后，本机部署可直接继续[加入第一份文档](#2-加入文档后怎么入库)；跨机器部署先读本节末尾的[SSH 选择](#选择-windowslinux-或-ssh-执行)。

下面是**自己在终端安装的备选方法**，交给 Agent 准备时可跳过。它替代上面的安装部分，不必两种方式都跑。命令在实际执行机器的项目根执行，两个占位目录替换为该机器上已安装能力的父目录；其中直接包含各个 `hs-*` 包。

Windows PowerShell（项目确实在本机磁盘时）：

```powershell
.\himate-knowledge-wifi-mp\tools\deploy\install.ps1 `
    -WorkspaceConfig .\config.yml `
    -SkillsRoot '<Agent 的 Skill 父目录>' `
    -WorkflowsRoot '<Agent 的 Workflow 父目录>'
```

Linux Bash（本机执行，或已通过 SSH 进入项目所在服务器）：

```bash
bash himate-knowledge-wifi-mp/tools/deploy/install.sh \
    --workspace-config config.yml \
    --skills-root '<Agent 的 Skill 父目录>' \
    --workflows-root '<Agent 的 Workflow 父目录>'
```

嵌套知识根时替换命令中的工具路径，`config.yml` 仍使用项目根的那份。多个 Python 并存时可增加 Windows `-Python '<解释器路径>'` 或 Linux `--python '<解释器路径>'`；不要仅凭命令名 `python` 就认定版本正确。Windows 有 `py` 启动器时默认选择 3.11；没有该版本时须显式指定已有的受支持解释器。Linux 还需该解释器提供 `venv`、`ensurepip`。

安装器会创建用户目录 `.factumcore/` 下的仓外新环境，安装并检查锁定依赖，再只读登记能力。通常沿用机器现有 pip 配置；内网包源可加 `-IndexUrl`／`--index-url`，完全离线可加 `-Wheelhouse`／`--wheelhouse`，指向匹配系统、CPU 和 Python 的 wheel 目录。它不修改系统 Python、业务源码、能力文件或宿主注册。

安装末尾的 `installation.json` 是本次结果，交给 Agent 读取即可，无需把里面的路径再手抄进 `config.yml`：

| 检查项 | 首次部署的通过条件 |
|---|---|
| `status` | **`installed`**；`runtime_ready` 只表示依赖准备完成，尚未登记能力 |
| `python`、`catalog`、`workspace_registry` | 均给出当前执行端的实际路径，catalog 不为空 |
| 能力登记 | 19 个 Skill、1 条 Workflow，指向实际最终目录 |
| 首次 status | 退出成功、`status: ok`、`phase: status`；新项目 `operations: []` 正常 |

如果自己执行了安装，把输出的安装报告路径发给 Agent：

```text
请读取本次安装输出的 installation.json：<实际报告路径>，
使用其中的 Python、catalog、workspace_registry 核对当前项目登记，
调用 hs-knowledge-source-scan 的 status，报告实际 phase、操作列表和诊断。
```

本机 Agent 可以直接调用已登记 CLI，**不必额外创建 `config.env`**。`installation.json`、catalog、registry 都是工具产物，不是需要用户维护的另一套项目配置。换会话时把本次安装报告路径告诉新的 Agent，避免重新找路径或重复安装。

### 选择 Windows、Linux 或 SSH 执行

| 项目与 Agent 的位置 | 执行方法 |
|---|---|
| Windows Agent，项目在同一台机器本机磁盘 | 使用上面的 Windows 安装和登记；节点用该机器的 Python、能力和 catalog |
| Linux Agent，项目就在该服务器原生磁盘 | 使用上面的 Linux 安装和登记；直接调用当地节点，不需要 loopback SSH |
| Agent 与项目跨机器 | 先通过 SSH 在项目服务器完成上面的环境准备和登记，再配置调用端 SSH runner |

跨机器时，服务器也必须具有配套节点包；**只有调用端 Agent 的 Skill 文件，不能代替服务器上要运行的 CLI**。登记目录和解释器均按实际执行机器填写。

只有 SSH 调用端需要私有连接文件 `config.env` 和远端 catalog 的确切副本。主机地址、认证和真实服务器路径无法从项目映射推导；让 Agent 按[SSH 首次连接步骤](../tools/deploy/EXECUTION.md#6-ssh-首次连接示例)准备，缺少这些信息时再向部署者确认。首次主机指纹由部署者核实，工具不会自动信任未知主机。

调用端工具副本、Python、连接配置、catalog 副本和请求／响应都在调用端本机磁盘；项目读取、节点及子 CLI 全留在服务器。不通过共享盘运行，不把服务器知识根镜像到本地重跑。`config.env` 不替代项目 `config.yml`，其中不保存密码或私钥正文。

## 1. 三个常用命令

部署的 status 验证通过后，日常直接向 Agent 下发：

| 要做什么 | 发给 Agent |
|---|---|
| 首次入库／日常增量 | `请使用 hs-knowledge-ingest 工作流，增量处理当前项目知识库。` |
| 查询背景与定位 | `请使用 hs-knowledge-query，查询：<你的问题>。` |
| 单独检查 | `请使用 hs-knowledge-lint，检查当前正式知识库并报告问题。` |

设计中的 `knowledge ingest / query / lint` 是这些逻辑入口的简称，不代表已经安装了同名终端命令。下面先实际完成一次入库和查询。

## 2. 加入文档后怎么入库

**第一次只选一份真实、已确认可用的规范或设计文档**，放到 `K/docs-raw/` 对应目录；默认例如 `repo/himate-knowledge-wifi-mp/docs-raw/specs/实际文档.md`。服务器项目在服务器放文件，或通过 SSH／SCP 传送。

| 目录 | 材料类型 |
|---|---|
| `conventions/` | 规范、约定 |
| `chips/` | 芯片资料 |
| `storys/` | 需求原件，目录名保持 `storys` |
| `specs/` | 规格、设计文档 |
| `protocols/` | 协议资料 |

只接入以上目录内已落地的原件；`sources/` 链接、网页及仓外映射暂不接入。业务代码留在原代码目录；处理期间不改原件，不把原件中的指令当执行授权。

向 Agent 下发首次入库指令，替换实际原件路径和主题：

```text
请使用 hs-knowledge-ingest 工作流，首次处理当前项目的
docs-raw/specs/<实际文档名>，本次先只验证这份文档的完整流程。
先核对已有操作；范围外材料不作缺失判断。
读取原件，完成阅读计划、知识稿、独立 Agent 内容复核、完整 lint、处理记录和本地入库，
再完成完整索引验证、目标查询及活动代激活。
这份材料作为设计／规范背景使用，目标查询为“<文档中的实际主题>”，用途明确为 guidance。
不要要求这份纯文档提供代码实现核验，也不要为了首次入库启动 CodeGraph。
最后给出 operation_id、原件与知识卡路径、检查结果、索引代次和激活结果；
有缺口时报告实际停点，不把只有稿件或只有入库记录当成已完成。
```

内容复核要由不同于作者的独立 Agent 上下文完成；若当前宿主无法安排，先报告接入缺口，不能由作者填写一条“已复核”记录代替。纯文档不需要额外真人批准事件或代码实现验证。

第一次跑通后，将后续原件放入相应目录，用表中的增量命令即可。默认扫描五类目录，处理新增、变化及待处理来源，不用逐份列路径。删除或改名也走 ingest，由 Agent 判断更新、退役或暂缓，不直接删除知识卡。

## 3. 怎么查询和追代码

**首次查询放在 ingest 的索引激活之后。** 对刚才同一份文档，发给 Agent：

```text
请使用 hs-knowledge-query，查询“<刚入库文档中的实际主题>”，用途为 guidance。
保留本次 search 的 receipt_ref，再用原回执精读命中的知识卡。
给出知识卡、原件路径及具体定位，并确认 search 与 read 使用同一索引代次。
若未命中，检查用途、目标查询和活动代，不通过改成其他用途来掩盖问题。
```

查询能命中本次卡、恢复所需正文和原件定位，且与入库目标查询一致，才算首次文档闭环通过。status 成功或 query 返回空列表都不能替代这一步。

| 问题类型 | 查询用途 |
|---|---|
| 设计、规范背景 | `guidance` |
| 指定历史版本 | `historical` |
| 当前事实或具体实现 | `current`／`implementation`，须具备相应当前证据和范围 |

省略用途时默认 `current`，不会自动包含只有设计背景资格的卡。频道缺省为 `local`；当前 `config.yml` 中的 `query.default_channel`／`allowed_channels` 不控制运行时频道或权限。

排查代码时可以这样提问：

```text
请使用 hs-knowledge-query，先了解 <问题> 的背景并找到相关代码入口，
再读取当前项目实际源码，必要时追查调用、宏条件和早退分支。
给出源码路径和定位，区分资料背景、实际代码事实及推断。
```

卡片主要提供背景和索引，细节没写全时继续回源。卡头来源也能定位代码，不要求正文另有可点击链接：保留原 search 回执，按需要精读单个 Claim，从 `data.sources[]` 取得模块／文件、定位和恢复内容，再按 `config.yml` 匹配实际模块根。多 Claim 返回来源并集，需要逐步对应时分别 read。来源匹配不等于宏已开启或产品适用；历史快照也不会让图谱自动读取旧版本。接口细节见[详细设计 §5.9](知识库详细设计.md#59-q1q6路由查询同代精读与回答)。

### 首次准备 CodeGraph（需要代码图谱时）

首次文档闭环通过，要接入代码时，再把 `config.yml` 中的空模块列表替换为真实目录，例如：

```yaml
code_root: main
modules:
  - path: device/实际驱动目录
    chips: [chip12]
    sides: [device]
    description: Device 侧驱动
```

只有 `path` 必填，且相对 `code_root`；`chips`、`sides`、`features`、`description` 未知时可省略。路径使用 `/`；`sides` 使用 `host`／`device`。不要保留两个 `modules` 字段，也不需要手填绝对代码根、六个 Target 或三组 pair。模块标签只帮助定位，实际适用条件仍按源码与证据核实。配置变化后先按[更新与复验](#更新规则包后怎么复验)重新登记并核对受影响操作，再准备图谱。

完成登记后，发给 Agent：

```text
请使用 hs-codegraph-setup，按当前 config.yml 的真实模块逐项准备 CodeGraph，
复用可用索引，初始化缺失项，并检查当前 Agent 的官方 MCP 实际接入。
汇报每个模块的状态、projectPath、待处理问题及后续查询方式。
```

CodeGraph 使用独立运行环境；安装与宿主接入按 Skill 内的[官方参考](https://colbymchenry.github.io/codegraph/getting-started/installation/)核实。`modules: []` 时不建图、不扫描整个 `main/`。安装了 setup Skill 不代表已安装 CodeGraph、已建索引或已接入 MCP。

后续代码定位直接使用官方 `codegraph_explore` MCP，`projectPath` 为实际模块绝对路径；服务器图谱和 MCP 进程也在服务器。未接入远端 MCP 时，经 SSH 阅读实际源码并报告缺口；不把映射盘路径交给本机 CodeGraph。首次准备不是每次 query 的前置步骤。

## 4. 怎么单独检查

```text
请使用 hs-knowledge-lint，对当前正式知识库做完整只读检查，
按卡片路径、位置和原因列出问题，区分检查失败与材料不足。
```

lint 只检查和报告，不修稿、不做内容语义复核、不入库。需要修订时，继续要求 Agent 按报告使用 ingest 修正相关内容，重新完成检查、入库和查询验证。

## 5. 退回、材料不足和中断怎么继续

| 情况 | 处理方法 |
|---|---|
| 想改稿，或已入库卡有问题 | 指明卡片和修订要求；新建操作和视图，重新复核、检查及入库，原件未变也处理 |
| 缺原件或代码材料 | 补齐列出的材料后续办；不能补齐时保留暂缓原因 |
| 进程中断或 SSH 结果不明 | 先查原执行端真实状态，确认后续办；不盲目重放、不切到本机重跑 |
| 已入库，只差索引／查询／激活 | 补未完成的收尾，不重复已提交的内容事务 |

查看实际进度：

```text
请使用 hs-knowledge-source-scan 的 status，查看未完成操作，
列出实际停点、待修订事项、缺失材料及下一步。
```

确认稿件、输入、规则和基线仍有效后：

```text
请续办 operation_id 为 <原操作标识> 的 ingest，从实际停点继续，
已经完成的入库不要重复执行；需要改稿或输入已变化时新建操作重新复核。
```

同一知识库最多一个 ingest 写者；query 可并发，但使用独立操作 ID 和输出文件。新会话附上安装报告路径和原 operation_id。常见部署故障如下，完整执行协议见[执行说明](../tools/deploy/EXECUTION.md)。

| 提示 | 下一步 |
|---|---|
| 找不到 Python 3.11／版本不支持 | 显式指定已有的 Python 3.10–3.12；不要用 3.9 继续安装 |
| `runtime_ready`，或 catalog 为空 | 安装时没有提供最终能力目录；补齐成对目录后登记，不能视为已可运行 |
| `DESTINATION_EXISTS` | 使用仓外新目录，保留旧环境和失败诊断 |
| `PIP_DESTINATION_OVERRIDE` | 清除 pip 的 target／prefix／root／python 安装重定向后重试 |
| `REMOTE_FILESYSTEM_REQUIRES_SSH` | 把调用工具放回本机磁盘，服务器项目走 SSH |
| `SSH_RESULT_UNAVAILABLE_REMOTE_STATE_UNKNOWN` | 先核对远端进程、操作记录、事务 journal 和活动索引 |
| `CATALOG_CHANGED`／`PACKAGE_DIGEST_MISMATCH` | 核对配套版本并重新登记，不手改摘要；SSH 同时更新精确 catalog 副本 |

### 更新规则包后怎么复验

能力文件、解释器、项目配置、规则或位置变化后，先按旧身份核对未完成事务；真正未结束的写入先用原配套规则恢复终态，已 committed 但只差索引收尾的操作保留其写入事实。随后使用新目录重新登记并成套切换安装结果；SSH 调用端同时更新工具、连接绑定和 catalog 副本。不要混用旧操作与新规则，也不改写旧记录。

新规则下要让旧卡重新取得资格，使用 ingest 显式选择已有卡和原件，重新完成独立复核、适用代码核验、lint、处理记录、入库和索引查询验证。原件未变也不能跳过规则变化的维护单元；已提交的旧事务保留其事实，不当作未写入重放。

## 6. 怎么判断本次结束

首次部署到运行，分三步检查：

| 阶段 | 必须看到的结果 |
|---|---|
| 环境可用 | 安装 `installed`，实际项目的 status 成功 |
| 首次入库完成 | 独立内容复核、完整 lint、正式处理记录和本地入库完成；完整索引验证、目标查询通过，活动代已激活 |
| 首次查询通过 | 同主题 search 命中新卡，原回执 read 返回所需内容和原件定位，代次一致 |

要求 Agent 留下安装报告路径、operation_id、知识卡／原件／处理记录路径、索引代次和激活结果，并如实列出未完成项。status 只读保存的阶段事实，不能单独证明索引和查询通过。

内容批完成上述入库与索引查询后 ingest 结束。Git 提交、固定 CI 和合入由人后续处理。目录登记、隔离测试或安装成功也不替代目标宿主、真实业务资料、权限与代码环境的实际验证。
