# 知识库关键点

本文说明如何以当前 **WiFi-MP 领域实现**为起点，适配其他领域的代码仓、资料分类、知识卡和配套能力。其他领域可以复用这里的流程和工具机制，但领域身份、适用范围及部分路径规则仍需配套改造、验证；目录改名或安装同名 Skill 不表示已经完成跨领域适配。

系统分层见[架构设计](HiMate知识库架构设计.md)，节点流程见[详细设计](知识库详细设计.md)，日常操作见[使用说明](使用说明.md)。本文的改动判断见第 2 节，Skill 配套范围见第 3 节，迁移顺序见第 4 节；第 1 节保留它们共用的路径与核验基础。下文 P2／P4、M 等编号沿用详细设计。

| 目标领域与当前项目的差异 | 先判断什么 |
|---|---|
| 源码不在 `main/`，模块文件夹名称不同 | 通常通过 `code_root`、`modules[].path` 映射真实目录，保留已有源码布局 |
| 原件种类、知识分类不同 | 区分现有目录内新增内容、增加 raw 类别和增加卡片 Profile，分别改对应规则与能力 |
| 芯片、端、Target 或领域标识不同 | 检查 WiFi 专用 Schema、配置发现、派生模型和取证约束，不能只改配置标签 |
| 希望同包支持多个领域 | 先补领域选择和规则装载；当前实现不能靠增加一个配置键自动获得这些能力 |

## 1. 工作区路径与部署边界

### 1.1 路径基准

```mermaid
flowchart TD
    ROOT["project_root<br/>项目根 repo/"] --> CONFIG["AGENTS.md / config.yml"]
    ROOT -->|相对项目根| CODE["code_root<br/>默认 main/"]
    CODE -->|相对代码根| MODULE["模块 path<br/>实际代码目录"]
    ROOT -->|knowledge_roots.wifi 相对配置目录| K["K：知识库根<br/>允许安全的前置子目录"]
    K -->|相对知识根| ASSETS["raw · 卡 · 记录 · 规则"]
```

| 名称 | 路径含义 |
|---|---|
| `project_root` | 项目根，示意为 `repo/`；保留业务仓的 `AGENTS.md` 和项目 `config.yml`，可管理多个 Git 仓；`AGENTS.md.example` 是接入示例 |
| `code_root` | `config.yml` 中的代码根，相对 `project_root`，默认 `main` |
| 模块 `path` | 相对 `code_root` 的实际目录，可覆盖一个或多个子仓 |
| `K` | 知识库根，由 `config.yml` 的 `knowledge_roots.wifi` 相对配置目录解析；默认 `himate-knowledge-wifi-mp/`，可增加安全的前置目录；raw、卡、记录及领域规则使用根内相对路径 |
| `S`、`F` | Agent的Skill指引与Workflow编排目录；执行端CLI不依赖其脚本，也不依赖项目根分发源码 |
| `S/hs-knowledge-explore/` | 全库能力入口与路由；仅在缺少项目上下文时执行只读发现 |
| `K/knowledge.py`、`knowledge.cmd`、`knowledge.sh`、`K/runtime/` | 随知识仓分发的实际命令、八阶段实现、manifest与依赖锁；裸命令通过每执行端一次install-command注册，治理规则锁仍独立 |
| `K/docs-raw/sources/dbox.local.yml` | 本机固定目录映射；schema_version为字符串1.0，path是执行端原生绝对目录，不从K父目录或调用端盘符猜路径，不合并共享config |
| 外部版本材料 | 可补充文件的版本标签与出处；不替代实际文件核对 |

### 1.2 知识库与代码位于同一工作区

整个项目只有两部分：真实业务工作区中的知识根、业务仓 `AGENTS.md` 与用户维护的 `config.yml`，以及 Agent 自己目录中已安装的 Skill／Workflow。根 `AGENTS.md` 说明业务架构与开发约定；本开发仓仅本地维护它，共享分发 `AGENTS.md.example`，部署时按真实路径合并四项位置说明和 explore 入口指针。全库能力路由归 `hs-knowledge-explore`，不要求把知识库能力表复制进业务仓说明。实际执行由K内CLI和runtime承担，每个执行端分别准备Python与依赖；业务产物沿用已有K布局，不外放。

```mermaid
flowchart TD
    subgraph AGENT["Agent 能力目录"]
        SETUP["hs-knowledge-explore<br/>任务路由<br/>按需只读定位项目入口"]
        S["Skill指引／Workflow编排"]
    end
    subgraph WORKSPACE["真实业务工作区 repo/"]
        CONFIG["config.yml<br/>用户维护项目配置"]
        CODE["实际业务模块"]
        K["知识库 K<br/>CLI/runtime·原件·知识·治理"]
        OUT[".build/：本批暂存<br/>logs/：正式事实与必要依据<br/>artifacts/：本机索引和报告"]
        CONFIG --> CODE
        CONFIG --> K
        K --> OUT
    end
    SETUP -->|"读取"| CONFIG
    SSH["OpenFlow SSH MCP<br/>远端执行前由部署者配置并验证"] -->|"仅远端执行"| HARNESS["Agent/harness<br/>本机执行或使用宿主 SSH MCP"]
    S --> HARNESS
    HARNESS -->|"执行并检查结果"| K
    HARNESS -->|"只读取证"| CODE
```

首次部署或本机依赖缺项使用分发仓根的 `deploy.ps1`，安装能力并由 Windows 直接在所选项目路径解压知识 ZIP。Agent 按已安装 `hs-knowledge-explore` 的指引选择知识库能力；后续缺少入口信息时才调用只读项目接口，定位代码仓、知识根并加载真实 `AGENTS.md`、`config.yml`；已有部署和有效上下文不重复部署或发现，explore 不自动执行 pip 或远端 setup。旧 setup 仅供显式诊断与兼容；业务运行不创建私有虚拟环境、catalog、registry 或机器 binding，也不要求用户执行登记步骤。业务 CLI 不要求 catalog；规则摘要默认取当前锁，仍核验规则文件，不增加第二套配置。操作见[使用说明](使用说明.md#首次准备运行依赖)。

| 配置／产物 | 位置与职责 |
|---|---|
| 项目配置 | 用户手填根 `config.yml`，知识根相对该文件，模块相对代码根 |
| 仓内CLI与运行包 | K的knowledge.py／cmd／sh及runtime；manifest与治理锁分别核验，Python环境每执行端准备；doctor和命令注册见[使用说明](使用说明.md#22-仓内命令入口与诊断) |
| 远端执行 | 用户或部署维护者先在 OpenFlow 配置、启用并验证 SSH MCP，凭据由宿主管理；Agent在服务器原生K调用随知识仓分发的CLI，不逐次传Skill脚本 |
| 本批暂存材料与稿件 | K 的 `.build/operations/<操作>/`；前六步的新证据、核验副本、请求和输出在此保存，P7按本批清单清理 |
| 共享处理与使用限制 | K 的 `logs/ingest/`、有效 `logs/events/`；记录正式处理结果和仍适用的限制，随对应资产共享 |
| 正式发布与必要依据 | K 的 `logs/publications/<操作>/`、`logs/evidence/published/`；发布后保留，支持清理后的状态查看、回源和提交核对 |
| 本机事务与恢复材料 | 新事务日志和备份在 `.build/operations/<操作>/transaction/`；旧 `logs/operations/` 保持显式兼容，不整体提交 |
| 可重建索引与报告 | K 的 `artifacts/` 等现有产物目录；本机索引不随生产者的暂存一起清理，也不是换机消费的前置 |

部署升级按资产所有权分区：本版能力包、安装根部署清单记录的旧包及明确历史包按新版本精确同步，清除包内过时文件／目录与退役包；其他能力和未知同前缀包保留。`.factum-knowledge-deploy.json` 仅供安装器记账，不参与能力发现、业务规则或机器绑定。K内启动器、完整runtime与 `governance/{contracts,schemas,specs,templates}/` 四个纯框架子树分别成套同步，其余共享入口与文档按明确文件更新；不能整个替换治理目录或知识根。来源锁、原件与卡及导航、私人来源配置、全部日志、未完事务、稳定写锁、巡检基线、索引和查询回执在升级时保留，详见[部署与升级](使用说明.md#2-首次环境安装)。

目标代码仓在远端时，先由用户或部署维护者完成[OpenFlow SSH MCP 配置与验证](使用说明.md#12-远端执行先配置-openflow-ssh-mcp)，连接凭据由宿主管理。远端须已有配套Python及锁定依赖；Agent通过该SSH MCP在服务器原生K运行同一仓内CLI，并检查实际结果。同机执行不要求 SSH。调用端的安装路径不能直接当作远端路径，部署脚本只检查本机 Python 与运行依赖，不配置宿主 MCP 或验证远端环境；运行环境不可用时报告缺口；CLI不内置SSH、不推断Samba映射，Windows经映射盘运行仍有网络文件访问开销。连接、环境和任务完成以实际结果为准。

K 继续由确切 `config.yml` 解析，允许安全嵌套，不把知识根父目录当项目根。代码按真实模块读取，空模块列表不创造源码范围。目录和模块标签不证明版本、宏、构建或产品适用。

普通本地运行和直接 Git 快照消费不要求原机器的私有登记。shared 索引构建请求可直接提供 `knowledge_commit`，按实际 Git 仓根核对卡、规则、来源锁和引用，结果只声明 `repository_snapshot`，query 复验所用代次记录的快照；构建时若显式提供签名发布回执，另外核验受信 adapter 与签名的身份真实性。签名身份与上游 Skill／CI 是否通过是不同信息。历史记录按确切 Git 内容和指纹恢复；当前配置有错误、歧义或不安全路径时不能用历史分支绕过，也不据此允许任意仓外读取。

换机需要可恢复的正式资产：原件及附件、卡及导航、来源锁、配套规则、正式处理记录、有效使用限制，以及本批正式发布结果和必要依据。代码及采用的构建／运行材料按实际模块另行取得。生产者的暂存、事务备份、私有审阅和机器索引不成为消费端前置，也不把原机续办义务传给其他工作区。同ID旧卡及其采用来源须按确切版本与内容指纹恢复，不能以当前卡或最新版替代；旧正式引用和记录不为换机或规则升级搬迁、重签、覆盖。

按正式提交清单在独立工作区核对普通扫描、lint、回源、索引重建和查询，并检查指定操作的正式发布结果与提交清单；这些操作不应依赖原机旧暂存。新的查询需要本机可用索引，旧查询回执所指代次未保全时应重新查询，不能把“索引可重建”理解成旧回执也能原样恢复。保存边界见[详细设计 §6.4](知识库详细设计.md#64-哪些内容上库哪些用于本机执行)。

当前查询频道由请求 `channel` 选择，缺省为 local；`config.yml` 的 `query.default_channel`／`allowed_channels` 不控制运行时默认或访问权限。

### 1.3 项目视图与文件核验边界

```mermaid
flowchart TD
    CONFIG["config.yml<br/>模块路径与归属"] --> MAP["共享映射与路径检查"]
    CHECKOUT["业务工作区<br/>已落地代码文件"] --> MAP
    MAP --> FILES["选定文件快照<br/>内容指纹＋定位"]
    VERSION["可选版本材料<br/>标签＋出处"] -.补充.-> FILES
    FILES --> READ["P2备料／P3阅读／P5独立复核"]
    FILES --> CHANGE["M 比较变化与限制用途"]
```

`config.yml` 维护模块路径、芯片、端、特性与用途。代码目录按统一的文件取证规则处理，同一模块覆盖多个子目录时，分别固定选定文件的内容和定位。

外部版本材料通过可选 `version` 记录明确提供的标签并保留出处，含义以原材料为准。缺失字段保持 unknown，不阻断当前文件的静态源码核验，也不冒充某个已发布产品版本。

当前核验比较原配置、实际路径和工作树文件内容指纹，不能只读 Git 已提交对象而漏掉未提交修改；旧结论也不能因目录标签相同就继续有效。涉及构建／运行断言时，Agent 将采用的配置、Target、材料文件和逐 Claim 引用作为 `code_contexts` 固定进索引，查询直接复查实际字节。这是生成的业务数据，不是另一份用户手填配置，也不依赖lint代码核验或apply的通过票据。静态源码结论和纯文档无需为此提供构建材料。缺少真实路径、Target 条件或必要材料时保留缺口；标签只帮助定位，不能证明宏开启、构建成功或协议兼容。

人工测试可逐个调用Skill；OpenFlow负责Workflow顺序、角色隔离和交棒合法性。Skill不要求流程身份、登记或上游通过票据，仍须核对本次输入、内容绑定、来源／代码范围、索引完整性和写入安全。知识质量与内容／代码独立审阅集中在P5。P7的 `apply.batch` 核对实际输入、原版本、允许写删及落盘字节，发布正式处理事实后验证索引、执行预定查询，并按原活动指针基线启用，不重跑整库质量判断。旧 `apply.run` 仍执行原完整固定检查，两者都不自动证明宿主已落实独立复核。

### 1.4 入库过程与正式资产

新启动ingest只从当前输入、正式处理记录和维护限制判断待办，不搜索旧草稿、日志或索引收尾。前六步在本批暂存目录中准备材料、成稿、审阅和生成待发布记录；普通捕获不会提前发布证据或登记正式事件。正式卡、导航、来源锁、处理记录、事件及索引在这期间保持不变。原件未变的明确修卡请求仍可处理，但普通扫描不会猜测上次的未完成修订意图。

P7按P5已审路径与字节发布内容和必要依据，回读核验后才保存正式成功处理记录及适用事件，再完成本批索引、目标查询、同代精读和启用，最后清理本批可删暂存。内容已发布与整批已完成分别记录。仅记录批保留欠账，不采用未接纳的来源版本发布变更事件，也不构建或启用索引。清理只处理本批清单，借用、保护或用途不明的文件保留并说明；不删除其他操作、正式依据、当前索引或稳定写锁，也不要求 `.build/` 全空。

清理失败保留已发布事实并报告整批未完成；只有明确继续该操作时，才补缺失的检索收尾或清理，不重复写入。指定操作的 `status` 优先读正式发布清单与完成结果，旧格式则读该操作的固定停点和确切引用；省略目标才是全局历史查看。历史完成只证明已保存的执行事实，当前规则、来源或索引资格须另核。旧事务恢复仍按原协议保护外部修改，不把旧事务改投新批次；不以删目录代替恢复。未完成草稿的定期回收和罕见P7部分写入的自动修复不在当前保证内。

这些边界应随领域适配一起保留，不能用独立maintain常规清理节点替代P7，也不能让新入库依赖原机历史目录。运行方法见[使用说明](使用说明.md#暂存正式资产与换机)，机制见[详细设计 §5.7](知识库详细设计.md#57-p7安全事务真实索引与检索收尾)和[§6.3](知识库详细设计.md#63-命令分派与工作流续办)。

## 2. 目录与领域规则如何适配

### 2.1 源码布局变化：先改映射，不改真实目录

`main/` 是默认值。目标代码仓可以保留自己的顶层目录和多仓布局，由配置描述实际位置；不用为了套用知识库，把源码目录重命名为 `main/` 或重新整理成 WiFi 的目录结构。

| 变化 | 配套工作 |
|---|---|
| 代码根不是 `main/` | 更新 `code_root`，它相对 `config.yml` 所在项目根；实际代码就在项目根时可用 `.` |
| Host、Device、算法或其他模块的文件夹名称不同 | 更新 `modules[].path`，它相对代码根；登记真实存在的模块，不按示例创建虚构目录 |
| 知识根改名或在工作区内增加前置目录 | 更新 `knowledge_roots.wifi` 的路径值及文档指针；这是物理路径配置，领域键本身仍有第 2.4 节的约束 |
| 执行机器或服务器仓根变化 | 使用 OpenFlow／宿主已有 SSH MCP 进入实际项目根，核实执行端原生K、Python与仓内运行包和依赖；不把调用端路径当成服务器路径 |

路径仍须满足同一工作区、相对路径和无链接等约束，依据[模块声明检查](../governance/contracts/validation.py#L346)与[知识根定位](../governance/contracts/validation.py#L422)。

**路径能配置，不代表已有数据会自动迁移。** 当前按工作区相对路径派生 repo/module 身份；改代码根或模块路径可能改变这些身份和配置指纹。已有卡片、来源登记、代码上下文和索引须重新核对，按正常更新或明确的数据迁移处理，保留历史原字节。[身份派生依据](../governance/contracts/validation.py#L477)

知识根改名还要验证历史恢复：旧式 Git 恢复会检查保存路径与当前 K 的前缀；普通来源引用的确切原版也须在新工作区可恢复，原机保留的证据对象不能成为唯一依据。不能只验证新文件可读，就认定旧版引用仍可恢复。[恢复路径依据](../governance/contracts/source_resources.py)

目标业务仓也要按实际目录合并 Git 忽略、字节保持和 CI 路径规则。本开发仓的 [`.gitignore`](../../.gitignore) 含 `main/*` 占位及 WiFi 知识根前缀，[`.gitattributes`](../../.gitattributes) 对受锁文件保留原字节；这些开发仓规则不能整份覆盖目标仓原有的代码跟踪策略。新目录的运行产物排除、规则摘要和换行处理都要单独核对。

### 2.2 扩展 docs-raw：类别和格式分别处理

当前原件入口为 `docs-raw/`，包含六类仓内原件和 `sources/dbox` 本机目录映射。dbox 的逻辑路径与目录内相对路径形成来源身份，实际绝对目录仅由 K 内被忽略的 `docs-raw/sources/dbox.local.yml` 提供；换电脑或搬目录不改变来源身份，但执行中的操作必须复核原目录绑定。默认全量包含 dbox，缺配置不能当库空；显式限定普通 raw 时不检查无关 dbox。首次配置与填写方式见[使用说明](使用说明.md#21-首次配置-dbox-资料目录)。其他领域先判断能否沿用现有类别，再决定是否新增顶层类别。

| 扩展方式 | 是否要改运行实现 |
|---|---|
| 在现有类别下增加普通子目录 | 扫描已递归支持；通常只需放置原件、补充领域分类说明并验收实际输入 |
| 新增、改名或删除顶层 raw 类别 | 要同步扫描、主件与附件捕获、适用的历史恢复和治理声明 |
| 接入新的文档格式、编码或外部来源 | 要另做提取、定位、来源恢复或获取适配，新增文件夹不会增加这些能力 |

新增顶层类别的直接改动点为：

- source和巡检共用的[原件枚举与扫描范围检查](../governance/contracts/source_inventory.py)，source 的 scan.py 只是薄入口。
- `hs-knowledge-source`共用的[RAW_CLASSES与主件／附件准入](../governance/contracts/source_operations.py)。
- 公共契约中适用的 [旧式 Git 原件恢复范围](../governance/contracts/source_resources.py#L139)。
- [registries.yaml 的 allowed_raw_roots](../governance/schemas/registries.yaml#L19)、规则锁、分类文档及相关 Skill／Workflow 指引。当前扫描和捕获各自使用代码白名单，单改该 YAML 声明不会启用新类别。

原件类别和卡片类型是两个维度；新增资料类别通常仍是 `kind: raw`，一个原件也可以产生多种卡，不需要为每个 raw 文件夹增加一种 Profile。[来源类型声明](../governance/schemas/sources.schema.json#L26)

当前文档主件支持非空 UTF-8 MD/TXT、每页有文字层的 PDF 和可提取的 DOCX，dbox复用同一套提取与附件规则；扫描图、其他格式、网页链接和平台 API 不会因目录接入自动获得支持。dbox的配置根和内部路径均不跟随原生链接/junction，不放宽全局 safe，也不扩大代码模块范围。新增适配须同时验证原字节、提取文本、locator 与历史复现；保留不透明附件字节不表示已解释其内容。[文档提取依据](../governance/contracts/source_operations.py)

源码目录改名和代码语言也要分开判断。源码捕获使用显式 UTF-8／GB18030 文本适配并生成行定位，读取文本不表示完成了新语言的语法、语义或 CodeGraph 验证；换语言时分别核对这些能力。[源码捕获](../governance/contracts/source_operations.py)、[解码与行定位](../governance/contracts/source_resources.py#L6)

### 2.3 扩展 knowledge：先复用卡结构，再决定是否增加类型

当前七类 Profile 为 `entity`、`flow`、`protocol`、`rule`、`command`、`runbook`、`glossary`。目标领域可以继续用它们表达对象、流程、协议、规则、命令、排障和术语，先补充本领域内容与导航。[现有 Profile](../governance/schemas/profiles.yaml)

| 变化 | 需要配套修改的内容 |
|---|---|
| 沿用现有 Profile，新增目标领域知识卡 | 使用现有 Card/Claim 格式、输出范围和导航规则；不因业务内容变了就改索引算法 |
| 只调整某类卡的必填章节 | 修改 `profiles.yaml`、对应模板和规则锁；评估已有卡的兼容与修订，章节检查已从规则读取 |
| 改变某个 Profile 的默认输出目录 | 修改公共 production 的 Profile→目录映射和允许目标范围，核对导航、链接和索引；已有卡移动须显式迁移 |
| 新增或重命名一种 Profile | 同步 frontmatter 的 Profile 枚举、`profiles.yaml`、对应模板、规划目录映射、导航、规则锁与测试 |
| 新增适用维度、Claim 字段、locator 或检索字段 | 扩展相应 Schema、解析和引用／范围校验；确实参与检索的新字段，再修改索引与查询逻辑 |
| 改变顶层 `knowledge/`、`governance/` 或正式卡格式 | 属于布局／协议改造，检查、扫描、规划、落位和索引等多处均需适配，不能作为普通目录改名处理。[正式库检查入口](../governance/contracts/checks.py#L279)、[索引扫描](../governance/contracts/index_runtime.py) |

直接目录耦合在受锁公共 [production.PROFILES 映射](../governance/contracts/production.py#L15)及[candidate 目标范围和身份检查](../governance/contracts/production.py#L95)。P3 change-plan只冻结作者判断，P4通过公共生产函数选择确切目标；已有卡不能借普通更新隐式换路径。Profile枚举和章节声明必须一致，见[规则一致性检查](../governance/contracts/validation.py#L247)；完整章节及内容规则由P5调用[parse_card](../governance/contracts/knowledge.py#L43)核对。

**新增同结构 Profile，不必机械地改索引和查询算法。** 当前索引保存 Card/Claim 元数据及选定词项，查询按代次清单读取并解码卡片，没有为七类卡分别编写检索分支；索引必需的解码不重复执行P5整库质量审查。保留相同业务结构时，先验证新Profile能规划、检查、入库、索引及查询；增加新的检索含义时才修改相应实现。[索引字段](../governance/contracts/indexing.py)、[公共查询读取](../governance/contracts/query_runtime.py#L326)

反过来，新增适用条件不能只让 Schema 接受字段：当前条件存在性与范围匹配有明确维度，必须同步它们及相应查询输入，才能影响结论资格。[条件与范围匹配](../governance/contracts/knowledge.py#L286)

### 2.4 更换领域：核对 WiFi 专用假设

当前实现中的以下限制需要由适配开发者处理，不能交给业务用户通过随意改标签解决。

| 当前固定点 | 目标领域的适配范围与依据 |
|---|---|
| `knowledge_roots` 只允许唯一 `wifi` 键 | 联动 workspace Schema、部署配置解析、explore发现、公共配置定位、来源恢复及代码捕获；旧setup诊断也须同步。修改路径值与更换领域键是不同工作。[Schema](../governance/schemas/workspace.schema.json#L15)、[部署入口](../../deploy.ps1)、[旧setup诊断](../runtime/himate_knowledge/stages/explore/setup.py)、[发现](../runtime/himate_knowledge/stages/explore/node.py)、[公共定位](../governance/contracts/validation.py#L422) |
| `knowledge_domain: wifi` 与 `contract_family: aiot-wifi` | 领域 Schema、派生上下文、代码域检查、契约声明、装载校验及规则锁须匹配。改文件夹名称或标题不会改变这些身份。[派生领域](../governance/contracts/validation.py#L479)、[取证检查](../governance/contracts/source_operations.py)、[契约族声明](../governance/contracts/__init__.py#L5)、[规则装载](../governance/contracts/validation.py#L183) |
| `chip12`、`chip08`、`chip07c` 模型 | 模块配置虽能写其他芯片字符串，当前会记录域外标签缺口，且仍只为这三类派生 Target；卡片 Context 的 chip 枚举也限定三类或 null。新增标签不等于模型适配。[标签与派生](../governance/contracts/validation.py#L459)、[卡片枚举](../governance/schemas/frontmatter.schema.json#L164) |
| `host`／`device` 与相应 Target／pair 关系 | 若目标领域采用其他端或配对模型，要联动模块 sides、卡片 Context、派生视图及旧式兼容检查；用户仍填写真实模块，不恢复为手工登记 WiFi 六 Target／三 pair。[端检查](../governance/contracts/validation.py#L371)、[Target 派生](../governance/contracts/validation.py#L498) |
| WiFi 的术语、原件提炼问题、示例与核验提示 | 适配领域 AGENTS、分类说明、模板、写作／复核指引、回归问题和代码图谱指引；保留未知范围与证据要求，不把 WiFi 的结论换名后当成新领域事实 |

受锁契约、Schema、Profile、模板或规范发生变化时，审查兼容版本并更新 `framework.lock.yaml` 摘要；同步运行包与固定 CI 的受信规则。不要改写历史记录以伪装成在新规则下完成的处理。[逐文件规则核验](../governance/contracts/validation.py#L183)

## 3. 哪些 Skill 和 Workflow 可以复用

当前能力的**处理机制可以复用，分发包仍需与目标领域规则配套**。优先集中适配公共契约，再修改具有直接目录／领域约束的节点；不要把同一个枚举复制到每个 Skill 里。

| 能力 | 可复用机制 | 领域适配边界 |
|---|---|---|
| explore | 路由、部署指引、只读发现、CodeGraph首次准备 | 实际配置、入口和代码仓；图谱不证明语义或构建 |
| source | 默认run同进程执行P1扫描和按待办P2备料；scan、prepare、capture、resolve、resolve-source、record、status各独立保留，P6仍转写待发布记录 | raw白名单、提取／编码、配置范围及来源身份；扫描事实由脚本生成；补料只prepare，输入漂移按变化对象刷新，不搜索旧执行或提前发布 |
| change-plan / view-materialize | 作者语义计划及冻结查询；直接六决策成稿、修订、导航与输入快照 | Profile、输出范围、旧Claim去向；P4只负责生产一致性 |
| lint | P5独立审阅计划、稿件、全部处置及必要代码；无内容阻断后一次完整固定检查；默认只读正式库检查 | 领域语义指引、逐Claim实际条件、引用与材料；记录批审欠账，内容已阻断时标明固定项未执行；code-check/code-recheck不替代CI |
| apply | 安全发布／恢复、真实索引、回归、限定清理和只读提交核对 | 允许写删、正式依据／记录、并发基线和实际索引协议；batch不重跑P5质量，清理仅限本批可删材料，旧run保持原事务语义 |
| query | 独立用途过滤、同代检索与精读 | 新领域范围和查询预期；不加作者批次／apply通过票据 |
| maintain | 差异筛选、完成核验与成功基线；当前影响、事件／限制和只读引用报告 | historical/guidance/current用途、确切原版、跨轮欠账、pending恢复和CAS；内容判断与发布复用既有ingest能力 |

上述是8个 `hs-knowledge-` 前缀指引包。对应执行阶段在K的 `runtime/himate_knowledge/stages/`，公共算法通过受锁contracts同进程复用，不委派兄弟CLI或导入已安装Skill的私有脚本。迁移时同步指引、运行manifest、依赖锁和治理锁；没有WiFi目录常量不表示可脱离领域规则。固定CI继续从受信基线执行K的check.py，不调用Agent或代码审阅包装。[P5与独立代码核验](../../skills/common/knowledge/hs-knowledge-lint/SKILL.md)

OpenFlow的ingest可复用七个业务步骤、六个调度节点及角色／返回结构。首个coder节点prepare_sources默认run完成P1脚本扫描和P2按待办备料，prepared交P3；仅完整且没有待办、维护限制、缺口或明确目标时unchanged结束。P3—P7职责不变，P5仍为独立reviewer。P3／P4／P5缺料回首节点时明确prepare定向补齐，不先run或重扫；语义和稿件问题仍回P3／P4。输入漂移按原文、旧卡、代码、配置或规则对象刷新，不能把affected_scope诊断路径全当raw的source参数；缺口可交P3，运行故障留节点。返工新operation精确关联旧稿及理由，保留仍有效的原扫描／单元身份，不覆盖历史工件。适配领域时，Skill ID、实际安装位置、返回数据和产物契约必须配套。[现有ingest编排](../../workflows/common/knowledge/hs-knowledge-ingest/workflow.yaml)

巡检 Workflow 先独立同步，再用脚本比较上次成功基线、raw 清单和登记代码文件，按实际待办复用 source.prepare 与 ingest P3—P7；无内容问题直接核验结束，仅索引问题维护派生索引。实际处理、查询、激活与清理完成后才以 CAS 推进本地成功基线，欠账和失败保留。外部系统负责周期触发，不嵌套 Workflow；旧 lint Skill 的默认 formal/full 与独立 audit-references 继续可用。代码引用分别处理 current（整文件改变需复核）、guidance（符号唯一可定位不为插行重写）和 historical（可恢复旧证据保留）；删除、歧义及不可用不猜测修复。固定巡检日志、本地水位与正式发布闭包分开保存。[治理巡检编排](../../workflows/common/knowledge/hs-knowledge-lint/workflow.yaml)

这些通用命名的Skill ID可以继续使用。同一Agent安装范围的同名指引只有一份；实际CLI/runtime随各K保存，显式跨K调用重新启动目标入口，不能混用运行包。若指引与阶段协议不兼容，仍须使用配套版本。希望一套指引服务多个领域时，须先适配领域选择、规则装载和直接硬编码，再逐域验证。当前不能在一个 `knowledge_roots` 中简单并列多个领域，也不能把同名包覆盖安装当成多领域支持。

## 4. 迁移顺序与验收

```mermaid
flowchart TD
    SCOPE["明确目标领域<br/>实际源码、资料与适用条件"] --> DIFF["列差异<br/>路径 · raw · Profile · 领域模型"]
    DIFF --> ADAPT["配套适配<br/>配置、规则、直接耦合节点与指引"]
    ADAPT --> PIN["核对规则锁、包版本<br/>Git 字节规则与 CI 路径"]
    PIN --> SAMPLE["最小真实样本<br/>文档链路＋适用代码链路"]
    SAMPLE --> CHECK{"入库、检查、索引<br/>查询与恢复均可核对？"}
    CHECK -->|否| FIX["按问题定位缺口<br/>修订后重新验证"]
    FIX --> ADAPT
    CHECK -->|是| EXPAND["再扩大材料范围<br/>保留领域边界与证据"]
```

新领域建立自己的原件、正式卡、来源登记、处理记录和索引。可以复用框架与模板，WiFi 的业务原件、知识结论、旧索引和回执不能因此成为新领域的有效材料；需要迁移历史内容时，逐项保留身份、授权范围和可恢复依据。

| 验收对象 | 至少核对什么 |
|---|---|
| 路径与部署 | 实际模块能定位；空映射、错误路径和越界路径保持正确结果；真实业务 AGENTS、远端能力和执行端路径已核实 |
| 文档生产与消费 | 用目标领域原件验证 ingest 业务链路、独立内容复核、固定检查、入库、索引验证与目标查询，再按回执精读和恢复来源 |
| 适用代码链路 | 核对目标领域的模块、条件与确切源码；源码变化能使旧的当前实现依据失效，历史／指导性用途不被误判为当前实现 |
| 本轮扩展点 | 新 raw 类别验证默认与限定扫描、嵌套目录、主件／附件及历史恢复；新 Profile 验证章节、规划路径、导航、索引与查询 |
| 更新与恢复 | 新原件增量、原件未变的明确修卡、前六步中断后重新入库、指定操作续办、清理失败、规则变化及迁移后旧引用分别验证；不靠采用旧草稿或改写旧记录获得通过 |
| 版本与权限 | 实际安装包、规则锁、CI 受信基线和样例材料匹配；领域数据与访问权限由真实部署落实，目录名和频道配置不提供 ACL |

机制回归与部署验收分开记录：机制验证可逐个调用 Skill，核对相同业务输入输出；按本方案部署的日常 ingest 仍通过 OpenFlow 运行，另行验明实际 Workflow、角色、交棒和停点。节点测试通过不表示宿主编排已接入。

先用最小样本确定适配有效，再扩大入库范围。纯文档链路不要求虚构芯片、端或业务源码；它通过只证明该链路与材料范围内的结果，不能替代目标领域的代码模型、宿主接入或权限验收。
