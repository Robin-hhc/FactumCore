# HiMate 知识库架构设计

## 1. 系统目标

HiMate 将设计文档、规格和代码分析整理为可追溯的知识卡，帮助 Agent 在开发和问题定位时找到相关结论、适用条件及实现入口。原件保存完整材料，卡片按主题提炼重点，索引提供快速定位，三者共同支撑知识使用。

系统以单个知识根为管理边界。文档更新通过 ingest 处理，周期治理通过 lint 发现原件和已引用代码的变化，查询通过精确词项、显式标签及整卡退役筛选定位候选。每个知识根串行执行内容更新，定时触发由执行环境提供。

## 2. 知识与来源模型

### 2.1 原件、卡片与引用

原件位于 `docs-raw/`，正式卡位于 `knowledge/`。一份文档可以形成多张主题卡，一张卡也可以融合多份文档和多个代码入口。卡片保存结论、条件、理由和必要证据，而完整原文通过引用读取。

卡头承担稳定身份、文档与代码关系，以及可选标签和整卡生命周期；新卡三个必填、两个可选字段的权威定义见[卡片规范](../governance/specs/cards.md)。标题和知识内容放正文。

来源登记使用统一的 `source_id` 标识文件，卡头的 `doc_id`、`code_id` 引用相应文件 ID。章节、页码和行段位于引用项中；同一代码文件中的多个函数可以分别引用。普通内容更新沿用文件身份，内容版本由 SHA-256 表示。

正文保留主题结论、适用条件、版本、不同性质的依据及必要缺口。设计要求、代码观察与测量结果分别表达，代码引用不证明实现已完成。旧卡的显式结构化知识保持可读，正常更新时迁入相应正文，读取和重建索引不改写旧字节。

### 2.2 持久资产与派生索引

`governance/sources.lock.yaml` 保存来源 ID、实际路径、代码编码，以及各文件最近一次完整处理的存在性、内容 hash、时间和可用 Git 定位。这些事实与正式卡一起保留，使没有产卡的处理结果也能被记住。

`artifacts/knowledge.sqlite` 保存文件表、卡片表、引用关系及检索词项。它支持按文件查关联卡、按卡查全部来源，以及列出被卡引用的文档或代码文件。数据库属于派生资产，可从来源登记和正式卡重建；Agent 通过 CLI 查询关系。

### 2.3 内容版本与处理进度

扫描以当前文件的 SHA-256 与最近成功处理的 hash 比较，区分新增、修改和删除。选中文件的原始副本与 hash 来自同次读取，本轮作者和审阅者使用该副本。入库成功后登记这次处理的版本；外部文件随后再变，下次扫描仍会发现差异。

Git 用于按需读取已有历史版本。来源提交可以辅助定位原文，但日常判变直接使用文件内容。卡片、原件和代码在周期治理完成前可能存在版本差异，使用者应按任务需要核对实际来源。

## 3. 执行组件

| 组件 | 负责内容 |
|---|---|
| Workflow | 节点顺序、执行角色、分支、返工和巡检循环 |
| Skill | 单步目标、必要材料、操作指引和交付要求 |
| 仓内 CLI | 参数处理、文件操作、关系查询、固定检查和索引维护 |
| `governance/contracts/` | 来源解析、卡片解析、版本检测、符号定位和检索算法 |
| 作者 Agent | 阅读材料、选择六决策、按主题写卡 |
| 审阅 Agent | 独立核对事实、条件、遗漏及知识归属 |

CLI 执行文件、结构解析、定位与固定检查，可调用预先准备的本地 Docling/OCR 模型；知识判断、图意理解与内容审阅由 Agent 完成，不自动调用远程视觉服务。Skill 包由 `SKILL.md` 和按需阅读的 references 组成；执行代码、依赖和测试集中在对应工程目录。运行包与治理规则分别由 `runtime/manifest.json`、`governance/framework.lock.yaml` 记录版本和文件摘要。

文档解析由统一模块交付 Markdown 阅读稿、结构 JSON、定位、图片及缺口。入库产物位于 `.build/materials/parsed/`，P1 从本轮原字节生成一次，P2—P4 复用，P5 按暂存生命周期清理；不建立跨轮解析档案，不把转换稿重新登记为另一份 raw 来源。图片独立落盘，阅读稿用相对链接引用；OCR 文字和原图共同供 Agent 核对，转换成功不等于图意已经审阅。

## 4. 核心业务协作

```mermaid
flowchart LR
    D["文档与已登记代码"] --> S["内容扫描与关联查询"]
    S --> A["作者决策与写卡"]
    A --> R["固定检查与独立审阅"]
    R --> P["正式卡与来源处理记录"]
    P --> I["双向关系与精确检索索引"]
    I --> Q["检索、精读与回源"]
    Q --> D
```

入库按 P1 选文件、P2 决策、P3 成稿、P4 审阅、P5 入库执行。巡检在同步和扫描后，逐文件复用同一入库链路。内容审阅通过后，P5 依次复制候选、刷新关系与检索索引、登记触发文件的成功版本，最后清理本轮暂存。

入库涉及卡片文件、引用关系和检索索引的顺序更新。只有本次更新全部完成，才登记触发文件的处理版本；中断后保留暂存，在当前步骤修正和重试。逐节点输入、输出及返工规则见[详细设计](知识库详细设计.md)。

## 5. 工作区与数据组织

### 5.1 路径基准

`repo/` 表示 manifest 工作区根，项目入口为 `AGENTS.md` 和 `config.yml`；该根不要求自身是 Git 仓，代码工作区可包含多个实际仓。`knowledge_roots` 和 `code_root` 相对项目配置目录，分别选择知识根和代码根；`modules[].path` 相对 `code_root`，描述允许引用的实际模块。`himate/` 是多个领域知识根的容器。

知识根内的 `config.yml` 和 `AGENTS-code-root.md` 是部署源模板，分别复制为 `repo/config.yml` 和 `repo/AGENTS.md`。部署目标由知识包根的 `../..` 确定，不通过 Git 查找；运行时按项目配置的准确映射选择知识根。

登记代码时，未填写 `repo_id` 的 `path` 相对项目配置目录；填写 `repo_id` 时，相对对应的已配置代码仓。文档路径相对知识根，位于 `docs-raw/`。路径参数详见[来源规范](../governance/specs/sources.md)。

### 5.2 运行位置与组件分发

命令在数据所在执行端的原生目录运行。执行端取得仓库代码、选用已有 Python 3.10—3.12，并配置实际项目和知识根。远端任务由宿主已有 SSH 能力调用同一仓内 CLI。

部署入口、分发源码与工具均位于知识根：`deploy.ps1`、`deploy.sh`、`skills/`、`workflows/` 和 `tools/`。Windows 与 Linux 入口共用 Python 后端，交互展示两个 Skill 安装目录和一个 Workflow 模板目录，回车采用默认值，也可输入自定义路径。

默认将 Skill 同时安装到 `~/.openflow/config/skills` 和 `~/.cac/skills`，将 Workflow 安装到 `~/.openflow/config/workflow-templates`。执行前还收集已有项目入口的覆盖选择，默认 `y`，输入 `n` 保留。确认后依次安装锁定依赖、删除全部本次同名包目录、复制全部新包，再按选择将两个源模板复制到 manifest 根；pip 失败不动旧包或入口，其他包与源文件保留。脚本不下载 Python、不创建虚拟环境、不配置远端 SSH 或注册宿主。

### 5.4 数据生命周期

| 数据 | 生命周期 |
|---|---|
| 原件、正式卡、来源登记 | 随知识库长期维护 |
| `.build/` | 一次文件处理，含解析文字和图片；P1 初始化，P5 成功后清理，失败保留以便同轮重试 |
| `artifacts/knowledge.sqlite` | 可从来源登记和正式卡重建的派生索引 |
| `artifacts/ingest/`、`query/`、`patrol/`、`sources/` | 运行回执、检索和巡检报告、按需恢复副本；按实际使用情况清理 |
| `artifacts/source-read/` | 临时文档阅读使用独立 ID，消费后释放并有界回收过期产物 |
| `artifacts/models/` | 独立准备和维护的解析模型，入库和阅读清理均保留 |
| Python 环境 | 在 `.build` 之外独立准备和维护 |

执行端保留来源登记和正式卡即可重建查询数据库。原件是否能回到某个旧版本，还取决于对应 Git 历史或已保留材料是否可用。

独立回源使用 `source extract`，在 `artifacts/source-read/<read_id>/` 生成材料，可限制 PDF 页范围；它不清理 `.build`，不推进处理 hash。读取结束使用 `source release` 释放指定 ID，长时间阅读可 `source renew`，`source cleanup` 只回收过期且不在转换中的任务。不同读取目录、入库暂存、检索报告和模型目录互不清理。新执行端从原件重新转换；原件缺失时不把缓存视为永久归档。

新任务的运行回执集中在 `artifacts/`，无需独立 `logs/` 目录。项目已有的历史记录、备份及来源引用的证据按原路径保留；`logs/evidence/` 中仍被引用的旧证据不能随缓存清理。

### 5.5 框架更新与目录清理

框架更新替换程序与规则，业务知识更新通过入库流程处理。更新前先完成当前写任务；需要续办的失败任务保留 `.build/`，不要用清空暂存代替重试。

| 内容 | 更新方式 |
|---|---|
| `knowledge/`、`docs-raw/` | 保留正式卡、导航、原件及本机来源映射；由业务变更和入库流程维护 |
| `governance/sources.lock.yaml` | 保留来源身份与成功处理事实，不能用发行包中的空登记覆盖 |
| 项目 `AGENTS.md`、`config.yml` | 部署时分别询问覆盖，默认 `y`；输入 `n` 保留现有文件，内容按实际项目维护 |
| 知识根的 `AGENTS-code-root.md`、`config.yml` | 项目入口源模板，部署后仍保留在知识根 |
| `runtime/`、仓内启动器与检查入口 | 按同一发行版本替换程序文件，运行环境独立维护 |
| `governance/` 中算法、Schema、模板、规则及 `framework.lock.yaml` | 按同一版本更新并保持摘要一致；项目定制规则按需合并，不能整目录删除 |
| `docs-llm-wiki/`、`evals/` | 更新随版本发布的文件，保留本地 SDD、任务和历史工件 |
| 已安装的同名 Skill、Workflow 包 | 由部署脚本完整替换，其他包保留 |

空闲时可清理已消费报告、可重建数据库和 Python/测试工具缓存。`artifacts/` 可能同时存放模型、环境和本机材料，不整目录删除；临时原件阅读使用专用释放与过期回收命令。已有备份和历史证据按项目保留规则单独管理。

## 6. 运行一致性

一个知识根同一时刻执行一条 ingest 或 lint 内容更新链路。P2、P3 在本轮暂存中完成计划和完整候选，P4 独立审阅，P5 使用已审结果发布。只有触发文件完整处理成功后，才更新该文件的成功 hash；引用了同一卡的其他文件按各自任务完成处理。

查询与内容更新可以共存，读取正式库并使用独立搜索报告，不接触 `.build`。CLI 的数据库刷新和检索使用常规 SQLite 短事务协调；遇到正在落位或重建的命令时短暂等待，完成后再读取。正式卡及来源登记使用单文件原子替换，文件与数据库更新仍按顺序完成。

已完整阅读但没有知识增量，也可以登记为处理完成。缺少必要依据时保留缺口，等待补充后处理。索引维护负责重建派生数据，来源内容版本由对应文件的入库任务推进。

周期巡检提供持续对齐：先处理原件和已引用代码的变化，再刷新需要维护的索引，最后报告实际剩余事项。处理频率由使用环境按知识变化速度和成本设置。

## 7. 知识使用与权限

检索以完整正式卡为单位，采用精确词项、显式标签和退役筛选，不按 Claim 用途或复杂条件资格过滤。结果附卡片入口和来源关系，供 Agent 精读并回到原文或实现。评分只表示相关性；知识是否适用于当前问题，由正文条件、版本和实际依据决定。

不同群组分别管理知识根、可引用代码范围及执行环境，并通过实际存储权限和运行账户控制访问。原件、卡片、数据库、缓存和记录应处于一致的访问边界；标签与检索条件用于选择内容范围。

日常部署与 OpenFlow 操作见[使用说明](使用说明.md)，环境配置和手动命令见[运维与命令参考](运维与命令参考.md)，来源格式及适用条件原则见[知识库关键点](知识库关键点.md)。
