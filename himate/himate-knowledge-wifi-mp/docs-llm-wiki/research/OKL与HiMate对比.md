# OKL 与 HiMate 知识库实现对比

本文以 [OKL 调研](OKL调研.md) 和 [HiMate 知识库架构设计](../../knowledge_graph/FactumCore/himate/himate-knowledge-wifi-mp/docs-llm-wiki/HiMate知识库架构设计.md) 为依据，对比两套知识库在同类功能上的实现差异、目录与架构管理差异，以及各自做得更好的部分。

对比基线为 OKL `0.2.1` 与 HiMate 工具包 `0.24.6`。两者都是"把材料沉淀为可追溯知识、供 Agent 消费"的系统，但知识来源的侧重不同：OKL 以**源码逆向**为主，HiMate 以**文档原件**为主。

## 1. 总体定位对比

| 维度 | OKL | HiMate |
|---|---|---|
| 主要知识来源 | 源码仓库（ingest / deep-analysis / update） | 设计文档、规格、PDF/DOCX/XLSX 原件 |
| 知识形态 | 主题页（Markdown + Obsidian 双链） | 知识卡（Markdown 卡头 + 正文 + 引用项） |
| 管理边界 | 单个 `{kbRoot}`，跨系统靠 `catalog.yaml` 编排 | 单个知识根，跨领域靠多知识根分别绑定 |
| 编排载体 | `okl-fsm` 通用状态机 + YAML pipeline | OpenFlow Workflow + Skill 节点 |
| 机械动作 | `okl` CLI | `knowledge` CLI（Python） |
| 一致性保障 | pipeline gate + lint 归零 | P4 独立审阅 + 来源 hash + 发布视图版本 |
| 人机界面 | React 知识库工作台 | OpenFlow 知识库工作台 |

一句话概括差异：**OKL 是"代码事实优先的逆向建库系统"，HiMate 是"原件优先的文档知识卡系统"。**

## 2. 同类功能的实现差异

### 2.1 入库（OKL `okl-ingest` vs HiMate P1–P5）

| 对比项 | OKL | HiMate |
|---|---|---|
| 处理单元 | 一个代码目录 / 一个 repo | 一份来源文档（PDF/DOCX/XLSX/Markdown） |
| 流程形态 | 单次 pipeline 多阶段顺序执行 | P1–P5 逐批循环，每批围绕一个来源 |
| 阶段推进 | `okl pipeline next` 取指令，`pipeline done` 提交 | Workflow 节点交接，节点间可回退 |
| 产物粒度 | 页面（overview/architecture/flows 等） | 知识卡（一文档可出多卡，一卡可融多源） |
| 是否先建广度 | 是，terrain 先出 overview/architecture | 否，按来源逐份推进 |
| 深度处理 | 内置 deep-dive 阶段，产出流程六件套 | 无对应深挖链路，深度靠作者评估 |
| 幂等性 | 未变源码重跑产生等价笔记，已有内容合并 | 以 SHA-256 判变，未变文件不再处理 |
| 失败处理 | gate 不通过则同阶段重试 | P5 失败保留 `.build/` 同批重试 |
| 分批能力 | 无（整目录一次性扫描） | 有，长文档按连续阅读单元分批，P5 登记本批覆盖 |

**核心差异**：OKL 的 ingest 是"一次扫描、广度优先、层层加深"；HiMate 的 ingest 是"逐份来源、分批推进、每批必审"。前者适合快速建立整仓认知，后者适合大文档（几百页 PDF）可控地啃完。

### 2.2 外部材料处理（OKL `okl-forward` vs HiMate 原件入库）

| 对比项 | OKL `okl-forward` | HiMate 入库 |
|---|---|---|
| 定位 | 把外部材料提炼成 Topic，融入或新建 `external/` 页 | 原件直接保存为 `docs-raw/`，再提炼为卡 |
| 原件是否保留 | 不保留原件，只留提炼产物与 review-report | 保留完整原件，卡片只存结论与引用 |
| 中间产物 | bundle → source-split → fragment-distill → topic-compose | `.build/` 暂存本批材料、计划与候选 |
| 与实现知识对齐 | 有 reconcile 阶段，主动与逆向页对齐 | 无显式对齐阶段，靠作者判断知识归属 |
| 冲突处理 | 一个精确规则只设一个主维护位置 | 一卡可融合多源，冲突在 P4 审阅时核对 |
| 可续办性 | `forward inspect-report` 校验并恢复 bundle | `.build/` 保留，失败可按原批重试 |

**核心差异**：OKL 把外部材料"消化掉"，只留结构化结论；HiMate 把原件当一等资产长期保留，卡片是原件的提炼视图。前者知识更紧凑，后者可回溯性更强。

### 2.3 深度分析（OKL `okl-deep-analysis` vs HiMate 无对应）

OKL 独有的一条链路：针对单个函数、算法或业务流做逐阶段源码追踪，固定产出六件套（调用树、主干流程、分支主题、跨边界数据流、数据结构、自查报告）。不适用成员也必须生成并标 `confidence: low`，不允许静默省略。

HiMate 没有等价的深挖链路。它的"深"体现在文档分批阅读的完整性（P1 准备完整转换稿、P5 登记覆盖），而非对代码调用链的逐层剖析。

**这是两者最明显的功能缺口差异**：OKL 面向"这个函数到底怎么跑的"，HiMate 面向"这份文档说了什么、依据在哪"。

### 2.4 查询消费（OKL `okl-query` vs HiMate 检索）

| 对比项 | OKL | HiMate |
|---|---|---|
| 检索对象 | 主题页 | 完整知识卡 |
| 检索方式 | 路由表选 `primary_route`，`okl search` 定位锚点 | 精确词项 + 显式标签 + 退役筛选 |
| 关系扩展 | `links` / `backlinks` / `expand` 沿双链扩散 | 按卡查全部来源、按文件查关联卡（SQLite） |
| 是否回源 | 证据不足或冲突时读源码核验，源码优先 | 按来源登记打开原件，核对页码/行段/符号 |
| 输出约束 | 必带 `confidence`、`source_lookup_performed`、`kb_evidence` | 结果附卡片入口与来源关系，评分只表相关性 |
| 索引形态 | 文件系统 + 双链，无独立数据库 | `knowledge.sqlite` 派生索引，可从正式卡重建 |
| 跨库查询 | Skill 读 `catalog.yaml` 切换 `kbRoot` 编排 | 不同知识根分别绑定，不跨根编排 |

**核心差异**：OKL 靠**双链拓扑**做关系扩散，是"图式检索"；HiMate 靠**数据库关系表**做精确关联，是"索引式检索"。前者更适合探索式理解，后者更适合精确定位。

### 2.5 增量更新（OKL `okl-update` vs HiMate 巡检/重入库）

| 对比项 | OKL `okl-update` | HiMate 巡检 |
|---|---|---|
| 触发方式 | 用户显式发起维护请求 | 外部调度器或维护者启动 L1–L4 |
| 变更判定 | 按变更类型映射受影响页面 | 文件 SHA-256 与最近成功 hash 比较 |
| 范围控制 | impact-analysis 锁定影响面，只刷受影响页 | L2 扫描原件与已引用代码，选中待办来源 |
| 外部知识更新 | 模式 B：提取主张 → 全库检索承载页 → 定点合并 | 复用 P1–P5 重新处理来源 |
| 索引维护 | 无独立索引，靠 lint 保证链接完整 | L3 专门从正式卡重建关系与检索索引 |
| 收尾 | 按 Skill 要求执行 lint | L4 汇总剩余事项与阻塞 |

**核心差异**：OKL 的 update 是"从变更出发推导影响面"，属于**影响分析驱动**；HiMate 的巡检是"从来源出发扫描待办"，属于**覆盖度驱动**。前者省算力但要先判断变更类型，后者更机械可靠但会重复触碰未变内容（有 hash 兜底）。

### 2.6 健康治理（OKL `okl-lint` vs HiMate lint）

| 对比项 | OKL | HiMate |
|---|---|---|
| 目标 | 链接、frontmatter、模板、组合规则、命名、来源 | 原件变化、已引用代码变化、未完成范围 |
| 自动修复 | `lint --fix` 自动修复，再逐项人工修复 | 无自动修复，转为重新入库 |
| 完成判据 | `issueCount == 0`，不接受 warning 或下降即止 | 所选来源无待办 |
| 检查对象 | 知识页结构完整性 | 知识时效性（来源是否变了） |
| 并行度 | 多库可并行，单库写入串行 | 单知识根同一时刻只跑一条更新链路 |

**核心差异**：OKL 的 lint 是**结构治理**（页面写得对不对、链得通不通）；HiMate 的 lint 是**时效治理**（知识是否还对得上原件）。两者解决的是不同问题，理想状态是两者都要。

## 3. 目录与架构管理差异

### 3.1 工程侧架构

| 对比项 | OKL | HiMate |
|---|---|---|
| 代码组织 | `skills/` + `agents/` + `assets/` + `scripts/` + `src/web/` 单仓 | `himate-skills/` + `himate-tools/` 双独立包 |
| 流程定义 | YAML pipeline（9 条） | Workflow 模板（节点/角色/交接/出口） |
| 运行时资源 | `~/.okl/assets/`，升级全量覆盖 | `runtime/` + `runtime/governance/`，按发行版本替换 |
| 版本一致性 | 资源可定制，重装覆盖 | `manifest.json` + `framework.lock.yaml` 记录摘要 |
| 技能分发 | npm 包内 `assets/` 回退 | `deploy.ps1` / `deploy.sh` 复制到 `~/.openflow/config/skills` |
| 语言栈 | Node.js | Python（标准库后端 + pip 锁定依赖） |

**关键差异**：OKL 把流程定义、模板、gate 全部当作可热替换的运行时资源，装一次就能改；HiMate 把工具包与能力包拆成两个独立仓库，分别部署、分别版本化，边界更清晰但安装链更长。

### 3.2 知识库产物架构

```text
OKL:                                  HiMate:
knowledge/                            <知识根>/
├── index.md                          ├── AGENTS.md / config.yml
├── log.md                            ├── docs-raw/           原件
├── global/                           ├── knowledge/          正式卡 + 导航
│   ├── use-cases/                    ├── governance/
│   ├── domains/                      │   └── sources.lock.yaml
│   ├── contracts/                    ├── .build/             本批暂存
│   └── architecture/                 └── artifacts/
├── repos/{repo}/                         ├── knowledge.sqlite
│   ├── overview.md / architecture.md     ├── ingest/parsed/
│   ├── api-surface.md / data-models.md   ├── query/ / patrol/
│   ├── candidate-flow.md                 └── source-read/
│   ├── usecases/
│   ├── submodules/{topic}/
│   └── flows/{topic}/   六件套
├── external/
└── test/
```

**架构哲学差异**：

- OKL 是**按视图分层**：global（跨仓）→ repos（单仓）→ external（独立知识）→ test（测试知识），层与层之间有明确的双链方向。知识页按主题组织而非按文件组织，目录本身就是知识模型。
- HiMate 是**按资产类型分层**：docs-raw（原件）→ knowledge（卡片）→ governance（来源登记）→ artifacts（派生）。目录不表达知识分类，分类由卡头字段和导航维护。

前者"目录即模型"，后者"目录即存储"。OKL 的结构约束更强（模板、五视图、双链规则），HiMate 的存储更宽松（一卡可融多源、七类主题靠导航组织）。

### 3.3 数据生命周期差异

| 数据 | OKL | HiMate |
|---|---|---|
| 正式知识 | 长期维护，增量演进 | 长期维护，增量演进 |
| 原件 | 不保留（forward 只留提炼产物） | `docs-raw/` 长期保留 |
| 中间产物 | `.okl/forward-work/`、`~/.okl/update-runs/` | `.build/`（P5 成功后清理） |
| 派生索引 | 无（双链即索引） | `knowledge.sqlite`（可重建） |
| 缓存 | 无解析缓存概念 | `artifacts/ingest/parsed/`（按版本复用） |
| 覆盖度记录 | `candidate-flow.md` 登记流程与深挖进度 | `sources.lock.yaml` 登记处理覆盖与 hash |

**关键差异**：HiMate 明确区分"持久资产"与"派生资产"，并声明派生资产全部可重建；OKL 没有独立派生层，文件系统本身就是唯一真相源。前者容灾路径清晰（删了能重建），后者更简单（没有一致性同步问题）。

## 4. 功能覆盖矩阵

| 能力 | OKL | HiMate | 说明 |
|---|---|---|---|
| 源码逆向建库 | ✅ 完整 | ❌ | OKL 核心能力 |
| 文档原件入库 | ✅ forward（不留原件） | ✅ 完整（留原件） | 侧重不同 |
| 代码深挖六件套 | ✅ | ❌ | OKL 独有 |
| 跨仓知识综合 | ✅ global-synthesis | ❌ | OKL 独有 |
| 大文档分批处理 | ❌ | ✅ | HiMate 独有 |
| PDF/DOCX/OCR 解析 | ❌ | ✅ Docling/OCR | HiMate 独有 |
| 知识卡引用定位 | 页面级 sources | 页码/行段/函数级 | HiMate 更细 |
| 双链关系网络 | ✅ 强制 | ❌ 无 | OKL 独有 |
| 数据库关系索引 | ❌ | ✅ SQLite | HiMate 独有 |
| 结构 lint 自动修复 | ✅ | ❌ | OKL 独有 |
| 时效 lint（来源变更） | 部分（sources 检查） | ✅ 完整 | HiMate 更强 |
| 发布视图版本控制 | 无明确机制 | ✅ `view_revision` | HiMate 独有 |
| 人机共享工作台 | ✅ React | ✅ OpenFlow | 各有实现 |
| 多知识库并行 | ✅ 多库并行 lint | 单根串行 | OKL 更适合多库 |
| 离线模型依赖 | 无 | 8 个模型约 416MB | 部署成本差异 |

## 5. OKL 做得好的地方

1. **状态机与业务彻底分离**。pipeline 只描述阶段、依赖、产物与 gate，Skill 只描述业务意图，流程规则不散落在多个 Skill 里。新增一条链路只需加 YAML + 阶段指令，不改引擎。
2. **双链即索引**。没有独立数据库，也就没有"索引与正文不一致"的问题；`links` / `backlinks` / `expand` 直接把关系网络变成检索能力，适合探索式理解。
3. **强制结构约束**。模板、五视图目录、`path:func()` 证据格式、双链唯一解析、新页必须有入链，这些硬约束让知识库长期不会腐化成"一堆散文件"。
4. **深挖链路完整**。六件套 + 不适用也要标 `confidence: low` 的规则，保证深挖不留暗角，这是纯文档系统做不到的。
5. **多知识库并行治理**。多库可并行 lint、单库写入串行，适合一个团队维护多个系统库。
6. **零外部模型依赖**。不需要 OCR/解析模型，安装即用，部署成本远低于 HiMate。

## 6. HiMate 做得好的地方

1. **原件与卡片分离**。原件完整保留、卡片只存结论与引用，任何结论都能回到原文页码/行段核对，可追溯性比 OKL 的页面级 sources 更强。
2. **大文档分批可控**。P1–P5 逐批推进、P5 登记本批覆盖、全篇完成才更新成功 hash，几百页 PDF 也能稳定啃完，不会因为一次失败前功尽弃。
3. **派生资产可重建**。明确区分持久资产与派生索引，`knowledge.sqlite` 删了能从正式卡重建，容灾路径清晰。
4. **版本一致性机制**。`view_revision` 保证一次查询/翻页/精读看到同一版本视图，避免读到半更新状态；OKL 没有等价的发布视图版本控制。
5. **时效治理完整**。巡检直接比对原件与已引用代码的 hash，能发现"知识卡还对，但来源已经变了"，这是 OKL lint 覆盖不到的。
6. **独立审阅强制化**。P4 是流程节点而非建议，作者与审阅者分离，事实核对有制度保障；OKL 的审阅更多依赖 Skill 约定。
7. **能力包与工具包解耦**。Skill/Workflow 与 CLI/运行时分别版本化，升级工具不影响能力定义，边界比 OKL 的单仓更清晰。

## 7. 结论

两套系统解决的是同一件事的两端：**OKL 擅长"从代码里长出知识"，HiMate 擅长"从文档里提炼知识并保证可回溯"。**

- 如果目标是快速理解一个陌生代码仓、建立跨仓系统认知、做影响面分析，OKL 的广度优先 + 深挖六件套 + 双链网络更合适。
- 如果目标是消化大量设计文档/规格/PDF、要求每条结论都能回到原文核对、并且需要长期跟踪来源变化，HiMate 的原件保留 + 分批推进 + 时效巡检更合适。

可互相借鉴的点：

- OKL 可借鉴 HiMate 的**原件保留与引用定位**，让 `external/` 页也能回到原始材料的具体位置。
- OKL 可借鉴 HiMate 的**发布视图版本控制**，避免查询读到正在写入的中间状态。
- HiMate 可借鉴 OKL 的**深挖链路**，为关键代码入口补一层调用树与数据流分析。
- HiMate 可借鉴 OKL 的**结构 lint 自动修复**，把断链、模板缺失这类机械问题自动清掉，减少重入库。
- HiMate 可借鉴 OKL 的**状态机与业务分离**，把 Workflow 中重复的流程约束收敛到统一定义。

## 8. 对 HiMate 的需求建议

以下三条需求来自第 7 章的借鉴点，按可验收的方式组织。参考实现引用自 [OKL 调研](OKL调研.md)。

### HM-REQ-01 为关键代码入口增加深挖链路

**优先级**：P2

**背景与现状**：HiMate 的知识来源以文档原件为主，代码只作为"已引用代码"参与时效巡检。当一份文档只给出模块级描述、而使用者需要知道某个函数实际怎么跑时，当前只能靠 Agent 临时读码，结论不沉淀、不可复用。

**需求描述**：作为需要定位实现细节的 Agent，我希望对知识卡中已引用的关键代码入口发起一次深挖，产出结构化的调用关系与数据流知识，以便后续同类问题可以直接查知识卡而不是每次重读源码。

**验收标准**：

1. 可从一张知识卡的代码引用项发起深挖，指定入口符号与所属模块。
2. 深挖产物固定包含调用树、主干流程、分支主题、跨边界数据流、数据结构、自查报告六份，缺任一份视为未完成。
3. 某类产物不适用时，仍生成该文件并标注 `confidence: low` 与不适用原因，不允许静默省略。
4. 深挖产物作为知识卡或独立知识条目发布，可被检索命中，并保留与入口符号的引用关系。
5. 深挖过程中读取的源码版本可回溯，源码变更后能被巡检识别为待更新。

**参考实现**：OKL 的 `okl-deep-analysis` 针对单个函数、算法或业务流做逐阶段源码追踪，"默认连续执行到全部生成，不跳过、不提前结束"；"六件产物固定为 `调用树.md`、`主干流程.md`、`分支主题.md`、`跨边界数据流.md`、`数据结构.md`、`自查报告.md`。不适用成员也必须生成，标 `confidence: low` 并注明不适用，不静默省略。"

### HM-REQ-02 增加结构 lint 自动修复

**优先级**：P2

**背景与现状**：HiMate 的 lint 解决的是时效问题（原件与已引用代码是否变化），结构问题（断链、卡头字段缺失、模板章节缺失）没有自动修复手段，只能靠重新入库或人工改卡。重新入库成本高，且可能引入新的内容变更。

**需求描述**：作为知识库维护者，我希望 lint 能自动修复机械性结构问题，并在修复后给出可判定的剩余问题数，以便把人工精力集中在内容判断上。

**验收标准**：

1. 提供自动修复模式，覆盖断链、卡头必填字段缺失、模板章节缺失、文件名不合规、引用项格式错误等机械问题。
2. 自动修复只改结构，不改动卡片正文的语义内容；无法安全修复的项保留并计入剩余问题。
3. 修复后输出剩余问题清单，每项包含文件、位置、问题类型与建议动作。
4. 提供复检模式，对修复结果重新检查并给出剩余问题数。
5. 完成判据是剩余问题数为 `0`；仅剩 warning、问题数下降或部分自动修复成功都不算完成。
6. 自动修复可限定范围（单个知识根、单类检查），且不触碰 `.build/` 中的进行中批次。

**参考实现**：OKL 的 `okl-lint` "对目标知识库执行自动修复、逐项修复和复检闭环，只有最终 `issueCount` 为 `0` 才算完成"，检查覆盖 `links`、`frontmatter`、`template`、`composite`、`filename`、`sources` 六类；并明确"不得因为 `ok` 为 `true`、只剩 warning、CLI 已部分自动修复或 issue 数下降而提前结束"。

### HM-REQ-03 收敛 Workflow 中重复的流程约束

**优先级**：P3

**背景与现状**：HiMate 的流程规则分散在 Workflow 节点定义、各 Skill 正文和 CLI 契约中。同一约束（例如"P5 成功后清理 `.build/`"、"分批文档只有全篇完成才更新成功 hash"）在多个位置重复表述，修改时需要多处同步，容易出现节点定义与实际 Skill 行为不一致。

**需求描述**：作为流程维护者，我希望阶段顺序、依赖、产物与出口校验只在一处定义，Skill 只描述本步骤的业务目标、材料与质量要求，以便修改流程时不需要逐份改 Skill。

**验收标准**：

1. 阶段顺序、依赖关系、产物路径与出口校验集中在一份可校验的定义中，Skill 正文不再重复描述这些内容。
2. 新增一个阶段只需修改该定义并补充对应的阶段说明，不需要修改已有 Skill。
3. 定义变更后可执行一致性校验，能发现"Skill 引用了不存在的阶段/产物"或"定义中的阶段没有对应说明"。
4. 现有 P1–P5 与 L1–L4 链路迁移后行为不变，可通过回归验证。
5. 校验失败时给出具体的不一致项，而不是只返回整体失败。

**参考实现**：OKL 的做法是"pipeline 只描述阶段、依赖、产物与 gate，Skill 只描述业务意图与质量约束，避免流程规则散落在多个 Skill 中"；并规定"Skill 只描述业务意图与约束，不重复实现状态机。所有使用 pipeline 的 Skill 必须通过 skill tool 调用 `okl-fsm`，通用状态流转、produce/scaffold 与 gate 处理只在 `okl-fsm` 中定义"。
