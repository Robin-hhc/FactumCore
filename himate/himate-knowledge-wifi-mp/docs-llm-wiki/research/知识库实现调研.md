# LLM Wiki 实现调研

## 一、LLM Wiki 是什么

LLM Wiki 是让 AI 持续整理和维护的一套知识页面。比如，一份设计提案说所有消息最多重试三次，后来的发布说明说只有关键消息可以重试、最多两次。问答助手可以在每次提问时临时翻两份原件。LLM Wiki 会先把这两份资料编进同一个“重试规则”页面，讲清哪条已经生效、哪条仅是历史提案，并链接两份原件。下次有人问，直接从整理过的页面开始查。以后规则再变，继续更新这张页面。Karpathy 把这种做法概括为先整理知识，再持续维护。[Karpathy 原文](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

基本结构只有三样：**原件**是证据，AI 可以读，原样保留。**Wiki 页面**是整理后的知识，按主题编写，可以互相跳转。**维护规则**告诉 AI 何时更新旧页、怎样处理冲突、怎样引用和检查。平时做三件事：收到资料就更新页面，回答问题就先读相关页面并回原件核对，定期查过时结论、断链和遗漏。**有没有形成一份可反复使用、以后还能继续更新的主题知识**，是本文选择样本的标准。全文搜索、向量检索和图谱都可以帮忙找页，具体用哪个由实现决定。[原文的架构与操作](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f#architecture)

## 二、把几种实现跑一遍

2026-11-16 在隔离目录试用。Obsidian 加 Agent 是复现原文组合的基准。OpenKnowledge、CANNBot 和 Crow LLM Wiki 都下载到本地并使用了实际入口。OKL 依据你提供的 0.2.2 报告。对照用虚构的 Cedar Relay 重试规则观察“新增证据后，旧认知怎样改变”，另用 CANNBot 的公开知识和 Crow 的合成材料验证各自的使用入口。每个案例只讨论实际试到的行为，或明确标注由文档和源码说明的行为。[试用范围与复核入口](#五试用范围与复核入口)

### 2.1 Obsidian＋Agent：最直接的人机分工

在 Obsidian 中打开一个普通文件夹。文件夹里只有原件时，把第二份原件放进去，Obsidian 已经能搜到它，原来的主题页却仍停在“三次”的提案上。这时由本轮 Agent 按维护规则更新主题页，把“两次”写入现行规则、把“三次”留在历史区，同时更新目录和处理记录。**屏幕上已经打开的同一页面立刻显示了新旧两节**。再从发布说明反查，应用也列出了引用它的主题页和日志。两份原件的字节保持原样。[Obsidian 的文件管理](https://obsidian.md/help/data-storage) · [查找哪些页面引用了当前页](https://obsidian.md/help/plugins/backlinks)

这种组合出彩的地方是**人的阅读界面和 AI 的工作现场是同一份文件**。读者可以从结论点回原件，Agent 改文件时也能当场看结果。判断两个版本谁生效、何时才算改完，取决于交给 Agent 的规则。在这个最小配置里，改完即见，中间没有专门的审阅发布步骤。[Karpathy 的使用方式](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f#the-core-idea)

### 2.2 OpenKnowledge：给“正在研究”和“可以引用”各一个位置

启动本地工作台，给目录套用官方知识库模板。第一份设计提案进入来源区，复述与讨论留在研究区，正式文章区为空。放进发布说明后，Agent 把两份证据的关系补进**同一篇研究稿**，正式区还是空的。试用者明确接受新规则后，按模板的定稿步骤创建正式文章，并把原研究稿标记为已被替代。两篇互相指向，之前的研究稿也还有保存记录。这一轮由 Agent 拟稿、试用者调用产品提供的写入和检查接口完成，能够观察写入、反查和历史记录。[官方知识库模板与定稿步骤](https://github.com/inkeep/open-knowledge/blob/v0.89.7/docs/content/workflows/karpathy-llm-wiki.mdx#L175-L220) · [产品接口](https://openknowledge.ai/docs/reference/mcp)

它的特色是**给不成熟的结论一个可以继续讨论的地方**。旧假设、证据和定稿都在，读者能理解结论为什么变了。有一个实际细节很重要：用默认搜索查相同主题时，已被替代的稿子排第一，正式文章排第二。该稿里的状态和取代链接需要由读者或 Agent 判断，不能直接取第一个结果作答。此次调用的默认检查显示没有链接问题，结论本身仍由审阅者判断。[编辑活动与历史](https://openknowledge.ai/docs/features/agent-activity) · [检索方式](https://openknowledge.ai/docs/reference/agentic-search)

### 2.3 CANNBot：先弄清适用于哪块硬件，再读接口细节

按消费模式安装后，直接查公开库的 Ascend C 接口。把范围限定为 A2 平台和算子接口，搜索 DataCopyPad，仍然找到两张同名卡：一张讲如何把数据从全局内存送入芯片内缓冲区，另一张讲反方向。打开第一张才知道，文中一项紧凑模式仍只适用于另外两款芯片，填充值又要再看一张关联卡。**筛选负责把人带到候选页面，单个条件到底适不适用，要看正文。** 这比把所有同名接口混在一个答案里更适合工程任务。[实际打开的接口页](https://gitcode.com/cann/cannbot-knowledge/blob/92dc260756e91e72e6dcd60f3996a4d54f43c8f5/knowledge/ops/ascendc/apis/simd_api/basic_api/memory_vector_compute/data_move/data_copy_pad_gm_to_ub.md#L1-L52) · [查询方式](https://gitcode.com/cann/cannbot-knowledge/blob/92dc260756e91e72e6dcd60f3996a4d54f43c8f5/.agents/skills/knowledge-query/references/cli.md#L11-L69)

贡献模式的试用把发布边界也看清了。缺少来源的正式卡被拒绝，同一内容可以作为草稿写进去。新草稿一入库，索引还是旧的，查询会明确报错。同步目录、检查草稿并重建索引后，默认查询仍然找不到这张卡，只有显式查对应平台的草稿才命中。CANNBot 还有面向不同证据的生产方法，例如从 Agent 的开发记录中提炼排障经验。试用中转换了两份合成记录，工具显示“仍失败”和 Agent 声称“已修复”被保存在不同记录里。合成试验能证明这两类证据被保留下来，真实排障知识仍要按流程复核后再发布。[入库规则](https://gitcode.com/cann/cannbot-knowledge/blob/92dc260756e91e72e6dcd60f3996a4d54f43c8f5/.agents/skills/knowledge-ingest/SKILL.md#L8-L62) · [开发记录处理](https://gitcode.com/cann/cannbot-knowledge/blob/92dc260756e91e72e6dcd60f3996a4d54f43c8f5/.agents/skills/model-knowledge-trace-ingest/SKILL.md#L9-L23)

### 2.4 Crow LLM Wiki：把分资料和写正文交给两个模型

给它一个资料目录，运行同步。用实际本地模型试用的经典模式，会在每次同步时检查原件有没有变化。试用中把同一份设备策略的重试次数从三次改到五次，同步后留下了两个有关联的页面和两份原件快照。再同步一次未改动的目录，没有调用模型。这个做法适合由固定目录持续提供新资料，避免每轮重读所有原件。[项目的目录同步说明](https://github.com/crow-hq/llm-wiki-v2/blob/436fcd148f9e876d222d4d7b52f44e2e4ab18295/README.md#L315-L340)

经典模式里，试用的小模型把设备策略放进人事分区。直接搜索能找到两页，问答却没沿目录找到它们，页面检查也没报错。改正分区名字后，问答还有一次没读到页面。明确提示它读哪份说明之后，才答对并附引用。**一份页面写出来、搜索能找到、问答确实会读到，是三件事。**

再用它的双模型模式跑同一批资料。这次先定义了设备策略等分区，由专门做选择的模型判断资料进哪个目录、该不该与旧页合并，生成模型负责写正文。运行记录显示新版仍然独立成页，但这次直接提问，系统选了两个版本来读，答出当前五次、历史三次，并附上两条引用。这个设计让“分错位置”“漏读旧文”“写错结论”可以分开查。两次试用的目录条件也不同，无法将结果差异单独归因于双模型。[两种模式的分工](https://github.com/crow-hq/llm-wiki-v2/blob/436fcd148f9e876d222d4d7b52f44e2e4ab18295/docs/wiki/crow.md#who-decides-what)

### 2.5 OKL：让知识出现在开发者要做决定的那一步

按 0.2.2 报告，OKL 把工程资料整理成四个视角：用户怎样用、系统按什么规则工作、代码怎样实现、运行中怎样操作和排障。Agent 收到问题后先判断该看哪个视角，再通过索引页找知识。遇到需要多份知识库的问题，由 Agent 的查询规则负责在各库之间找，底层工具一次处理一库。它适合把同一个工程从不同角度讲清楚，像“这个故障应怎么绕开”和“这个接口要满足什么条件”，可以从不同入口找到对应知识。[OKL 调研报告第 3、5、6 节](OKL调研.md)

最值得看的做法是**把“先查已有知识”写进设计开发流程**。报告里的实践要求开发者在指定节点先查库，未命中可以换一种方式重试，再失败就记录缺口。生产端也把切分、主题合成、覆盖检查和关联收口排成明确的步骤。上游检查失败时，下游的完成确认会撤销，这样就知道要从哪里再做。部分检查依赖作者自报，因此“流程走完”与“结论经独立核实”仍是两项不同的证据。报告基于静态阅读，安装和完整入库待实测。[OKL 调研报告第 5、7、10 节](OKL调研.md)

## 三、用同一份材料看 HiMate 的取舍

用相同的 Cedar Relay 材料跑了两轮 HiMate 工具。第一轮发布设计提案。第二份资料放进知识库后，扫描能找到这份新增资料，但它刚进库时还没有卡片引用它。作者查出它和原提案属于同一主题，更新原有卡片，由另一 Agent 核对。**候选通过固定检查时，读者仍然读到第一轮已发布的内容。** 提交后，原卡以同一身份发布新版本。测试再拿旧的发布编号读取，接口明确提示刷新。两条引用分别解析到各自原件的第 3 行，能看出一条是提案，另一条是发布说明。已证明的是这条本地发布链的行为，OpenFlow 界面和生产调度属于另一层验证。[入库与审阅](../HiMate知识库详细设计.md#21-完整流程与节点判断) · [正式视图](../HiMate知识库详细设计.md#41-openflow-正式知识视图) · [引用回源](../HiMate知识库详细设计.md#57-来源恢复与定位)

这显示出 HiMate 的优势**在于控制哪条结论何时可以给其他人用，并且留得下复核依据**。和 Obsidian＋Agent 相比，它多了一道发布边界。和 OpenKnowledge 相比，正式查询有专门的已发布版本入口，所以调用方可以明确只读已发布结果。和 CANNBot 相比，两者都重视工程证据，CANNBot 的平台筛选和专用知识生产更细。HiMate 的取舍是让不同格式的资料遵循同一路径更新正式卡，并把文档页段和已引用源码的版本纳入巡检。和 OKL 相比，OKL 更关注在设计任务的哪一步强制用知识，HiMate 更关注相应卡片变了多少、哪份依据支撑哪条结论。当前巡检能跟踪已登记、已引用的源码，新增资料涉及哪些已有主题仍要由作者判断。[HiMate 巡检与适用范围](../HiMate知识库详细设计.md#31-lint-的检查流程)

## 四、这几种设计分别解决什么问题

| 真实问题 | 试用中看到的办法 |
|---|---|
| Agent 改完内容，我想马上翻过去看 | Obsidian 直接显示同一份文件，并能从原件反查引用它的页面 |
| 团队还在讨论，我想保留推理过程，最后再定稿 | OpenKnowledge 给研究和正式文章各留位置，用取代链接把过程串起来 |
| 同一接口在不同硬件、不同方向上有不同语义 | CANNBot 先按工程条件缩小范围，再通过卡片与关联页核对适用细节 |
| 资料目录每天更新，我想避免重复处理 | Crow 识别未变的原件，双模型模式可分别查看归类和写作是怎么做的 |
| 开始设计时总有人忘了查积累下来的经验 | OKL 的报告把查库和未命中后的处理写进开发流程 |
| 我需要知道别人此刻读的是哪一版，引用是否还能找回来 | HiMate 独立审阅后发布同一版卡与关系，能从正式卡按版本和位置核对证据 |

试用里最能说明差异的一步，是给已有页面补进一份相反的新证据。只查文件数量或链接是否有效，发现不了旧稿排在新稿前面，也发现不了问答漏读了已经写好的页面。检验一套 Wiki 时，应同时看**旧结论有没有被正确标为历史、读者从默认入口会读到什么、以及能不能沿引用找到它为什么变了**。

| 实现与版本 | 实际操作与可复核结果 |

| [Obsidian 1.15.1](https://github.com/obsidianmd/obsidian-releases/releases/tag/v1.15.1) | 本地启动，应用内打开主题页，通过其命令读取、搜索并检查引用关系。同一窗口观测更新，无需重开文件。Agent 更新前后核对原件摘要 |

| [Crow LLM Wiki 1.0.2](https://github.com/crow-hq/llm-wiki-v2/releases/tag/v1.0.2) | 用本地 Qwen3-1.7B 跑经典模式，再接本地 Laya 分类模型跑双模型模式。两轮均验证目录同步、改版、搜索、问答和页面检查 |
| [OKL 0.2.2](OKL调研.md) | 依据你提供的源码和指南分析报告，无新增运行试验 |
| HiMate 工具包 0.22.3 | 隔离知识根中跑扫描、候选检查、独立内容审阅、发布、两版读取和引用原件解析 |

这些小样例用于查清产品怎么运转，语料、模型和操作方式也有差异。准确率、维护成本和大批资料处理能力仍需同条件实验。RAGFlow 的 Wiki 编译功能另有下载核对，本机缺少它所需的容器运行环境，因此未列为实跑案例。
