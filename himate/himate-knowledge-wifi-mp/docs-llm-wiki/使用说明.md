# HiMate 使用说明

首次部署使用分发仓根的 `deploy.ps1`，将配套 Skill、Workflow 与知识库放到选择的位置，操作见[首次环境安装](#2-首次环境安装)。接入时保留业务仓已有的 `AGENTS.md`，按 `AGENTS.md.example` 合并 `main/`、`config.yml`、知识根及设计文档四项说明和日常业务入口，不覆盖原有业务内容；没有真实入口时再按示例补全，未知部分保留大纲与 `...`。本开发仓的根 `AGENTS.md` 仅本地维护，分发文件为 `AGENTS.md.example`。下文 `K` 指实际 `config.yml` 解析出的知识根；新项目默认 `repo/himate/himate-knowledge-wifi-mp/`，已有安全配置继续沿用。

使用顺序：**按需部署 → 在实际执行端准备环境并运行 doctor → 首次配置执行端dbox目录 → 按任务选择入库、检查或查询**。按任务直接使用对应Workflow或Skill，实际命令由知识根自带的 CLI 执行；不必查找或上传 Skill 脚本。已有知识可直接查询；独立检查使用 lint，增量治理启动同名 lint Workflow。读取已发布旧证据不要求生产者的私人目录仍可用。

## 1. 项目配置与执行位置

Workflow首节点复用已有项目和执行端；缺少时从当前工作区实际AGENTS.md及config.yml取得知识根，必要信息不明确或多候选时询问用户。进入实际知识根后，Windows使用.\knowledge.cmd，POSIX使用sh ./knowledge.sh；下文Python命令也以该目录为工作目录。

### 1.1 项目配置

| 文件 | 位置与用途 |
|---|---|
| `config.yml` | 位于实际代码仓根目录，由项目维护者手工维护并上库，使用者沿用仓内配置。 |

项目配置只维护仓根的 `config.yml`，按真实工作区填写 `code_root`、`modules` 和 `knowledge_roots.wifi`，路径基准见[知识库关键点](知识库关键点.md#11-路径基准)。

dbox目录另由K内的 `docs-raw/sources/dbox.local.yml` 保存，仅有 `schema_version: '1.0'` 和一个绝对 `path`。它不合并到共享项目配置，也不参与团队来源身份或共享config_digest。模板 `dbox.example.yml` 与同目录 `.gitignore` 上库，本机文件精确忽略；一个执行端使用一个资料根，不需要账户或目录登记表。

### 1.2 远端执行：先配置 OpenFlow SSH MCP

目标代码仓在服务器上时，用户或部署维护者须先在 OpenFlow 中配置并启用 SSH MCP，使本次任务所用 Agent 能调用远端命令工具，再执行实际业务任务。Windows 部署脚本通过所选路径直接复制和解压，不使用 SSH；同机执行可跳过本节。

1. 在 OpenFlow 的 **MCP Hub → `ssh-mcp-server` → 配置** 中勾选“启用 SSH MCP”，填写目标主机、端口、用户名，以及密码或私钥等认证信息；私钥文件路径须能由运行 OpenFlow 的机器访问，加密私钥另填私钥密码。点击“测试连接”确认结果后保存。已有连接可复用。连接信息和凭据由宿主管理，知识库项目不另设 SSH 配置文件。
2. 在需要远端执行的 AI 角色中启用 `ssh-mcp-server`，确认本次任务使用的 Agent 可以调用它；ingest 的 `coder`、`reviewer` 都要能访问各自执行步骤所需的远端工具。仅保存连接设置还不代表任务内已可调用。
3. 通过该 MCP 做一次只读验证：用 `ssh_get_capabilities` 检查远端环境，确认实际服务器、登录身份和远端项目根，读取项目 `AGENTS.md`、`config.yml` 和知识根入口；在服务器原生 K 运行 `python3 knowledge.py doctor --json`，核对该端 Python 与依赖。连接测试成功仍须核对运行环境，路径使用服务器原生路径，不能直接套用调用端路径。
4. 连接、认证、权限或工具可见性有缺口时，先在 OpenFlow／执行端完成配置或部署，再继续任务。后续通过 `ssh_exec` 在服务器原生 K 调用仓内 CLI 并检查结果；实现已随知识仓分发，无需逐次上传 Skill 脚本。Git 操作仍在实际项目根执行。

OpenFlow 的具体配置入口与字段以所用版本为准。部署脚本不修改 SSH MCP、角色工具权限或其他宿主开关，也不核验服务器 Python；实际任务前另行检查远端运行环境。旧 `setup.py` 仅保留显式诊断与兼容用途。

Windows 通过 Samba 映射盘启动本机 Python 时，扫描仍由 Windows 经网络逐文件读取；改用 CLI 名称本身不会消除这些开销。数据位于服务器时，由宿主 SSH 在数据所在端运行同一 CLI。CLI 不内置 SSH 客户端，也不猜测映射盘对应的主机或原生路径。

### 1.3 运行依赖

| 依赖 | 在哪里准备与核对 |
|---|---|
| 配套 Skill／Workflow 与仓内运行包 | 使用下节部署脚本安装 12 个 Skill 指引、两个 Workflow 与知识根的 CLI/runtime/规则，核对 OpenFlow 加载结果；实际执行端只需访问 K，不依赖 Agent 的 Skill 脚本目录。 |
| SSH MCP（远端项目） | 用户或部署维护者在 OpenFlow 配置、启用并完成上节验证；本机项目不依赖 SSH。 |
| Python 与依赖 | 每个执行端准备 Python 3.10–3.12 及 `K/runtime/requirements.lock.txt` 中的精确依赖。部署脚本只检查调用机；缺包修复须交互确认或显式 `-InstallDependencies`。服务器可由维护者在选定解释器执行 `python3 -m pip install --user --only-binary=:all: -r repo/himate/himate-knowledge-wifi-mp/runtime/requirements.lock.txt`；已准备的专用环境使用其解释器和对应安装方式，不跨 Windows/Linux 共用虚拟环境。日常命令不自动安装或联网。 |
| CodeGraph CLI／MCP（代码图谱任务） | 首次配置代码仓建图时，源码所在端须有可用 CLI；需要图谱查询时，宿主须提供可调用的 CodeGraph MCP。具体步骤见下节；图谱缺项保留诊断，不代表源码或知识结论已验证。 |

SSH MCP 配置完成只说明远端执行通道可用。运行包准备、项目入口读取、Workflow 加载、角色工具可见性和实际业务结果仍分别核对。

## 2. 首次环境安装

在 Windows 打开包含本项目分发源码和根 `deploy.ps1` 的目录，执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy.ps1
```

脚本交互询问三条路径，回车采用默认值：

| 询问项 | 默认值与含义 |
|---|---|
| Skill 安装根 | 采用脚本显示的 Agent Skill 默认目录或实际自定义目录，各 `hs-knowledge-*` 指引包直接放在其下 |
| Workflow 模板根 | 采用脚本显示的 OpenFlow 模板默认目录或实际自定义目录，两个 Workflow 模板直接放在其下 |
| 知识项目根 | 选择实际 `repo/`，指含 `config.yml` 的项目根，不是知识根本身；已有配置按 `knowledge_roots.wifi` 定位 K，没有配置时默认其下的 `himate/himate-knowledge-wifi-mp/` |

这些值是部署脚本的产品默认值，可按实际位置修改。共享路径示意仍用 `repo/`。已有 `config.yml` 与真实根 `AGENTS.md` 保留，按实际业务仓检查配置和合并入口说明；脚本不根据占位配置创建虚构业务源码。`himate/` 只是领域知识容器，`config.yml`、`main/` 仍在项目根；已有旧平铺或自定义多级知识根不会因升级自动搬迁。

脚本查找本机已有 Python 3.10–3.12；找不到时提示安装或用 `-Python` 指定实际解释器，不自动下载。默认检查该解释器的配套运行锁，依赖已齐直接复用；缺失或版本不符时，交互模式询问是否安装，非交互模式须显式加 `-InstallDependencies`。依赖修复和部署使用同一个解释器。

| 参数 | 用途 |
|---|---|
| `-SkillsRoot`、`-WorkflowsRoot`、`-ProjectRoot` | 显式指定三条目标路径 |
| `-Python` | 指定本机实际 Python 可执行文件 |
| `-Plan` | 只读预检；依赖可用时列出部署计划，缺项时报告，不安装依赖或写入目标；不能与 `-InstallDependencies` 同用 |
| `-NonInteractive` | 使用显式路径或默认值，不询问输入；缺包时仍需明确授权修复 |
| `-InstallDependencies` | 显式允许在所选解释器修复缺失或版本不符的运行包 |

例如先按默认位置只看计划：

```powershell
powershell -ExecutionPolicy Bypass -File .\deploy.ps1 -Plan
```

部署在本机临时生成 Skill、Workflow、知识三份 ZIP。Skill 包分发指引与契约文本；知识 ZIP 包含仓内启动器、完整 runtime 和治理框架，整体复制到所选项目根内本次暂存位置，再由 Windows 直接在目标路径解压，逐文件回读 SHA-256 核对落盘字节。目标为映射共享盘时仍有小文件写入开销，这不代表服务器本地解压，部署也不通过 SSH 检查或安装服务器 Python。

首次部署和后续升级使用同一条命令。受管 Skill／Workflow 包按新版精确同步，删除不再分发的包内文件、子目录和退役包，包内手工增加的文件也会清除；不会清空 OpenFlow 共用安装根或删除其他能力。两个安装根各保存 `.factum-knowledge-deploy.json`，仅记录上次安装包名，用于后续清退；不参与业务运行或机器绑定。无清单的旧部署按本版包与明确的历史包名单接管；未知包即使同前缀也保留，并在 `unmanaged_packages` 列出。清单损坏时停止，不猜测所有权。

| 更新范围 | 处理方式 |
|---|---|
| 受管 Skill／Workflow 包、`K/governance/{contracts,schemas,specs,templates}/` | 精确同步框架，移除旧文件和空目录；规则与 `framework.lock.yaml` 成套更新 |
| `K/runtime/`、`K/knowledge.py`、`K/knowledge.cmd`、`K/knowledge.sh` | 成套更新仓内执行实现、manifest、依赖锁与启动器；旧 Skill 脚本不再分发，不删除执行端已准备的外部 Python 环境 |
| 共享设计、入口与检查脚本 | 按明确文件清单更新；保留其他文档及本机 `sdd/`、`task.md` |
| `K/docs-raw/`、`K/knowledge/`、各级导航 | 保留原件、附件、卡片与导航；初始骨架只在缺失时补齐，dbox 空模板按分发更新 |
| `K/logs/`、`K/.build/`、`K/artifacts/` | 保留历史处理／发布／证据、未完事务、稳定写锁、巡检基线、索引与查询回执；升级不做业务数据清理 |
| 项目 `config.yml`、真实根 `AGENTS.md`、来源锁与 dbox 私人配置 | 保留原字节；dbox 忽略文件只追加精确项 |

升级前可运行 `-Plan` 核对文件更新、删除和目录移除计划；JSON 中 `write_count`、`delete_count`、`remove_directory_count` 无变化时均为 0。受控失败会尝试恢复已更新／删除文件和空目录；恢复冲突时保留备份并报告失败，部署不是整目录原子切换。

部署前停用正在使用这些能力的宿主任务，结束同一项目的业务写入，不要从多台机器同时部署到同一目标。部署不带开发机运行缓存、测试产物或历史 SDD，不修改宿主 SSH／MCP／权限开关。完成后重启 OpenFlow，核对十二个 Skill 与两个 Workflow 是否在列表中，再用新任务验证实际调用；已创建的 Workflow 副本不自动升级。远端任务继续按[SSH MCP 与执行端环境](#12-远端执行先配置-openflow-ssh-mcp)核对。

部署仅分发dbox空模板和精确ignore规则，保留已有local地址及自定义ignore；JSON中的 `source_setup.status: pending_execution_host`、`configuration_checked: false` 表示尚待真正执行端完成来源配置。`deployed`只说明文件部署完成，不表示dbox目录可用；下一步见下节。已有已验证配置不因再次部署而改写。

日常已有部署、可用依赖和项目上下文时直接使用仓内命令或 Workflow，入口不明确时先读当前工作区实际AGENTS.md/config.yml，必要时询问用户；不会自动运行 pip 或远端 setup。显式 setup 兼容实现保存在 `runtime/himate_knowledge/stages/explore/setup.py`，不作为常规业务前置。

升级前，如有已知未完成的写事务，先按原配套工具、规则和明确事务引用处理，再安装完整十二个Skill及匹配规则；普通新入库不会代替用户搜索或恢复旧执行。扫描／备料统一使用`hs-knowledge-source`，默认`run`执行正常扫描后备料，显式`prepare`保留独立及返工用途，不做兄弟CLI转发。旧包不再是活动入口，历史工具身份、原规则摘要及引用不迁移、不重签。change-plan的旧字节请求及`verify/rederive`不再生产或复验写集，字节输入交view-materialize，内容审阅交lint。

CodeGraph 初始化仍由 Agent 按任务与项目上下文使用源码所在端已有 CLI 逐仓执行，部署脚本不安装 CodeGraph 或建图。Agent只处理config.yml已配置的真实模块：先运行codegraph status，缺少本目录索引时再运行codegraph init并复核；保留排除范围，跳过非必要Git hook或额外集成，不强制重建。Agent只处理已配置的真实代码仓，空 `modules` 列表不扫描或初始化整个 `main/`；跨机器时通过 OpenFlow／宿主已有 SSH MCP 在源码所在端执行。执行端缺少 CLI 时报告缺项。CodeGraph MCP 由宿主／harness 提供，是否可用按实际接入核对。

代码来源的符号导航使用配套运行锁内的 C/C++ 解析依赖，和 CodeGraph 图谱分别准备。日常 query、lint 或巡检不会因为卡里声明 code_ref 就自动安装工具或建立图谱；执行端缺依赖时保留实际 unavailable，由部署维护者按该端环境补齐，Windows 本机部署结果不能代替该检查。固定检查可供 CI 复用，但文档与本机通过不表示已经配置远端受保护门禁。

### 2.1 首次配置 dbox 资料目录

首次来源准备必须在实际运行ingest的机器调用仓内 `source configure`，填写一个现有可读目录。SSH任务在服务器执行；Windows本地地址或映射盘可读，不能证明服务器能访问。这里的配置是普通YAML目录映射，不创建原生软链接，也不连接dbox API。

在本机独立配置请求中填写下列JSON，将 `ACTUAL_DBOX_DIRECTORY` 换成执行端原生绝对目录，`operation_id` 每次使用独立值：

```json
{"operation_id":"configure-dbox-unique","path":"ACTUAL_DBOX_DIRECTORY"}
```

在 K 调用仓内入口；下例使用跨平台 Python 形式，已注册命令时可直接用 `knowledge`：

```text
python knowledge.py source configure --input REQUEST.json --json
```

成功会在 `K/docs-raw/sources/dbox.local.yml` 保存下列格式，`path`为实际填写值；空模板不能当成来源已配置：

```yaml
schema_version: '1.0'
path: 'ACTUAL_DBOX_DIRECTORY'
```

`configure`只检查根目录能否读取，不递归文件、不读取资料正文。无path只检查现有配置；显式同地址保留原字节；显式新地址在验证后单独修改，不需重装能力。字段、版本、目录或Git忽略保护有误，或者写入前配置已被他人修改，都保留原配置并报告具体缺项。local已受Git跟踪时不会自动删除索引或提交；非Git工作区可配置，但不声称忽略已验证。根与内部路径不跟随软链接/junction，资料目录不能包含知识根，避免扫描自己的输出。

后续默认全量扫描包括六类仓内原件与dbox。dbox目录内文件使用逻辑地址 `docs-raw/sources/dbox/<相对路径>`，可按该前缀指定子目录或文件；显式仅扫描原六类raw时不检查无关dbox。未配置、根不可读或子树读失败会明确报告不完整，不能当成无变化或整目录删除。来源就绪、扫描完整、内容已入库分别以实际结果判断，日常不隐式重复configure或setup。

### 2.2 仓内命令入口与诊断

知识根 K 自带 `knowledge.py`、`knowledge.cmd`、`knowledge.sh` 和完整 `runtime/`。默认布局从项目根先进入 `himate/himate-knowledge-wifi-mp/`；已有项目先按 `config.yml` 确认 K。Windows 在 K 运行 `.\knowledge.cmd doctor --json`，POSIX 运行 `sh ./knowledge.sh doctor --json`；也可用准备好的解释器执行 `python knowledge.py doctor --json`。`HIMATE_KNOWLEDGE_PYTHON` 可指定已准备的解释器；Windows 启动器未指定时优先尝试 `py -3.11`，再尝试 `py -3.12`、`py -3.10` 及兼容的 `python`，POSIX 使用 `python3`。路径含空格时按当前 shell 正常引用。doctor只读核对当前主机、解释器、运行manifest／依赖、治理锁版本与登记规则字节，以及最近config.yml是否确切映射本K；缺项明确阻断，不执行未验证治理程序、不扫描main/modules或原件／卡片，也不安装或创建索引。

需要直接输入裸 `knowledge` 时，在每个实际执行端显式注册一次轻量命令：

```text
python knowledge.py install-command --json
```

Windows 需要同时写入用户 PATH 时显式加 `--add-path`，之后打开新终端；POSIX 将返回的命令目录加入自己的 PATH。可用 `--bin-dir` 指定本机命令目录，已有同名文件保留并报告，不自动覆盖。注册器从当前目录向上寻找 K，不把某个项目或权限组固定为全局默认；应在目标 K 或其子目录使用。它不进入知识 Git，也不提供业务初始化或模型服务。无需注册时继续使用仓内相对启动器即可。

注册后的常用命令如下；未注册时将 `knowledge` 换成对应相对启动器或 `python knowledge.py`：

```text
knowledge doctor --json
knowledge query "认证 超时" --purpose guidance --json
knowledge read CARD_ID --receipt RECEIPT_REF --json
knowledge source scan --source docs-raw/specs/ --json
knowledge source run --source docs-raw/specs/ --json
knowledge review --input REVIEW_REQUEST.json --json
knowledge record --input RECORD_REQUEST.json --json
knowledge lint --json
knowledge patrol sync --input SYNC_REQUEST.json --json
knowledge patrol plan --json
knowledge status OPERATION_ID --json
knowledge apply --action batch --input BATCH_REQUEST.json --json
```

`read` 使用上次搜索实际返回的 `receipt_ref` 和 `card_id`。普通背景查询可明确选择 `guidance`；当前／实现查询沿原资格要求核对范围和实际依据。`review`消费确切候选和实际审阅输入，复用原lint.review；独立正式库检查仍使用`knowledge lint`。`record`消费本次`operation_id`和`view_ref`，生成待发布记录；不代替P2判断或P6发布。`source run` 只完成扫描及备料，`patrol plan` 只完成差异筛选；需要 Agent 判断、成稿或独立审阅时，按实际引用交给对应 Skill／Workflow。CLI 不调用 LLM，不提供自动完成 P1—P6 的 `knowledge ingest`，也不能把 `knowledge lint` 当成自动修订工作流。

阶段命令及独立record命令均支持复杂 JSON：`knowledge STAGE --action ACTION --input REQUEST.json --output RESPONSE.json --json`，`--input -` 从 stdin 读 JSON。省略操作 ID 时自动分配；不必填写 K、规则摘要或默认请求／结果路径。原始 JSON 与简短参数同时给出且内容冲突时直接报错。`--input` 与显式 `--output` 的相对路径按执行端当前目录解释；`source`、卡、材料和 receipt 等业务引用仍相对 K。跨目录直接调用 K 内启动器也锚定该 K，显式选择另一 K 时重新启动其入口，不混用运行包。

默认请求和结果位于 `.build/operations/<操作>/cli/`，按原阶段归属与 P6 清理规则处理。`--json` 的 stdout 只输出一个对象，包含真实阶段状态、诊断及 `cli_transport`；其中 `request_ref`、`result_ref` 是实际传输位置，`stage_result_digest` 对应结果文件原摘要。CLI 显示对象加入传输信息后另算摘要，不改结果文件、旧报告或历史记录。实际退出码保留原阶段语义，lint 的 0／1／2 与普通阶段的 blocked 不合并成成功。

运行实现由 `runtime/manifest.json` 固定，依赖由 `runtime/requirements.lock.txt` 固定；治理规则继续由 `governance/framework.lock.yaml` 固定。新结果保留逻辑 Skill 名并声明 `executor: knowledge-cli` 和真实运行包摘要，不冒充旧安装包。同步可能更新 CLI、规则和配置，`patrol sync` 后必须新起命令进程再执行 `patrol plan`。旧 journal、receipt 和已发布依据按原版本验证，升级不迁移或重签，未完旧事务沿原入口与停点恢复。

显式移动已有知识根时，先处理真实未完事务并保全历史资产，再由维护者同步实际目录和项目 `config.yml`、Git 路径规则及 CI 路径；在每个执行端进入新 K 运行 doctor。新开始的操作使用新配置，旧 journal、receipt 和正式引用保留原字节；原有绝对路径或运行绑定须逐项核对，不靠批量替换修复。已有通用裸命令在新 K 核对可用性，缺项时按 install-command 的实际诊断处理；部署不自动修改本机命令注册、PATH 或远端路径。

首次引入或升级时，仓库维护者须按部署清单评审并提交三个入口与 `runtime/` 的配套变更，服务器才能通过 Git 同步取得完整执行副本；Git 提交与本地部署、ingest 完成分别处理。本机 Python 环境及注册命令仍留在各自执行端。

命令返回的 `request_ref`、`result_ref` 相对 `cli_transport.knowledge_root`；`--input`、`--output` 是 shell 文件参数，相对当前工作目录。跨目录调用复杂请求时，使用确切绝对路径或先进入 K；请求内部的来源、稿件和回执引用仍按对应契约解释。

<a id="1-三个常用命令"></a>

## 3. 日常使用

| 任务 | 类型与使用方式 | 适用情况 |
|---|---|---|
| `ingest` | Workflow：通过 OpenFlow 运行 `hs-knowledge-ingest`。 | 原件入库、增量更新或明确修订已有知识；指定某次执行时可按其停点续办。 |
| `review` | Skill：向 Agent 提出检查要求，指定 `hs-knowledge-review`。 | 独立只读检查正式库或明确候选，获得实际问题报告。 |
| `query` | Skill：向 Agent 提问，指定 `hs-knowledge-query`。 | 检索知识、精读同代内容与来源，并追查实际代码。 |

巡检来源／代码变化并处理待办时，在 OpenFlow 中运行 `hs-knowledge-lint` Workflow；独立审阅与只读检查使用 `hs-knowledge-review` Skill，两者按职责分别命名。

ingest 已包含 P4 审阅与质量检查、P6 索引与检索验证；独立 lint 和 query 按需使用。公开能力为 12 个 Skill；Workflow 为 ingest 和治理 lint 两条，不是同名终端命令。

<a id="2-加入文档后怎么入库"></a>

### ingest：通过 OpenFlow 执行入库 Workflow

1. 将原件放入知识根六类仓内目录，或放入[已配置的dbox资料目录](#21-首次配置-dbox-资料目录)。六类分别为`conventions/`（约定）、`chips/`（芯片）、`storys/`（需求）、`specs/`（规格与设计）、`protocols/`（协议）或`troubleshooting/`（问题定位与排查经验）；dbox不必先复制整个资料目录到代码仓。
2. 确认 OpenFlow 已加载 `hs-knowledge-ingest` Workflow，12 个配套 Skill 及 `coder`、`reviewer` 角色已接入，然后在 OpenFlow 中选择并运行该 Workflow。
3. 查看 Workflow 返回的处理范围、知识更新、检查与查询结果。需要继续本次执行时，保留操作标识和返回引用，按实际停点及材料缺口处理。

设计文档含代码分析时仍走同一ingest：提炼关键结论，保留原文版本与段落，并按需要关联配置代码仓中的实际函数和流程，不把源码搬进docs-raw。作者识别必要代码后回P1定向备料，脚本同时固定本批文件与项目上下文，P4独立核对文档分析及源码。纯文档结论只需文档依据；涉及实现行为的结论另需代码依据，同卡可混合，两者不是不同上传入口或卡片目录。仅有函数名或设计要求不证明代码已实现。

每次新启动Workflow使用新操作，首节点`prepare_sources`调用source默认`run`：先由脚本从当前原件、正式处理记录和维护限制生成扫描清单，有待办再同进程备料，返回`prepared`和真实`scan_ref/material_ref`。仅完整且没有待办、维护限制、缺口或明确修订目标时返回`unchanged`，不生成材料或记录；不能把读失败、不完整扫描或空待办数组单独当作无变化。Agent只传范围／目标并消费引用，不重写扫描清单、指纹、分类或完整性。流程不搜索旧私有操作，原件未变但明确要求改卡仍可备料。

历史用途卡保留其确切旧依据。旧证据仍可恢复时，当前源码升级不会单独制造该历史 Claim 的修订待办；原件真实变化、旧证据缺失或明确的语义／适用性问题仍需处理。

日常ingest按P1—P6六个OpenFlow节点执行，P1在同一节点内完成扫描与备料。下表按节点说明职责。Skill名省略`hs-knowledge-`前缀；P4由独立reviewer执行，其余节点为coder，隔离由宿主安排。

| 节点 | Skill／动作 | 输入与本职结果 |
|---|---|---|
| P1 观察与备料 | source默认`run`；独立`scan`／`prepare` | 脚本对照当前原件、正式记录和必要来源／代码状态保存真实待办清单，再按待办或明确目标准备新旧原文、附件、旧卡、代码／配置、差异与缺口；不读旧执行材料，返工直接prepare。 |
| P2 决定内容 | change-plan／`plan` | 作者阅读材料，固定逐单元处置、卡与旧 Claim 去向、记录动作和本批查询预期；按实际Claim选择用途和上下文，正向用例建议绑定预期Claim。 |
| P3 保存稿件 | view-materialize／`run` 或 `revise` | 组织作者提供的卡稿、导航、来源锁、写删集合、处置预览和输入快照；只保存候选，不改正式库。 |
| P4 审阅与检查 | lint／`review` | 独立阅读计划、完整稿件及证据，审内容、归卡、实质 skip 和适用代码依据；无内容阻断后，同次执行一次完整固定检查，并在已全验临时索引上执行原冻结查询和精读。 |
| P5 转写记录 | record（`knowledge record`） | 机械复制计划及处置预览中已定的动作、卡／Claim 引用和欠账，保存待入库记录，不重新决定内容。 |
| P6 发布与收尾 | apply／`batch` | 核实际输入和写入安全，发布并核验已审内容及必要依据后，保存正式成功记录；再验证索引、执行本批预定查询和同代精读、按原基线启用，最后清理本批可删暂存。 |

P2／P3／P4缺材料返回首节点时，明确调用source的`prepare`，不先执行默认`run`或重扫；作者判断或归卡有误仍回P2，稿件问题仍回P3。已有冻结稿时，返工使用新`operation_id`，显式带原`previous_view_ref`、真实`revision_reason`及旧稿精确绑定的`existing_material_ref`和补充目标，只补缺口；缺口可保留后交P2决定处置。仍有效的原扫描和单元身份不变，旧工件不覆盖、不重签，新稿重新交P4。采用的原文、旧卡、代码、配置或规则漂移时留首节点说明停点，按变化对象刷新所需输入；`affected_scope`是诊断路径，不能全当raw的`source`参数，也不无限自动刷新。纯环境故障留节点等待。P2计划已冻结但P3尚无可采用view时，补料产生新材料不代表旧计划可以改用新摘要；遇不可变绑定阻断保留真实停点，不伪造前序view或覆盖计划。

查询用途以实际Claim为准：设计背景通常选 `guidance`，`current` 还要求 `usage: current` 和适用范围匹配，`implementation` 另需实现／测量依据；代码链接只提供定位。正向新增／修改结论建议填写已有的 `expected_claim_ids`，负向用例保留自己的排除或空结果断言。P4报告中 `check_id: index.build` 的 `candidate_queries` 保存逐例预期与实际结果；`TARGET_QUERY_EXPECTATION_FAILED` 阻断并回P2重判，必需输入不可用则保持未完成及真实诊断。P4不查旧活动索引冒充候选、不发布正式卡或激活索引；独立正式lint／CI不要求这份私人计划，仅记录批不运行内容查询。

P3核对稿件生产所需的一致性，P4承担知识质量和代码语义复核。P6检查输入快照、原版本、路径、写锁、并发基线、备份和实际回读，不重复P4完整质量判断，也不凭一张通过报告放行。内容发布成功后，还要完成本批适用的索引、查询、启用和清理，整批才算完成。仅记录批保留跳过、暂缓、失败或未覆盖事项，不夹带失败稿件，不建索引；记录成功不表示欠账已解决。

#### 进度、续办和完成判断

询问某次进度时，给source的只读 `status` 动作明确 `target_operation_id`。已发布操作优先读取 `logs/publications/<操作>/` 下的正式发布清单与完成结果；尚未发布的操作只检查自己的固定停点和确切引用，不在全库拼接报告。省略目标则是明确查看全局历史，可能列出其他旧操作和损坏记录。两种查询都不执行恢复，也不重新验证当前索引健康。

正式发布清单说明当时发布了什么，完成结果说明当时的检索收尾与清理到了哪里。历史完成事实不等于当前规则、来源或索引仍然适用；当前检查有缺口时须保留，不能凭旧成功记录获得当前使用资格。需要核对当前落盘内容时使用 `verify-result` 的默认当前用途；指定 `purpose: historical` 只核历史内容事实，不授予当前提交资格。

中断或响应不明时，只有明确继续这次执行，才检查原执行端进程及该操作的实际停点。正式结果优先，不要求已清理的旧稿仍存在。已发布的内容不重复写入，只补确实缺失的索引、查询、启用或清理，保留最初的 `expected_active`，包括真实的 null。内容批返回 `completed`、仅记录批返回 `recorded`，且 `batch_complete: true` 时，才表示该批适用收尾完成；事务 `committed` 只表示内容事务已落位。

旧 `run` 事务使用配套版本和原恢复入口，不改投 `batch` 重放。真实未完成写事务仍受写入保护，不能靠删目录绕过。罕见的P6部分写入不承诺自动修复，应保留现场按实际诊断处理。内容已入库但有误时，用新操作修订，保留原事实。宿主、SSH和进程故障按真实执行端情况处理，不据此改卡或自建运行工具。

只处理部分材料时，向 Workflow 提供来源范围，例如 `docs-raw/troubleshooting/`；修订已有知识时，提供目标卡片和修改要求，原件未变也可修订。问题定位经验可按模块建立子目录，材料宜写清现象、环境与触发条件、排查过程、根因或当前判断、解决方法和验证结果，保留未解决、未验证部分。

显式给出的来源路径不存在且没有已知删除历史时，扫描会明确报告范围不存在，先核对路径；默认六类原件目录为空仍是有效扫描，已登记原件被删除则按历史来源的缺失处理，不自动删知识卡。

#### 暂存、正式资产与换机

P1—P5在知识根内新产生的本批请求、输出、原文与附件副本、提取定位、旧卡、代码及构建／运行核验副本，都保存在 `.build/operations/<操作>/`。来源变化也先形成待发布事项，不提前登记正式事件；正式卡、导航、来源锁、处理记录、事件和索引保持不变。P3/P4固定将要发布的路径与完整字节，P6按已审内容发布，不临时重生成另一份。

P6核验内容后，正式处理记录写入 `logs/ingest/`，发布清单与后续完成结果写入 `logs/publications/<操作>/`，必要依据保留在 `logs/evidence/published/`。这些文件支持清理后的回源、状态观察与提交核对。处理记录区分“看到了哪版原件”和“正式知识接纳了哪版”，执行暂存或事务日志不能代替它。

索引、查询和启用完成后，P6只删除本批清单中确实可删的暂存文件。借用的前序材料、明确保留或用途不明项留下并说明；其他操作、正式依据、当前索引及稳定写锁不删除。不要求 `.build/` 为空，最终命令响应也可能留下一个小文件。删除失败时报告 `cleanup_pending`、`batch_complete: false`，保留内容已发布的事实；再次明确执行该批时只补未完成阶段，不回滚或重写已发布内容。新流程不自动接管或定期清除旧未完成草稿。

ingest完成本地知识更新，Git提交和上库由人后续处理。按本批清单一起检查卡与各级导航、来源锁、采用的 `docs-raw/` 主件及附件、`logs/ingest/` 处理记录、有效的 `logs/events/` 使用限制、正式发布结果和必要依据；被引用旧版须能从Git历史或同组持久位置恢复。不要只提交新卡，或把来源锁仍为空、依据只在原机私有目录中的批次交给别人消费。

本机暂存、事务备份、旧 `logs/operations/` 和派生索引不进入新业务提交，也不随Skill能力包分发；正式发布结果和必要依据按业务清单保存。已有旧格式与正式引用继续按原路径使用，不批量搬迁或重签，也不因新清理机制而整体删除旧证据目录。目录清单见[详细设计 §6.4](知识库详细设计.md#64-哪些内容上库哪些用于本机执行)。

其他用户拉取仓库后，先完成本机能力与依赖准备，取得 `config.yml` 声明的真实代码及被采用的构建／运行材料，再检查正式库和来源。由apply的 `index-build` 构建并完整验证候选代，保留 `generation_ref` 和原 `expected_active`；用 `regression` 执行明确的目标查询与同代精读，通过后按该基线启用本机索引。随后可用query的 `search`、带原 `receipt_ref` 的 `read` 核对内容与回源，再普通扫描确认正式处理结果。消费副本不继承生产端的私有续办义务：正常扫描、lint、查询、回源、提交核对和指定正式操作的状态观察都不需要原机 `.build/`、事务日志或复核稿。本机没有索引时重建本机索引即可。旧版原件或业务材料缺失仍须报告；浅克隆和只复制最新文件不保证历史引用完整。

<a id="lint使用-skill-独立检查"></a>

### review：使用 Skill 独立检查

向 Agent 提出检查要求，同时选择或注明 `hs-knowledge-review` Skill。例如：**“使用 hs-knowledge-review 检查当前知识库。”** 需要限定范围时，一并说明。

独立调用 `knowledge lint` 默认检查正式完整库（formal／full）；候选检查须明确 `mode: candidate` 和确切 `view_ref`，局部检查须明确范围，其结果只说明所选范围。Agent 读取报告的实际状态、完整性和问题位置；退出 0／1／2 分别表示完整无阻断、有阻断、输入或运行不可用。lint 只检查和报告；需要修复时，将问题交回 OpenFlow 的 ingest Workflow 修订后再检查。ingest 的 P4 使用 `knowledge review`，同时承接内容审阅和适用固定检查。

需要持续处理“raw新进来”或“登记代码变了而知识未更新”时，运行已安装的 `hs-knowledge-lint` Workflow。L1由patrol-sync Skill独立同步，随后新CLI重新加载规则，L2由patrol-plan生成待办；L3索引修复和L4完成核验分别使用patrol-reindex与patrol-complete，中间复用入库节点仍保持P1—P6。脚本比较上次成功处理基线、当前 raw 与各子仓Git变更（含未提交修改）；有待办把固定 source_request 直接交 source.prepare，复用 ingest P2—P6，保留独立reviewer。单独使用 review Skill 和 maintain.audit-references 仍只生成检查/引用报告。接口、分类和失败语义见[详细设计 §3.1](知识库详细设计.md#31-lint-的检查流程)。

周期执行由外部系统触发，建议先手动验收再接半日/每日调度。内部根目录同步通过控制端明确的 `sync: {argv: [git, mm, sync, -j8], cwd: <执行端实际 mm 工作区根>, timeout_seconds: 600}` 适配，cwd由执行端用 `git mm --root-dir` 运行时解析，不写死机器路径；未配置时仅检查本地现状；不从文档读取命令，不假设 mm log。确认同步覆盖仓与 config.yml 实际映射一致。JSON/Markdown/库存保留在本机 `logs/patrol/<operation>/`，成功基线在 `.build/runtime/patrol-state.json`；均不提交Git。欠账、读取失败、同步失败、P6或清理未完不推进成功基线。已发布未完返回精确续办引用，应重试原batch，不另起apply重放。真实MM、OpenFlow加载、权限和业务质量须内部验证。

活动卡的每个 code 来源必须有 code_ref，缺失由固定检查报 CODE_REF_REQUIRED；文档背景卡及未被 Claim 采用的来源同样适用。旧活动卡通过 ingest 补齐，历史恢复及 deprecated 卡保留原四字段兼容。固定检查另核旧证据中的符号绑定及当前导航。报告将 code_navigation 和旧定位／字节差异分开：missing／ambiguous 为失败，unavailable 为未完成。guidance 符号仍唯一可定位时，不因普通插行或函数体变化要求重写知识；current 实现依据仍按原规则核对，符号存在不表示结论准确。

<a id="3-怎么查询和追代码"></a>

### query：提问并使用 Skill 检索分析

向 Agent 提出问题，同时选择或注明 `hs-knowledge-query` Skill。例如：**“使用 hs-knowledge-query 分析：<你的问题>。”** 可补充目标芯片、版本或关注范围。

设计背景应明确使用 `purpose: guidance`，省略时默认是 `current`。例如：**“使用 hs-knowledge-query，以 guidance 解释 HWDL 发送流程；问题范围为 chip07c/host，特性条件为 `_PRE_WLAN_FEATURE_HWDL`。”** 这里只示范已明确的问题范围，不是固定配置，也不证明宏已开启；未知范围保留缺口，不抄卡片条件凑命中。

返回空结果时，先核对用途、已有依据的范围及实际诊断，再调整查询词；`guidance` 仍需匹配卡片的范围约束，缺少特性列表不等于通配。当前实现问题不能自动改查背景后当作实现答案。字段、用途边界和请求示例见已安装 `hs-knowledge-query` 包内的 `references/public-api.md`（Search request）。

Agent 使用 `search` 检索正式活动代，取得候选卡摘要、卡片及来源地址；再用原搜索 `receipt_ref` 和 `card_id` 调用 `read`，即使活动代后来变化也精读原来命中的同代合格 Claim 正文。卡片的逻辑 `path` 和确切代内文件 `card_ref` 均相对知识根；逻辑路径已有新版时，原回执及 `card_ref` 仍表示原代。查询以 `source_links` 给出简洁来源地址，原文、源码及原件编码由 Agent 按问题需要另行读取，不嵌入查询结果或新回执。涉及具体实现时，按地址声明的基准及 `config.yml` 模块映射追查所问版本的实际源码，给出结论、实际读过的依据位置和仍不确定的部分；历史／背景知识不直接证明当前实现。已有材料不足时说明缺口，需要补充材料再通过 ingest 入库。

卡头的 sources 项仍保存 evidence_ref/source_id/snapshot_id/locator，Claim.source_refs 关联这些原引用。活动卡的代码项按[卡片规范与示例](../governance/specs/cards.md#代码来源的可选符号补充)填写 code_ref，选择函数、结构／类、枚举／成员、宏、类型别名或文件／namespace 层变量；函数原型须显式 role:declaration，省略时选择定义。纯文档不强制连代码，P4 按实际内容判断必要入口，不新增卡级符号表，也不提供 file／range 兜底。query 内部继续核对来源字节和 code_navigation，对外链接用 `evidence` 标明固定证据、用 `current` 标明当前位置，并保留实际 `navigation_status/current_source_matches`；不返回完整来源解析对象。代码的 current 路径、定位和摘要来自同一次导航的实际文件观察；未读得文件摘要时返回 null，ambiguous 仅可保留已核验的文件地址且不带定位。声明符号仅 resolved 带当前符号行段，原文已变时也不把旧行号套到新文件。对外 current_source_matches 比较该当前文件与固定证据的整文件摘要，无 current 时为 null；内部查询资格核验不变。resolved 仅说明唯一可定位，不能证明活动宏分支、参数含义或当前实现语义。

地址中的 `path` 按自身 `base` 解释：`knowledge_root` 是知识根，`workspace` 是实际项目根，`repository` 由 `repo_id` 映射授权 scope，`git` 另带确切 commit；卡片 `path/card_ref` 均相对知识根。dbox的`current`可用`absolute`给出本次实际核验的执行端文件，允许留在当次响应及私有Receipt，不进入共享资产。切换配置、目录或文件时核对同次观察，不能把新路径配上旧摘要或旧定位；未配置/不可达时current为null，固定已发布证据仍可按原条件读取。不要按目录层级猜项目根，也不要把旧证据当当前代码。PDF 页、DOCX 段落／表格行保持原生定位，必要时按卡头及来源锁使用已有的确切来源恢复能力。原回执的规则绑定、卡片摘要和 Claim 子集检查继续执行；旧展开结果格式的回执按原字节验证，规则升级不自动放行陈旧回执。沿链接回源也不能扩大原查询用途或把未合格的 Claim 当作当前依据。

CodeGraph 可帮助 Agent 找候选及追调用，卡片不保存其内部节点 ID；图谱搜索未命中不直接表示符号不存在。普通背景问题选 guidance，当前实现问题继续读取实际代码并核条件；字段补充不改变用途资格，也不自动触发 ingest。规则升级后按现有 apply 索引动作重建派生索引，不改旧 generation；P6.batch 仍只做安全落位和检索收尾，不重跑 P4 完整质量检查。

来源、同代正文或当前材料不可用时读取真实诊断，先补齐材料或处理运行问题，不据此修改卡片或宣布没有命中。


### 独立备料、恢复、索引与提交核对

下表列出八阶段的独立用途，名称对应仓内子命令。使用 `knowledge STAGE --action ACTION --input REQUEST.json --output RESPONSE.json --json`，也可将动作直接写在阶段名后；K 和规则默认由实际入口确定，复杂请求与 `--knowledge-root`、`--rules-digest`、`--catalog` 仍保留。请求文件／显式结果路径按执行端当前目录解释，业务引用以 K 为基准；不要求 catalog 或上游通过票据。

| Skill | 动作 | 使用边界 |
|---|---|---|
| source | `configure` | 首次在实际执行端填写或校验本机dbox目录；只检查根目录，不递归扫描或入库，操作见[首次配置](#21-首次配置-dbox-资料目录)。 |
| source | 默认`run` | 正常新批次先扫描再按待办备料，读取实际scan_ref/material_ref及prepared／unchanged；重试只复用本op的source-inventory.json固定槽位，原source范围不变，核验后继续失败子步骤，不重扫或覆盖。已保存的无变化清单不能证明当前仍无事，返回FRESH_OBSERVATION_REQUIRED时使用新操作重新观察。 |
| source | `scan` | 只生成脚本观察的真实扫描清单并返回scanned；独立动作不是Workflow必需前驱票据，Agent不能手造清单。 |
| source | `prepare` | 可采用原操作的真实`scan_ref/unit_ids`，也可传明确`targets`、旧卡ID／主题／代码材料独立备料，不伪造扫描或新建交接manifest；补料沿前述新操作和旧稿绑定，不重扫。 |
| source | `capture`、`resolve`、`resolve-source` | 将已落地原件或配置内代码捕获为本批暂存材料、校验指定材料，或恢复指定来源快照及原定位；不提前发布证据或登记正式事件，缺旧版时不以新版替换。 |
| source | `record`、`status` | record机械转写待发布记录；status指定target_operation_id时只读该操作确切引用，不指定时显式查看全局历史。两者不提供前驱通过票据，历史完成不证明当前索引健康。 |
| view-materialize | `describe` | 只读描述已保存的确切候选、来源与基线，不运行内容审阅或质量检查。 |
| lint | `record-review`、`code-check`、`code-recheck`、`verify-evidence` | 分别保存审阅声明、核对逐 Claim 代码依据、复查当前材料或按 current／historical 用途复验已有证据；独立动作不表示完整 P4、CI 或角色认证通过。 |
| apply | `run`（默认）、`inspect`、`resume`、`rollback`、`verify-result` | `run` 保留旧事务完整检查；恢复遵守原日志并保留外部修改。`verify-result` 默认核当前内容、规则及适用输入，`purpose: historical` 仅核历史内容事实。日常ingest显式使用 `batch`。 |
| apply | `index-build`、`index-verify`、`index-activate` | 独立构建并完整验证、复验或启用索引；沿确切 `generation_ref` 和原 `expected_active`。独立启用只证明该次启用，不替代某批冻结查询和完整收尾。 |
| apply | `regression`、`regression-verify` | 传确切代和非空查询预期；`regression` 通过后尝试按原 CAS 启用；`regression-verify` 依据 `report_ref` 重跑原案例，不启用，也不能改代次、案例或基线。 |
| apply | `prepare-submission`、`verify-submission` | 整理本批精确文件与删除清单；后者按明确 `commit_sha` 只读核真实 HEAD、commit／blob、删除和变更范围，不执行 Git 提交／推送／合入。 |
| maintain | `inspect-context`（默认）、`status`、`audit-references` | 分别观察受影响 Claim、读取限制／未完成事件、生成只读引用报告，不自动修订或登记事件。 |
| maintain | `register-source-change`、`register-code-change`、`recover-events`、`advance` | 显式登记来源／代码变化、恢复 pending 事件或复查来源一致性限制；这些动作会写维护状态，不属于只读巡检。 |

未完成维护事件缺少原始内容或确切证据时，保留限制并阻断恢复。`advance` 不能绕过未完成事件，只能在实际卡／Claim、来源和配置满足条件时清除机械的来源一致性限制；语义／适用性限制继续保留。普通捕获只保存材料与变化建议，P6在对应来源版本被正式接纳后发布适用事件；仅记录欠账的批次不提前登记未接纳版本。独立维护确需立即登记来源或代码变化时，显式使用上表维护动作，它们不受ingest前五个节点只写暂存的约束。
