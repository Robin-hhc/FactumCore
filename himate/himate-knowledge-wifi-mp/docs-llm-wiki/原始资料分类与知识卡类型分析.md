# 原始资料分类与知识卡类型分析

调研日期：2026-11-03。本文分析公开 LLM Wiki、CANNBot 与嵌入式知识服务的原始输入、C／驱动 Agent 的资料需求，以及这些来源是否需要对应新增知识卡类型。

## 结论与证据范围

`raw` 表示可追溯的原始输入层，并不限定为 PDF 或设计文档，也不要求所有实现都采用这个目录名。公开实现的输入包括文章、论文、网页、图片、数据、人工记录、对话和代码；生成的来源摘要、主题分析和问答另有归属。

这里的“原始”相对于本次知识提炼流程：团队已有的设计、分析和故障复盘也可以作为来源，前提是作者、版本、依据和结论状态可辨。存入 raw 不会使材料自动成为事实；Agent 新推导的结论也不应通过写回 raw 变成自己的独立证据。

对驱动 Agent，建议准备六部分长期基础资料：目标与版本、硬件、源码与构建配置、架构和接口约束、诊断与验证方法、已验证历史问题。每次任务再补需求或同一次复现的现场证据。关键是能把需求、硬件约束、实际实现、运行观测和验证结果联系起来。

本轮建议保留现有六类 raw 目录与七种知识模板。raw 按原件用途组织，卡片按可复用知识主题组织，两者是多对多关系。CANNBot 有九种机器识别的知识类型，但硬件领域与资料类别没有各自变成同名卡型；具体案例、反模式与基准观测也能共享一个 Profile。对本项目先验证案例／观测正文骨架，并评估任务指南、API／可运行样例和优化方法的组织需求；是否升级为新卡型取决于真实表达与消费缺口，不能照搬外部九型。

公开实现事实来自第一方文档或源码；本项目现状以卡片规范、模板及实际解析／检索代码为依据。本文中的映射和扩展条件是工程建议。本次未安装外部服务、调用其 MCP、测量问答准确率或进行硬件实验；本次交付是分析文档，未变更卡片契约、模板、Schema、运行时或正式知识。

## 区分资料分类与知识形态

| 维度 | 回答的问题 | 示例 |
|---|---|---|
| 来源分类 | 原件是什么，在哪里维护？ | TRM、原理图、接口规范、需求、复盘、日志、实验报告 |
| 知识形态 | Agent 希望理解或执行什么？ | 对象职责、流程、协议、约束、命令、排查、术语 |
| 证据性质 | 这项结论凭什么成立？ | 规范要求、设计声明、静态实现观察、测量结果、建议 |
| 适用条件 | 结论在什么条件下成立？ | 芯片 revision、板卡、Host／Device、代码／固件版本、构建配置 |

来源不同不意味着知识形态不同，证据性质与适用条件也不能由目录或卡型推定。例如 TRM 与故障复盘都可能支持一张资源约束卡；同一份 TRM 也可能形成对象、流程、协议和规则等多个主题。来源多不要求多产卡，按有价值的主题提炼即可。

|---|---|---|---|

| DeepWiki-Open | GitHub、GitLab、Bitbucket 仓库中的源码与可读文件 | 源码直接进入代码索引与 wiki 生成；不要求复制为 raw 文档。文件筛选和大小限制影响覆盖 | [README](https://github.com/AsyncFuncAI/deepwiki-open/blob/main/README.md)、[pipeline](https://github.com/AsyncFuncAI/deepwiki-open/blob/main/api/rag/pipeline.py#L73-L160) |

补充样本 [nvk/llm-wiki](https://github.com/nvk/llm-wiki/blob/master/AGENTS.md#L68-L120) 使用 articles、papers、repos、notes、data，并为大型数据设置 manifest、samples、profiles、queries。它说明原始数据可保留在适合其体积与读取方式的位置，再由清单连接到知识库。

从这些样本可以归纳出原始输入的常见类别：正式规范与文档、外部阅读材料、组织内记录、图片与附件、数据集、代码材料。具体比例随用途变化。代码 wiki 不会自动补出仓库中不存在的芯片勘误、板级连接和故障现场；领域 wiki 的摘要也不能替代对匹配版本源码的读取。

### 核验范围与版本

GitHub 文件按调研日期的 `main`／`master` 核验，链接可能随分支更新。以上输入设计不构成对特定产品生成质量的测评。

RAGFlow 平台流程另核验了 [v1.0.0-rc3 官方说明](https://ragflow.io/docs/v1.0.0-rc3/knowledge_compilation/overview)。其能力不能直接套用到旧版部署。Karpathy 原 gist 为 2026-04-04 创建的模式说明。

三个样本对来源与输出的处理进一步说明两者并非一一对应：

- Karpathy 的 ingest 同时处理来源摘要、实体、概念与交叉引用，一份来源可能影响多页，见原 gist 的 Architecture 与 Operations。
- Microsoft 的 raw 子目录由用户自定义，知识页类型另行定义；[初始化说明](https://github.com/microsoft/llmwiki/blob/main/packages/core/src/init.ts#L43-L49) 包含 entity、concept、source、summary、query，[实际 ingest](https://github.com/microsoft/llmwiki/blob/main/packages/vscode/src/llmIngest.ts#L17-L30) 则把一份来源的输出分为 summary、entities 与 concepts，再分别建页。
- RAGFlow 的 [Wiki mode](https://github.com/infiniflow/ragflow/blob/main/docs/guides/knowledge_compilation/built_in_templates_and_dedicated_configuration.md#L442-L448) 按 Entity 或 Topic 组织页面；实体、关系、事实、概念及章节 Blueprint 是不同配置，不是每增加一种原始文件就增加同名页型。

这些是其他实现的组织事实；本项目是否扩展卡型仍须依据自己的表达、检索和校验缺口。

## CANNBot 的硬件知识与卡型

### 硬件相关性与版本范围

CANNBot 是 CANN 社区的 Agent 层，服务 Ascend C／PyPTO／TileLang／Triton 算子开发、模型迁移与推理优化，并覆盖图模式和 Runtime，见[应用仓说明](https://gitcode.com/cann/cannbot/blob/b520f3e0a7c9f9355378b1943686cd3285d63f19/README.md#L7-L11)。知识仓确实包含 NPU 微架构、片上与外部内存、芯片能力差异、同步、性能和运行故障等硬件相关知识。这使它成为本项目重要的工程知识组织参照；具体芯片能力仍属于昇腾 NPU 场景，不能据此推定其覆盖 WiFi 板级电路、寄存器或驱动全部环节。

本轮从官方 Git 仓读取以下独立快照，未运行安装器或硬件工作流：

| 仓库 | 本轮固定提交 | 角色 |
|---|---|---|
| cannbot-knowledge | `62e2d52276e6b42813027e377a4e8537df55fc80` | 知识卡、来源治理、生产与检索 |
| cannbot | `b520f3e0a7c9f9355378b1943686cd3285d63f19` | 场景插件、工作流及用户入口 |
| cannbot-skills | `ac5de28c41a25bfcd47fef98bcfc96e48b2c9b51` | 可复用技能、参考材料与工具 |

这些快照不是同一发布组合。应用仓的 vendor gitlink 锁在 Skills `c35e9609c758bf605fb7e651b915b8af841626a8`；[源码安装逻辑](https://gitcode.com/cann/cannbot/blob/b520f3e0a7c9f9355378b1943686cd3285d63f19/script/lib/skills-source.js#L55-L119)默认可能选取远端同名分支最新版本，显式指定 SHA／路径时才选择相应来源。本节按所属仓库分别引用，不把独立 HEAD 当作已验证兼容的安装版本。

### 原始资料并非一个 raw 目录

[来源规范](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/governance/specs/frontmatter.md#L146-L163)与[来源 Registry](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/governance/schemas/registries.yaml#L145-L281)定义了不同的原始资料根：

| 原始资料 | CANNBot 落点／治理 | 对本项目的启发 |
|---|---|---|
| 官方 API、开发指南等文档 | ignored 的 `cann-docs-raw/`；获取方式由 Registry 登记 | 原始文档与知识卡分开；大型手册可按需回源 |
| 四类官方算子源码 | `cann-ops-raw/ascendc/<repo>/<commit>/` | 实现知识与固定版本源码相互引用，不复制代码成为另一套 SSOT |
| Runtime 源码 | `cann-runtime-raw/runtime/<commit>/` | 公共运行机制需要对应软件栈源码，不能仅靠硬件手册 |
| 模型与依赖源码 | `cann-recipes-raw/<repo>/<commit>/` | 完整任务也需要集成、依赖和参考工程材料 |
| 开发轨迹与原始观测 | 按专用生产流程提炼；特定 Runbook 可在正文保留触发、探针和验证信号 | 日志、探针和验证属于知识依据，不能只保存整理后的根因结论 |

其版本保证并不一致：Git 来源固定 40 位 commit；官方文档归档明确是滚动来源，不校验归档或内容树 SHA-256。固定知识仓提交因此不等于固定全部 raw 字节。官方 API／Guide 另有受控镜像流程，可保留来源正文并处理链接、章节与导航，见[知识仓指引](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/AGENTS.md#L54-L56)；不能把所有知识生产概括成“每份文档都重新摘要”。

本项目继续使用自身的来源身份、内容 hash 和定位契约。CANNBot 的[轨迹来源例外](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/governance/specs/frontmatter.md#L154-L157)允许特定 Runbook 的 `sources: []`，但要求正文保留观测闭环；这也不改变本项目新卡至少一项 `doc_ref` 的要求。两种证据契约不能混用。

### 九种类型具有机器契约

CANNBot 的[profiles.yaml](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/governance/schemas/profiles.yaml#L11-L57)定义八个公共必选字段 `type/title/description/tags/status/sources/created_at/updated_at`，再按 Profile 增加字段要求。[Profile 检查器](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/governance/contracts/checks/profile.py#L38-L65)实际核对路径与 type 映射、字段组合；九类映射不是仅写在目录说明中，也不是 JSON Schema 的 type 枚举。

分类也有实际消费者：Query 的[`--type` 参数](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/.agents/skills/knowledge-query/references/cli.md#L66)按路径 Profile ID 过滤，例如 `apis`；结果中的 `type` 才是 `API` 等 OKF 类型。本项目当前没有相同的类型过滤契约，因此不能仅增加同名目录就声称获得上游的消费能力。

下表前两列是上游事实，最后一列是本项目的归属建议，并不要求逐一对应：

| CANNBot Profile／type | 主要职责 | 本项目当前可能归属 |
|---|---|---|
| concepts／Concept | 稳定概念、执行与编程模型、对象边界，包含硬件架构知识 | entity；时序与约束可拆 flow／rule |
| apis／API | 签名、语义、参数与使用约束 | entity／protocol／rule；成套 API 参考需求另行评估 |
| examples／Example | 具备输入、输出与验证方式的最小样例 | 样例工程保留原件；解释与用法按 entity／protocol／flow 组织 |
| guides／Guide | 围绕完整开发任务组织原理、步骤、约束和验证入口 | flow 串联相关 entity／rule／command；有必要时试写任务指南骨架 |
| operators／Operator | 完整算子的语义、设计、Tiling、Kernel 与工程职责 | 领域任务聚合；WiFi 模块知识按实际对象与路径组织，不照搬算子类型 |
| optimizations／Optimization | 优化触发条件、收益来源、选择与失效边界 | rule／flow 加明确的测量依据；值得试写专用优化骨架 |
| runbooks／Runbook | 诊断、验证与处置闭环 | runbook |
| interoperability／Interoperability | 两种技术间可复用与必须重新推导的映射 | protocol／rule／flow；迁移／兼容高频任务可试写对照骨架 |
| glossaries／Glossary | 术语、定义与别名 | glossary |

上游[路径职责](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/governance/specs/paths.md#L42-L66)还明确不单设 patterns／migrations，按知识作用分配到现有 Profile。硬件、语言或领域本身也不各自成为同名 type。这支持按知识职责设计类型，但不能证明本项目的七模板已经覆盖所有未来任务。

### 案例与测量不必先新增 type

模型推理的 `optimizations/rules`、`cases`、`anti_patterns`、`benchmark_observations` 共享 `optimizations` 路径 Profile，对应 `type: Optimization`；section 仅用于导航，不进入 Frontmatter。这不只是目录声明，当前有实际卡片：

### TX timeout 的任务上下文示例

这是材料清单示例，不表示已确认当前代码存在某种 TX 实现。

1. 问题定义：谁报告 timeout、从哪个事件计时、阈值、预期完成事件、实际现象和复现步骤。
2. 精确基线：双端源码、运行固件、芯片／板卡、有效配置、测试拓扑和负载。
3. 相关路径：提交、双端传递、排队、完成通知、超时检测、回收与恢复的实际代码入口，以及异步上下文／所有权约定。
4. 同一次复现证据：带时间的双端日志、队列与完成计数、相关抓包／dump。注明时钟关系与 packet／message／descriptor 的关联方法；无法关联时保留缺口。
5. 对应条款：本路径相关硬件寄存器、描述符、固件协议、errata。
6. 正常对照：相同条件下的正常记录，或明确只变化一个因素的版本／配置对照。
7. 验证方法：超时是否消失、数据是否完成、资源是否回收、恢复是否有效，以及适当的重复／压力测试。

此时 Agent 应有条件区分“尚未提交、传递失败、排队阻塞、完成通知缺失、计时或回收错误”等待验证假设。已有计数与 trace 的具体含义仍须读取项目实现，不能从名称推定。

上述目录表示材料职责；文件可按主用途放一处，再交叉引用。当前[架构设计](HiMate知识库架构设计.md)已区分原件、来源登记、知识卡、解析缓存、索引与回执，不需要为本次调研另造一套目录。`storys` 沿用现有路径名称，本分析不进行目录重命名。

运行现场首先保存在适合的持久证据位置；需要长期维护的故障报告再引用这些原始附件。不要把全部临时运行输出混入 raw，也不要把长期引用证据仅放在会清理的缓存。PCAP、dump、ELF、SVD 等是否能由当前摄入链直接解析，须另行核验；本次没有验证格式适配能力。可先登记可读报告与原始附件位置，按需用相应工具分析附件。

### 建议的补齐顺序

先选一个真实目标和关键路径，例如一个明确配置下的 TX／RX，不先扩展所有芯片和所有主题：

1. 固定双端代码、运行固件、板卡和有效配置，避免知识适用范围混淆。
2. 补齐该路径依赖的硬件／接口条款、异步边界与 buffer／ring 生命周期。
3. 补齐构建、诊断采集、正常基线和明确的通过标准。
4. 整理一例真实故障的原始证据、根因与前后验证，再按现有 Workflow 提炼知识。

Linux／Zephyr／ESP-IDF 可提供原理与排查参考，不能替代 HI1105／HI1102 本身的硬件、固件、协议或现场证据。是否需要扩大资料范围，应由真实任务遇到的缺口决定。

## 现有知识卡能表达什么

[卡片规范](../governance/specs/cards.md)明确：同一来源可被多卡引用，一卡也可融合多份文档与多个代码入口；正文区分设计、规范、静态观察、测量与建议。[知识导航](../knowledge/index.md)提供 entity、flow、protocol、rule、command、runbook、glossary 七种主题入口，对应[模板目录](../governance/templates/)中的七类正文模板；其中 index.md 是导航页模板。

这里的“卡型”主要指模板与导航职责。当前新卡没有 `type`、`profile` 或 `subtype` 卡头字段，只接受 `id/doc_ref/code_ref/tags/lifecycle`；[新卡解析](../governance/contracts/cards_v3.py#L167-L194)在 `concise_only=True` 时拒绝旧格式字段，[P4 检查入口](../governance/contracts/ingest.py#L727)使用该模式。旧卡兼容 Schema 中的 `profile` 枚举不能作为新卡新增字段的依据。

[P2 指引](../skills/hs-knowledge-change-plan/SKILL.md)由作者按主题查重、选择六决策，并从现有导航选择新卡路径。程序不从 raw 目录自动推定知识类型；[raw 指引](../docs-raw/AGENTS.md)也明确要求按知识性质提炼，不按目录名新增卡型。

### 来源到现有模板的建议映射

下表表示可选知识归属，不要求每份原件产出表中所有卡。

| 原始资料分类 | 可以提炼的知识 | 适合的现有模板 | 要保留的关键边界 |
|---|---|---|---|
| Datasheet、TRM、SVD、原理图、errata | 芯片／板卡／外设职责，复位启动流程，寄存器与时序限制 | entity、flow、rule；交互格式用 protocol | 硅版本／板卡／电气条件；手册能力与实际启用分开 |
| 标准、总线规范、Host–Device／固件 ABI | 字段、状态、消息交互、版本兼容、顺序与资源契约 | protocol、flow、rule；术语用 glossary | 标准条款与产品实现分开；内部 ABI 不冒充标准协议 |
| 架构设计、代码分析 | 模块边界、事件／调用／数据流、对象生命周期 | entity、flow、rule | 静态可达与运行实际发生分开；代码按版本回读 |
| 构建、配置、部署资料 | 组件／配置项语义、依赖互斥、构建与加载方法 | entity、rule、command、flow | 配置定义、默认值与实际生效配置分开；快照保留为证据 |
| 需求、功能说明、验收规格 | 功能边界、期望流程、约束和通过条件 | entity、flow、rule | 记录批准状态及目标；不把计划中的需求写成已实现 |
| 编码规范、并发／DMA／内存管理约定 | 对齐、字节序、锁顺序、上下文、所有权与发布／回收约束 | rule；关联对象用 entity | 强制规则与建议分开；C／编译器／ABI及硬件条件明确 |
| 构建／烧录／日志／trace／dump／抓包手册 | 单命令使用与输出，多步骤采集流程 | command、flow；有诊断分支时用 runbook | 例子与实际运行结果分开；普通操作步骤不一律归排查手册 |
| 具体故障复盘、Issue、修复记录 | 有条件的排查分支、已确认案例、恢复方法、复发检查 | runbook；采集命令用 command；可推广约束用 rule | 保留当时基线、排除过程、补丁与验证；相同现象不证明相同根因 |
| 实验、性能／功耗／时序测量、正常日志 | 对象或路径在特定条件下的观察，测量方法与异常判别 | 相关 entity／flow／runbook 的正文；方法用 command／flow | 指标、单位、样本、方法、误差与原始数据；观察值不改写成普遍阈值 |
| 会议记录、讨论、技术文章、参考实现 | 经确认的设计约束、概念、方案边界与术语 | 按结论主题选 entity／flow／rule／glossary 等 | 作者身份、讨论／决定状态、适用性和验证缺口；不因讨论出现而认定获批 |

### 需要新增哪些卡型

| 候选卡型 | 当前判断 | 何时才值得单独设计 |
|---|---|---|
| 硬件 hardware | 暂不新增。它主要标识领域对象，现有 entity／flow／rule／protocol 可表达 | 若要机器校验寄存器地址、位域、单位与 revision 适配，需要硬件结构模型；新增一个名称不能提供这些能力 |
| 接口 interface／contract／API | 当前先用对象、协议、流程和规则；CANNBot API 说明成套接口参考确有专用组织价值 | 高频签名／参数／约束查阅或受控手册镜像有稳定需求时，评估 API 正文模板和来源更新成本；不因 raw 出现接口文档就自动改 type |
| 配置 config／build | 暂不新增。定义用 entity／rule，操作用 command／flow；有效配置是构建证据 | 若需要对构建矩阵、选项依赖和生效快照做自动比较，须设计配置／构建关联能力 |
| 需求 requirement | 暂不新增。可复用的行为和约束可提炼为 entity／flow／rule | 若要追踪需求 ID→实现→测试覆盖、变更基线与验收状态，需要需求管理模型，并明确与项目 SDD／任务系统的边界 |
| 故障案例 case／incident | 先验证 runbook 下的案例正文与导航，保留事件和通用排查的区别；CANNBot 的优化案例也复用原 Profile | 当独立事件检索、审阅和关联长期无法由正文／导航满足时，再论证新模型；案例多不自动要求 Case type |
| 实验／测量 experiment／measurement | 优先验证相关主题下的实验／观测正文骨架；CANNBot 将观测分别放 Concept 或 Optimization | 独立实验管理、样本／误差审阅或 baseline 比较有持续需求时再考虑模型；自动聚合与回归判断另需实现 |
| 优化方法 optimization | 列为优先试编项。它关注何时优化、收益机制、代价与失效边界，不能只保存性能数字 | 用真实调优材料检验 rule／flow 是否能自然保留决策和前后证据；重复出现稳定的独立检索与审阅需求时再讨论正式类型 |
| 技术任务指南 guide | 试编完整技术任务的原理、步骤、约束和验证入口；与系统运行过程 flow、症状排查 runbook 分清 | 长期技术指南若被拆成多卡后失去任务上下文，可评估 Guide 骨架／入口；纯执行配方仍归 Skill／Workflow |
| 可运行样例 example | 试编带输入、输出、依赖、目标和验证方法的最小样例；代码仍由原工程维护 | 多个例程需要按能力检索与独立审阅时，评估 Example；不复制脱离版本的代码片段 |
| 互操作／迁移 interoperability | 按实际迁移需求评估端点语义映射；当前可组合 protocol／rule／flow | 当技术端点、可复用部分、必须重推导部分及验证边界构成稳定主题时再设计；CANNBot 注册此 Profile 不等于本轮证明有成熟样卡 |

测量的专用审阅要求包括目标／假设、装置、刺激、采样、指标／单位、样本数、统计方法、误差和复现。七模板没有专门的实验骨架，应先通过真实材料试编；CANNBot 的共享 Profile 实例说明专用正文与导航可能已经足够。单个日志文件、正常输出或性能结论不必各自升级成实验卡。

故障案例与通用 runbook 也应区分粒度：案例保留事件、版本和证据，通用手册保留可复用的诊断分支。当前可在同一主题正文中明确案例范围并引用原复盘；案例数量和独立检索需求确立后，再决定是否分离。

CANNBot 的[Vector Add Example](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/knowledge/ops/triton/examples/vector_add.md#L19-L75)和[Profiling Guide](https://gitcode.com/cann/cannbot-knowledge/blob/62e2d52276e6b42813027e377a4e8537df55fc80/knowledge/ops/triton/guides/workflows/profiling_guide.md#L18-L33)提供了这两种知识形态的真实样本。对本项目，后续可选高频 API／最小例程、一次有前后对照的优化、一个移植／bring-up 任务，分别用现有模板与专用骨架试编，比较可检索性、证据保留、重复知识和更新成本；本轮尚未进行这项真实语料对照。

### 多对多归卡示例

以下仅展示材料充分时的组织方式，不声明本项目已有对应技术结论：

1. 一份 DMA TRM 可以形成“控制器职责” entity、“descriptor 字段交互” protocol、“启动与完成” flow、“发布／回收约束” rule；没有增量的主题不单独建卡。
2. 一份 Host–Device 接口规范可以形成消息协议 protocol、请求／确认／超时 flow，以及 buffer 所有权 rule。
3. 一份故障复盘可以更新 runbook 和采集命令 command；只有额外证据足以支持可推广结论时，才更新相应 rule。
4. 一张“descriptor 发布与回收约束” rule 可以融合 TRM、接口规范、匹配版本源码和针对性测量，逐项说明每份来源支持哪部分结论。
5. 一张“恢复后发送超时排查” runbook 可以融合 PM 设计、协议、代码、多个历史案例及日志；当前任务根因仍需自己的证据确认。

## 扩展层次与判断门槛

建议依次判断内容、模板与机器契约的缺口：

1. 缺的是原件、适用条件或依据：补来源与正文，不新增卡型。
2. 缺的是稳定的写作／审阅骨架：先用真实材料试写专用段落；跨多例重复有价值，再评估模板或导航调整。
3. 缺的是独立检索、结构化关系、生命周期或自动校验：明确查询与验证目标，再设计数据模型和运行时支持。

新增正式卡型前，至少应提供多个真实材料中的稳定语义、现有七模板表达不足的具体例子、预期查询／审阅收益，以及对旧卡／引用／入口的兼容方案。将“硬件”“实验”等词加入标题或标签可以帮助召回，但标签不能保证条件生效、数值可比较或知识正确。

当前[卡片规范](../governance/specs/cards.md)规定整卡为检索单位，使用者精读正文判断复杂条件；[搜索参数](../governance/contracts/library.py#L69-L75)只有 query、tags、top_k、include_deprecated，[搜索索引内容](../governance/contracts/library.py#L36-L46)为标题、标签和正文。仅新增目录或模板不会获得类型过滤，也不会获得按实验条件、硬件版本或故障状态自动过滤的能力。[profiles.yaml](../governance/schemas/profiles.yaml)虽然列出章节骨架，当前[规则装载检查](../governance/contracts/validation.py#L271-L272)核对 profile 集合一致，并不证明程序按各型检查正文语义完整。

如未来确需机器识别的新型别，评估范围包括卡头解析／兼容 Schema、计划与落位、索引与查询、审阅校验、导航／模板／Skill，以及相应回归；需要只改展示骨架时，不必扩大到这些层。若正式扩展 profiles.yaml 中的集合，还须同步兼容 Schema 的 profile 枚举，避免规则装载不一致；受锁治理文件变动时按[治理指引](../governance/AGENTS.md)更新相应版本与摘要。当前没有完成真实案例／测量材料的对照试用，因此本轮提交保留分析结论与后续触发条件，不提前增加卡型或字段。

## 给 Agent 的读取入口与充分性验收

建议采用逐层读取：根入口提供真实模块、知识根、目标确认方法和工具入口；模块页提供相关契约与源码入口；任务上下文只附本次基线、需求／复现、关键来源和验证方法。完整原件与源码按需回读，不必在会话开始时全部展开。

每份可复用资料或其来源登记至少能确定：来源身份、版本／日期、目标适用范围、原件位置／hash 和章节／页码／代码定位。故障记录另含采集环境、构建身份、时间关系、复现、观测、假设、结论、验证与未决项。不要只给一个结论而丢失排除其他解释的证据。

“知识足够”建议用代表任务来验收，检查 Agent 能否：

- 正确识别目标与版本，排除旧配置／旧固件知识的误用。
- 将关键结论追到可读取的规范、源码或运行证据，区分设计意图、静态实现与测量结果。
- 解释相关异步路径、所有权与正确性约束，并识别证据缺口。
- 提出能确认或排除根因的最小检查，说明预期观察。
- 按项目方法构建与测试，并用原复现和适用的目标硬件验证修复。

可对相同真实任务分别使用现有资料与补齐资料，固定代码／固件／配置、模型、提示、工具、预算和期望结果，比较关键事实与证据是否正确、严重错误、是否能完成复现／验证以及耗时。正确率和改进幅度必须由试验得出。本次调研没有产生这些数值。
