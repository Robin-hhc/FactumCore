# HiMate 运维与命令参考

本文供维护者准备环境、诊断执行问题，以及 Agent 按需手动调用 CLI。日常放文档、运行入库和提问查询见[使用说明](使用说明.md)；普通用户无需手工登记来源或编排入库节点。

## 项目配置与执行位置

从实际工作区的 `AGENTS.md` 和 `config.yml` 确认项目根、代码范围和知识根。本文用 `repo/` 示意项目根，默认知识根为 `repo/himate/himate-knowledge-wifi-mp/`；执行时使用项目的实际位置。

`config.yml` 的 `code_root`、`modules` 和 `knowledge_roots` 描述实际工作区及允许处理的范围。代码登记的路径基准见[来源登记与关系查询](#来源登记与关系查询)。模块名称只用于组织范围，具体宏、版本、构建和适用条件以真实资料与代码为准。

本文业务命令均在实际知识根执行。Linux 使用 `sh ./knowledge.sh`，Windows 将这个入口替换为 `.\knowledge.cmd`，后续参数相同。CLI 可执行预先配置的本地文档解析/OCR，不自主调用生成式模型；看图、知识决策、写卡和独立审阅由宿主中的 Agent 执行。

### 远端执行：先配置 OpenFlow SSH MCP

数据在 Linux 服务器时，使用宿主已配置的 SSH 能力，在服务器原生目录运行 CLI。服务器需要取得运行代码、实际项目配置和依赖；凭据由宿主管理。调用机安装了 Skill，不代表服务器已准备好运行环境。

## 部署与环境准备

先在实际执行端取得本仓库代码，并准备项目的 `AGENTS.md`、`config.yml` 和知识根。目录与分发边界见[架构设计](HiMate知识库架构设计.md#53-himate-knowledge目录架构)。

### 选择运行解释器

选用实际执行端已有的 Python 3.10—3.12。部署脚本向指定解释器安装锁定运行依赖，不下载 Python、不创建虚拟环境。运行环境放在 `.build` 之外，避免 P1 清暂存时删除。

业务命令使用安装依赖的同一解释器，可通过 `HIMATE_KNOWLEDGE_PYTHON` 指定。未设置该变量时，Linux 入口使用 PATH 中的 `python3`；Windows 入口依次选择 `py -3.11`、`py -3.12`、`py -3.10`，最后尝试 PATH 中受支持版本的 `python`。

### 安装 Skill 与 Workflow

安装命令在包含 `deploy.sh`、`deploy.ps1`、`tools/`、`skills/` 和 `workflows/` 的完整源码仓根执行。Linux 使用：

```sh
sh ./deploy.sh --skills-root '<宿主Skill目录>' --workflows-root '<宿主Workflow模板目录>' --python '<所选Python可执行文件>'
```

Linux 入口默认使用 `python3`；可用 `--python` 选择实际解释器，或通过 `HIMATE_KNOWLEDGE_PYTHON` 设置默认值。其他参数原样交给同一部署后端，`--help` 查看参数。Windows 使用：

```powershell
.\deploy.ps1 -SkillsRoot '<宿主Skill目录>' -WorkflowsRoot '<宿主Workflow模板目录>' -Python '<所选Python可执行文件>' -NonInteractive
```

可用 Linux 的 `--source-root` 或 Windows 的 `-SourceRoot` 指定另一份完整源码仓。Skill 默认目录为 `~/.openflow/config/skills`，Workflow 模板默认目录为 `~/.openflow/config/workflow-templates`；Windows 不传目录且未指定 `-NonInteractive` 时交互询问。脚本先收集源码仓 `skills/common/knowledge/` 中的有效 Skill 包和 `workflows/common/knowledge/` 中的 Workflow 模板，并校验源码和目标路径，再严格执行三步：

1. 向选定 Python 执行一次锁定运行依赖的 pip 安装。
2. 删除本次将部署的全部同名 Skill、Workflow 包目录及其旧内容。
3. 将全部新包复制到各自指定目录。

pip 失败时停止，旧包保持原样。同名包完整替换，源码和目标根中的其他包保留。宿主从目标目录加载能力与模板；项目与知识仓代码通过各自的仓库方式取得。安装器不创建业务仓配置或知识根，也不配置 SSH、注册宿主或追加部署后验证。部署工具的参数和替换边界见[部署说明](../../../tools/deploy/README.md)。

### 首次配置 dbox 资料目录

已有可读 dbox 目录时，将以下 JSON 保存为 `artifacts/dbox-config.json`，把 `path` 替换为执行端实际目录：

```json
{"path":"/srv/dbox/team-docs"}
```

```sh
sh ./knowledge.sh source configure --input artifacts/dbox-config.json --json
```

命令生成本机配置 `docs-raw/sources/dbox.local.yml`，此配置不提交。它只提供本地资料入口；原件保持只读。普通仓内文档可直接放入 `docs-raw/` 的适当目录。

### 仓内命令入口与诊断

```sh
sh ./knowledge.sh doctor --json
sh ./knowledge.sh status --json
```

业务命令的 JSON 请求通过 `--input FILE.json` 传入，文件相对命令的当前目录；`--input -` 表示从标准输入读取 JSON 对象。`--input` 不接受内联 JSON 字符串。可用 `--knowledge-root` 显式指定知识根；产物中的相对引用仍以该知识根为基准。

结果包含 `status`、`phase`、`data` 和 `diagnostics`。需要保存命令输出时，可使用 `--output artifacts/文件名.json`。业务命令的返回结果与诊断是完成判断的依据。

### 本地文档与 OCR 准备

默认运行锁包含 Docling slim 及 PDF/Office/HTML 等 native 依赖，不安装 Torch 或下载 OCR 权重。扫描件 standard 模式需要另外准备匹配的本地 OCR 环境；仓内 `runtime/requirements-ocr-cpu-py312.lock.txt` 是已验证的 Linux x86_64、Python 3.12 CPU 依赖集合，其他执行环境须匹配其实际平台，不将此局部验证视为跨平台验收。

在知识根、选定 Python 环境中显式安装可选依赖，再预取模型；以下仅为环境准备，不在业务任务中重复执行：

```sh
python -m pip install -r runtime/requirements-ocr-cpu-py312.lock.txt
python -c "from pathlib import Path; from docling.utils.model_downloader import download_models; download_models(output_dir=Path('artifacts/models/docling-cpu'), with_layout=True, with_tableformer=True, with_code_formula=False, with_picture_classifier=False, with_rapidocr=True, rapidocr_models=['onnxruntime:ch'], progress=False)"
```

将具体来源及 `parser` 配置写入请求后开始 P1，例如 `{"source":"实际来源ID","parser":{"pipeline":"standard","models_path":"artifacts/models/docling-cpu","ocr_languages":["ch"]}}`。模型目录必须位于当前知识根的 `artifacts/models/`；模型与环境独立维护，不随入库或来源阅读清理。standard 的 OCR 用于 PDF 和独立栅格图片；Office 内嵌图先导出供 Agent 阅读，不自动逐图 OCR 或生成图意描述。多帧 TIFF 当前只保留首帧，后续帧以明确的 partial 缺口报告，不能据首帧认定全文已读。默认 native 与 standard 的耗时、内存及覆盖范围不同，按实际资料选择。

### 框架更新与清理

更新仓内程序时，保留原件、正式卡、来源登记、项目配置、模型和独立环境，按版本更新程序与规则文件。具体目录边界见[架构设计 §5.5](HiMate知识库架构设计.md#55-框架更新与目录清理)。部署脚本只安装依赖并替换同名 Skill、Workflow 包，不更新知识根业务资产。

最近一次入库回执位于 `artifacts/ingest/latest.json`；处理进度仍由来源登记维护。清理前先完成当前任务，失败任务保留 `.build/` 重试；不要整体清空 `artifacts/` 或带有历史证据、备份的目录。

## 手动入库与来源管理

### 入库命令

正常入库由 OpenFlow 的 `hs-knowledge-ingest` Workflow 编排。以下命令供 Agent 执行节点或维护者诊断时使用；一次处理一个变化文件，完整步骤见[详细设计 §5](知识库详细设计.md#5-节点详细职责)。

自动扫描支持 `.md`、`.txt`、`.pdf`、`.docx`、`.xlsx`、`.pptx`、`.html/.htm`、`.csv` 和 PNG/JPEG/TIFF/BMP/WEBP 图片；`AGENTS.md`、`README.md`、`index.md` 作为说明或导航，不参与扫描。旧版 `.doc` 等未启用格式需先转换。默认 native 模式保留可提取文字和图片，不做 OCR；扫描件需要显式 standard 模式、可用的本地模型与依赖，缺项报告在解析缺口中，不临时下载。

| 节点 | 实际执行 |
|---|---|
| P1 | `ingest scan` 选择变化文件，保存副本和关联卡入口 |
| P2 | 作者阅读材料和完整旧卡，在 `.build/plan.md` 固定候选 ID/正式路径并制定六决策 |
| P3 | 作者按计划既定路径和模板在 `.build/cards/` 写完整候选 |
| P4 | `ingest check` 核对计划与候选 ID/路径，再由独立 reviewer 审阅实际内容 |
| P5 | `ingest commit` 落位、刷新关系和检索索引、登记本文件已处理 |

P1 默认扫描 raw，可限制到一份文档或子目录：

```sh
sh ./knowledge.sh ingest scan --json
sh ./knowledge.sh ingest scan --source docs-raw/design/radio.md --json
```

上面两条是不同的扫描选择，按本次需要执行其中一条。`prepared` 表示材料已写入 `.build/task.json`；`unchanged` 表示选定范围没有待处理变化。P1 会清空 `.build`，其中只保存当前一次任务的暂存。

文档的 `source.parsed` 包含 `.build/materials/parsed/` 内的 Markdown、结构 JSON、定位、图片及产物摘要，P2—P4 复用这一份结果，P5 成功后一起清理。默认不生成全部整页 PNG，不长期保存转换副本，也不将转换 MD 重新登记为 raw。长文按页段阅读，图片须用宿主图片工具实际打开，复杂表格结合 JSON；`parsed` 只表示机械转换状态，不认证所有内容已理解。

需要重新审阅 hash 未变的来源时，将 `{"source":"实际已登记ID","reprocess":true}` 保存为请求文件，用 `ingest scan --input FILE.json --json` 开始一轮。该选项必须指定具体已登记来源，不自动清空成功处理标记。

`.build/plan.md` 必须以 YAML frontmatter 开始，`cards: [{id, path}]` 只列本轮完整候选；`path` 为知识根相对的 `knowledge/...md`。更新保留原路径，新卡在 P2 按现有类型导航选目录；未改卡不列，无完整候选写 `cards: []`。frontmatter 后保留自然语言六决策计划，见[计划格式与示例](../../../skills/common/knowledge/hs-knowledge-change-plan/references/request.md)。

P3 将计划 `path` 的 `knowledge/` 前缀替换为 `.build/cards/`，例如 `knowledge/concepts/flows/radio.md` 对应 `.build/cards/concepts/flows/radio.md`；不自行重选目录，不在卡头增加 `path`。P4 由 `ingest check` 一一核对，落位拼写问题回 P3，计划决定需要改变才回 P2。需要删除旧卡时，在 `.build/changes.json` 明确列出知识根相对路径：

```json
{"delete":["knowledge/concepts/flows/old-radio.md"]}
```

候选写好后进入 P4；固定检查与独立内容审阅均通过，才执行 P5：

```sh
sh ./knowledge.sh ingest check --json
```

```sh
sh ./knowledge.sh ingest commit --json
```

没有候选卡但确认本文件已完整处理时，先由 P4 审阅不改理由，将实际理由保存为 `.build/commit.json`，再提交：

```json
{"reason":"本次仅调整排版，关联卡的结论、条件和定位均保持有效。"}
```

```sh
sh ./knowledge.sh ingest commit --input .build/commit.json --json
```

上例理由应替换为本次真实情况。仅有删除清单、没有候选卡时，也需提供 `reason`。必要依据不足时选择暂缓，保留缺口，不登记文件已完成。

扫描以文件存在性和 SHA-256 判断新增、修改、删除，不要求事先提交 Git。成功入库只更新触发文件的处理版本。P1 后文件再次变化，下次扫描仍会发现。

### 来源登记与关系查询

P1 自动登记扫描到的文档。作者需要增加代码引用或其他实际来源时，使用 `source register`，然后将命令返回的真实 ID 填入卡头。来源登记与已处理版本由命令维护，无需手工更新处理账本。

文档登记请求示例，保存为 `artifacts/register-doc.json`：

```json
{"kind":"raw","path":"docs-raw/design/radio.md"}
```

```sh
sh ./knowledge.sh source register --input artifacts/register-doc.json --json
```

raw 路径相对知识根，必须指向实际文档。代码登记请求示例，保存为 `artifacts/register-code.json`：

```json
{"kind":"code","path":"main/module-a/radio.c","encoding":"utf-8"}
```

```sh
sh ./knowledge.sh source register --input artifacts/register-code.json --json
```

未指定 `repo_id` 时，代码路径相对项目 `config.yml` 所在目录。例如配置的 `code_root` 为 `main`，路径应包含 `main/`。指定 `repo_id` 时，路径相对配置中该仓库的根；两种方式都受配置的代码与模块范围约束。

代码默认按 UTF-8 解码。实际为 GB18030 时，登记请求改为 `"encoding":"gb18030"`；目前支持这两种代码编码。修改编码配置后继续使用该来源 ID，核对本轮抽取文本与实际行号。

关系查询使用 `source list`。将所需的一行请求保存为 `artifacts/relations.json`，替换真实 ID 后执行：

| 目的 | JSON 请求 |
|---|---|
| 查某卡的全部文档与代码 | `{"card_id":"实际卡ID"}` |
| 查某来源及受影响卡 | `{"source_id":"实际来源ID"}` |
| 列全部已被卡引用的文档 | `{"kind":"raw","referenced":true}` |
| 列全部已被卡引用的代码 | `{"kind":"code","referenced":true}` |

```sh
sh ./knowledge.sh source list --input artifacts/relations.json --json
```

需要旧原文时，保存如下请求为 `artifacts/resolve-source.json`：

```json
{"source_id":"实际来源ID"}
```

```sh
sh ./knowledge.sh source resolve --input artifacts/resolve-source.json --json
```

可补充 `commit` 或 `hash` 指定所需历史版本。恢复结果返回 `original_ref`，可抽取时另有 `text_ref`。Git 只能恢复实际取得的历史；未提交且没有副本的旧内容无法恢复。P2 可按当前全文与旧卡继续判断，确有必要缺口时暂缓。

旧 PDF 提取与定位不支持加密文档；返回 `ENCRYPTED_DOCUMENT` 时，应提供业务允许读取的未加密原件，不把失败当作已完成回源。

### 当前文档回源、按页读取与释放

将 `{"source_id":"实际来源ID","page_start":995,"page_end":1000}` 保存为 `artifacts/extract-source.json`，页范围可省略；页号限 PDF 的实际原页，不是转换稿行号。需要 OCR 时在同一请求中加入明确的 `parser` 配置。

```sh
sh ./knowledge.sh source extract --input artifacts/extract-source.json --json
```

返回独立 `read_id`、UTC Unix 秒的 `expires_at`、原件副本和 `parsed` 材料入口，位于 `artifacts/source-read/<read_id>/`；不触碰 `.build`、查询报告或来源成功处理标记。读取 Markdown/JSON，并使用宿主图片工具查看相关图。完成后将 `{"read_id":"本次返回的ID"}` 保存为请求文件，执行 `source release --input FILE.json --json`；重复释放同一合法 ID 安全返回。

PDF 的曲线、时序图等可能由矢量线条和文字组成，不能只看导出图片数量。显式页范围会额外生成 `role: page_preview` 的页面视图，从 `parsed.images` 和 Markdown 读取；固定 1.5 倍，每次最多 8 页、累计 1600 万像素及 16 MiB PNG，并计入总产物配额。超限或渲染失败会报告未生成页，缩小范围继续读取。原 Docling 结构和原图缺口保持可见；预览不代表已 OCR 或已理解。未指定范围与全量 P1 不默认生成整页图。正式 PDF 卡引用物理页号，不能复用页段解析中的局部 `element` 编号。

需要更长阅读时间时，在到期前调用 `source renew`，请求可加 `ttl_seconds`（1—86400，默认 1800）；到期入口不能续活，需要重新提取。`source cleanup --json` 与新提取开始时只回收过期且没有活跃转换的目录，转换中的释放返回 busy。最多保留 8 个有效/待检查阅读目录，每份原件及解析产物各受 256 MiB 上限约束；达到容量应释放已消费的 ID。损坏租约保留待检查，不据此删除未知内容。这里没有后台清理守护进程，工作流必须主动释放，不能批量清空 artifacts。

### 独立格式与引用检查

```sh
sh ./knowledge.sh lint --json
```

该命令执行正式库的固定格式与引用检查。review Skill 指导独立内容审阅；固定检查通过不代替对事实、条件和依据的判断。需要内容修订时，通过入库流程处理。

## 查询命令

按关键词搜索完整正式卡，再精读正文与必要来源：

```sh
sh ./knowledge.sh search "状态切换" --top-k 5 --json
sh ./knowledge.sh read '实际卡ID' --json
```

需要搜索整卡退役资料时，在 search 后增加 `--include-deprecated`。旧 draft 不自动升为 stable，不进入默认搜索；已知 ID 时仍可直接 read。

需要标签时通过 JSON 请求查询。例如保存为 `artifacts/query-request.json`：

```json
{
  "query":"状态切换",
  "top_k":5,
  "tags":["实际标签"],
  "include_deprecated":false
}
```

```sh
sh ./knowledge.sh query --input artifacts/query-request.json --json
```

标签按实际材料填写或删除；多个标签要求全部匹配。请求字段与结果的完整定义见 [Query API](../../../skills/common/knowledge/hs-knowledge-query/references/public-api.md)。旧 `--purpose` 或 JSON 中的 `purpose/context` 在执行搜索或读卡前报 `QUERY_PARAMETERS_REMOVED`、退出码 2，不生成正常命中报告；删除旧字段后通过正文判断适用性。

`read` 返回原始 metadata、完整 body、规范化引用及来源入口，允许直接阅读退役卡。搜索只返回相关候选，不按用途或复杂条件认证结论；Agent 核对正文条件、版本、依据性质及缺口，再按需核读原文、代码或测量记录。stable 或代码引用都不证明已实现。空结果先检查关键词、标签、退役状态、截断和诊断。

搜索返回 `report_ref`，指向 `artifacts/query/` 下本次独立报告。使用本次返回结果；显式 `--output` 在知识根内也只能写入 `artifacts/query/`。查询不读写 `.build`，可以与入库或巡检共存；短暂等待落位或索引重建的数据库命令属于正常调度。ingest 与 lint 两条写流程仍按串行方式安排。

## 巡检命令

调用已安装的 `hs-knowledge-lint` Workflow。L1 同步实际工作区，L2 查找 raw 或被正式卡引用的已登记代码变更，逐文件复用 P1—P5，L3 处理索引，L4 汇总实际剩余事项。巡检与单独入库按串行方式安排。

L1 需要同步时，保存如下 JSON 为 `artifacts/patrol-sync.json`，将 `cwd` 替换为执行端真实多仓根目录：

```json
{
  "sync":{
    "argv":["git","mm","sync"],
    "cwd":"/srv/workspace/repo",
    "timeout_seconds":600
  }
}
```

```sh
sh ./knowledge.sh patrol sync --input artifacts/patrol-sync.json --json
```

本次只检查本地现状时，可运行 `patrol sync --json`；结果仍为 `phase: synced`，但 `data.synchronized` 为 `false`。同步完成后，后续命令使用新的 CLI 进程。

```sh
sh ./knowledge.sh patrol plan --json
```

返回 `needs_ingest` 时，将 `data.next_file.source_id` 原样交给 P1；即使待办是代码文件，也使用该来源 ID：

```sh
sh ./knowledge.sh ingest scan --source '实际来源ID' --json
```

然后按入库 P2—P5 处理。成功后再次 `patrol plan`；暂缓时结束本轮，报告缺口。返回 `needs_reindex` 时运行重建；无待办时直接汇总：

```sh
sh ./knowledge.sh patrol reindex --json
sh ./knowledge.sh patrol complete --json
```

`complete` 返回真实 `remaining` 数量；`phase: completed` 表示统计已完成，仍需查看是否存在待办。周期触发由外部调度器配置。

## 来源审计、索引与提交核对

`maintain audit` 检查被正式卡引用的来源是否存在且可访问；`patrol reindex` 从正式资产重建关系与检索索引，不改变内容处理标记：

```sh
sh ./knowledge.sh maintain audit --json
sh ./knowledge.sh patrol reindex --json
```

本地入库、Git 提交、推送和 CI 合入分别执行和报告；入库命令不自动提交 Git。

## 进度续办和完成判断

| 情况 | 继续方法 |
|---|---|
| P1 `unchanged` | 选定范围无待处理变化，结束本次入库 |
| P2 必要依据不足 | 记录缺口并暂缓；补齐后再处理 |
| P4 指出决策问题 | 回 P2 修订计划，再成稿与审阅 |
| P4 指出成稿问题 | 回 P3 修稿，再执行 P4 |
| P5 中途失败 | 保留 `.build`，修正执行问题后直接重试 P5 |
| P5 `completed` 且返回 `cleanup_error` | 入库已完成，按错误清理暂存残留 |

P5 失败后不要先运行 P1，以免清掉本轮材料。需要改稿时，回 P3 并重新经过 P4。`status` 可查看本轮任务或最近结果，错误原因查看命令的 `diagnostics`。

## 正式资产与换机

原件、正式卡、来源身份和成功处理信息按业务仓规则保留；`.build` 和派生索引不用作为换机前置。新执行端取得正式资产，准备实际配置、代码和依赖，再运行 `patrol reindex` 重建数据库与检索索引。

本机 dbox 路径、解释器和宿主能力在新端重新配置。需要历史回源时，同时取得对应 Git 历史；实际权限、宿主触发和服务器行为在目标环境验证。
