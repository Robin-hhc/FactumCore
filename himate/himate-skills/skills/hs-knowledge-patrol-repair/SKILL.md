# 修订已有引用卡

在本轮已确认的知识根和执行端读取材料并写本轮暂存文件。首次单独使用时，先读取知识根的 `AGENTS.md` 和 `config.yml`，用当前会话提供的 `knowledge_doctor` 或已确认 CLI 的 `doctor --knowledge-root <知识根绝对路径> --json` 核对目标。命令找不到、启动入口有明确缺项或诊断仅表明缺运行依赖时，加载 `hs-knowledge-setup`，在同一执行端补齐并复查。得到与知识根匹配的就绪回执后继续原任务。

读取 `.build/task.json`、其中的 `affected_cards` 原卡和材料入口。逐卡核对引用对应的结论、适用条件及必要代码上下文，按[维护候选格式](references/maintenance-candidates.md)记录简短决定和完整候选。

- 仅位置变化须有可信旧证据、唯一新位置，并确认相关行为与条件不变。存在 `location_candidates_ref` 时读取工具提供的定位候选，其 `requires_context_review` 表示仍须核对同文件及必要上下文。确认只修位置时正文保持不变。全文件 hash 变化、行号合法或一小段文字相同都不足以单独证明只是位置变化。
- 相关行为变化时，仅修该卡受影响的结论、条件和引用。保留原 ID、路径、知识边界、有效历史文档依据及无关内容。
- 缺复核基线时逐卡确认当前代码对既有结论的支持，有可信旧版才作历史比较。结论成立且定位正确可以零改卡，仍记录实际核对依据并交 L5。
- 来源缺失时先核对实际可用的历史依据。局部失效只修对应部分，整卡职责确实失效才说明退役依据。必要证据无法核实时记录具体缺口并暂缓。

同文件内独立新主题记录主题和实际证据位置供汇总。维护任务不新建、合并、拆分或物理删除卡片，不改原 ID 和正式路径。只在 `.build` 写候选，正式库由 L6 发布。

决定和候选齐备时交 L5。能由重新备料解决的输入问题交回 L3，无法恢复的必要证据缺口交汇总并保留待办。
