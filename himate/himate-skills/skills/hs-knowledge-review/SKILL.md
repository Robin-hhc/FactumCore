# 检查并独立审阅候选

沿用本轮已确认的知识根和执行端。当前会话提供本步骤所需的 Knowledge MCP 工具时，调用该工具并沿用其绑定的知识根。采用 MCP 时，缺少工具则报告工具名，调用被拒、失败或返回 `blocked` 时按实际诊断处理。

采用 CLI 时，从知识根运行该执行端已确认的 `knowledge` 入口，每次传入同一 `--knowledge-root`。首次单独使用 CLI 时，先读取知识根的 `AGENTS.md` 和 `config.yml`，运行 `knowledge doctor --knowledge-root <知识根绝对路径> --json` 核对目标和版本。命令找不到、启动入口有明确缺项或诊断仅表明缺运行依赖时，加载 `hs-knowledge-setup`，在同一执行端补齐并复查。得到与知识根匹配的就绪回执后继续原任务。

## P4

1. 先调用 `knowledge_ingest_check`，使用 CLI 时运行 `knowledge ingest check --json`。机器核对计划与候选、格式、有效引用，以及固定原件和本批 `source_units` 或旧 PDF 的 `source_pages`。`PLANNED_CODE_REF_MISSING` 指出某张卡的计划位置未被有效引用覆盖，成稿漏填或错填回 P3，所需依据不足回 P2。遇到 `CODE_SYMBOL_*` 同时读取 `message` 中的具体解析原因，按[代码定位诊断](references/review-guide.md#代码定位诊断)核对，不只凭状态名归因。范围和计划填写问题回 P2，候选漏写、多写或偏离清单时回 P3。
2. 独立 reviewer 按任务范围复核。
   - 审阅文档时对照 `index_ref` 和计划读取实际范围。打开决定结论的图像，路径以完整 `markdown_ref` 所在目录为准。核对图像、相邻 OCR、关键事实及遗漏，再检查旧知识迁入和生命周期决定。沿用 task 指向的同一份转换稿、JSON 和图像。产物丢失或摘要变化时停止核对并重新备料。记录未审图片或页段。
   - 核对计划是否列齐候选用来解释行为或用于回查的真实代码位置，包括设计卡里的实现入口。遗漏重要位置的计划回 P2。沿已登记路径和行段核对引用、模块与版本，判断能否支撑对应结论。定位不足、歧义或冲突影响结论时补查，并核对原应保留的条件和例外。
3. 在 `.build/review.md` 记录实际结论、选定范围、无增量判断和缺口。必要内容均已核实后交 P5。空候选仍须核对选定文档范围，确认无增量。剩余文档单元由后续批次处理。

- 决策、事实、条件或归卡问题回 P2。
- 表达、格式、引用填写、路径拼写或组稿问题回 P3。
- 返工稿重跑固定检查，独立核对修改及受影响的结论，结论与依据均未变的部分复用本轮已有的独立审阅结果。缺依据说明缺口，不能写成通过。

P4 是唯一独立 reviewer；P5 直接入库，不重复这轮质量检查。必要的审阅要点见[内容复核](references/review-guide.md)。
