# Index integrity and shared repository snapshots

Apply's `index-build`, `index-verify` and `index-activate` actions run independently with the actual K and global Python. They validate complete SQLite table sets and values, schema/tokenizer versions, frozen card bodies and generation fingerprints. Query checks the actual source/Claim qualifications for its purpose. Indexing does not repeat P5's whole-library quality rules and does not require upstream review or processing-record qualification credentials. Activation retains full index verification, actual-input checks and active-pointer CAS; the immediately preceding same-process verification can be reused only while its actual generation fingerprints still agree.

Both local and shared generations use the shared `contracts/indexing.py` format (index schema 3.0, tokenizer 2.0). Changed business rules require an explicit rebuild. Workflow sequencing, role separation and handoff checks belong to OpenFlow.

`channel: shared` can read an explicit `knowledge_commit` from the actual Git repository and returns `repository_snapshot`. The Skill checks actual immutable Git cards, rules, source lock and references, without inferring publisher identity, CI success or remote merge acceptance. If an explicit `publication_receipt_ref` claims signed publication identity, its trusted adapter and Ed25519 signature are verified under the existing optional publication trust interface. That identity check is separate from workflow handoff; ordinary local use and direct repository snapshots need no signing adapter or catalog. No Git writes or network publication run here.

Shared verification, activation and query retain snapshot identity and actual Git/content checks. Current code questions still require current configured source and Claim scope; a historical snapshot does not prove current implementation. Build and activation keep the writer lock and refuse unfinished write transactions before snapshotting or switching the pointer.

Build may accept `code_contexts` (alias `code_evidence`) keyed by card ID. Each business snapshot contains `code_identity`, `config_digest` and per-Claim `claim_evidence` with requirement, path and SHA-256. These are actual source/Target/build material bindings, without a required passed status, reviewer identity or upstream Skill record. Current build/runtime Claims need their adopted evidence files; query rechecks those bytes. Static source Claims continue to use direct config/source checks. Changed supplied build or configuration material cannot remain current merely because source text is unchanged.

The Agent prepares these snapshots from actual materials and freezes them with the index. They are generated business data, not another user-maintained configuration file.
