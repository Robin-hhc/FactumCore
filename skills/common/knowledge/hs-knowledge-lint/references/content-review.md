# Declared semantic review inputs

The public `record-review` action records actual review declarations through the same pinned domain rules used by P5 `review`. It needs `operation_id`, `semantic_plan_ref`, exact `sampled_unit_ids/unreviewed_unit_ids`, a nonempty `reason`, and an explicit `findings` list (including an empty list when no finding exists). An optional `view_ref` binds the exact complete candidate. Reviewer/context labels are descriptive and never identity gates.

Sampled and unreviewed IDs partition all authored dispositions, including content, skip, defer, failed, uncovered and maintenance units. Record-only batches review the actual missing-material facts, reasons and next steps; they cannot pass with an empty declared scope. At least one unit must be sampled when an applicable scope exists. A completed unchanged skip is exempt only when the semantic plan binds a real scan proving that state; explicit material targets never invent scan completion or receive that exemption.

Each finding identifies a sampled unit, actual evidence and reason, and a return target P2/P3/P4. The result preserves `content_review_ref`, `review_status` and `skip_sample`; the record binds the exact semantic plan, real scan or explicit material observations, and optional view.

`record-review` reports `reviewed` or `needs_revision` for this declaration only. It does not claim that full lint or the complete P5 quality stage passed. P5 `review` combines the actual semantic review inputs and one deterministic fixed check in the same invocation; formal/full and CI checks remain independent of these declarations.

For a content candidate, P5 also executes the semantic plan's unchanged `target_queries` against the complete final candidate using the same query qualification/retrieval rules and the already verified temporary database. It checks required/forbidden cards, order, expected/forbidden Claims and same-candidate reads. An unmet expectation is a blocking plan issue to return to P3; missing required inputs or unavailable runtime conditions retain their actual incomplete diagnostics. Inspect the actual per-case results rather than treating index construction as query success. This preview neither reads the old active generation as the candidate nor creates a formal Search Receipt or activates an index. Record-only batches and ordinary formal/full or CI checks do not acquire a private-plan dependency.

Read `candidate_queries` on the `index.build` check row: it preserves the original cases digest, per-case purpose, expected/actual cards and Claims, same-generation reads and qualification gaps. `TARGET_QUERY_EXPECTATION_FAILED` is a blocking semantic result and adds P3 to the review return targets. `TARGET_QUERY_INPUT_UNAVAILABLE` keeps the check incomplete and does not direct a semantic replan merely to bypass an unavailable input.

A new P4 revision can explicitly adopt its previous view's unchanged semantic plan. Review then requires the new `view_ref`, exact previous-view adoption and original scan identity; an old plan alone cannot be relabeled as a new round. The saved review always binds the new view's digest and actual operation, with the original scan operation retained separately.

Every code source on an active card requires `sources[].code_ref`, independently of review_mode or Claim adoption. P5 decides from actual content whether a necessary code link is absent; pure documents do not require invented links. The field is part of the exact card/view bytes. Changing it requires review of the new view; snapshot-only source_set identity does not authorize reusing an old review. No separate symbol-review credential or new Claim.source_refs form is introduced. Historical recovery and deprecated cards retain the original four-field compatibility. Review declarations and actual fixed navigation results remain distinct.

P5 reads the exact staged payload through its frozen final-path mapping. Reports, code-check copies and temporary databases remain in this operation stage; it publishes no formal evidence/events. Independent lint writes its own report and never cleans other tasks. A passed report cannot authorize changing the frozen publication bytes.
