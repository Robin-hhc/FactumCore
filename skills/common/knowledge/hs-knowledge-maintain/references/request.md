# Requests

`register-source-change`: operation_id, bundle_ref. Changes are derived from the actual current source lock and fixed bundle, not accepted from caller assertions. `status`: operation_id. `advance`: operation_id, apply_result_ref, generation_ref. Raw originals are read-only; unresolved human, code, activation or source evidence keeps blocks intact.

`register-code-change`: operation_id, bundle_ref. This explicit action derives old registered snapshots and affected Claims, verifies the new code snapshot against the currently authorized repo/path through the public source resolver, and durably records `code_changed` blocks. Capture alone does not register a semantic change. A source ID cannot migrate to another repo/path. Repeated identical transitions are idempotent.

For code blocks, `advance` additionally needs `current_code_proof_ref`: apply's public current-content verification must authenticate a fresh signed semantic proof for the exact same final view and include each current card in `eligible_files`. Historical code source snapshots remain immutable; they need not be replaced merely because a fresh proof checked newer code. Raw-document blocks still require an accepted card referencing the latest observed snapshot and matching current original bytes. Missing proof, unactivated/stale generations or self-reported eligibility never clear blocks.

`recover-events`: operation_id. Completes only the exact sealed source events retained in pending state, including fixed resource/snapshot and affected Claim identities; does not clear a block or need temporary capture files. Pending blocks/epoch are durable before the event publish, and scan watermark advances only after event persistence. Repeated source versions carry explicit observed-snapshot event identities.
