# Public request

Common inputs: `operation_id` and the actual knowledge root. The current framework lock is loaded by default; `--rules-digest` can pin it explicitly. Catalog and Workflow execution identities are not required.

- `scan`: optional `source` (raw file or directory relative to K), optional `prior_record_refs` only for explicit recovery; default reads formal `logs/ingest/*.yaml`. Returns sealed `scan_ref`/`scan_digest`, including exact scope and completeness. `new`, `changed`, `missing`, `unchanged`, `unfinished`, `read_failed` are observations, not semantic decisions. Incomplete scans never infer missing files.

  An explicitly absent `source` with no matching registered history returns `RAW_SCOPE_NOT_FOUND`, rather than a successful empty scan. Known deleted originals remain `missing`; absent default raw directories are allowed. Complete no-op inventories with no maintenance debt or later authoring stages do not create pending work. `data.finalization_pending` separately lists local content batches whose committed bytes need indexing/query/activation finalization: each includes `operation_id`, `status`, `next_action`, exact view/generation references when recoverable, and gaps. Empty raw `actionable_unit_ids` does not mean this list is empty. A consuming clone without local producer journals has no inherited producer execution obligation.

  Normal ingest follows its planned P6 record → P7 apply/index/query sequence. Status and scan summaries help locate an interruption; they do not add a shortcut around those nodes. If an uncompleted old view no longer matches current knowledge/source-lock bytes, `historical_finalization_unknown` retains that historical uncertainty separately instead of reactivating its stale generation or treating it as current mandatory finalization.
- `prepare` is retired with `ACTION_RETIRED`. Use the separate `hs-knowledge-source-prepare` Skill. Source-scan does not dispatch its CLI or import its private scripts. New P2 accepts fixed scan units or explicit targets independently, and publishes immutable material versions. P5 missing-material returns target P2 only; actual adopted-input drift requires a new affected P1 observation/operation.
- `record` normally receives `view_ref`, optional explicit `semantic_plan_ref` and `disposition_preview_ref` (defaulting to the view's exact references). The fixed P3 plan supplies `scan_ref`. P6 checks the preview's operation, semantic digest, input snapshot and exact unit/maintenance/card-decision copies, then transcribes them. Content units require P3's fixed `record_action`, `card_refs` and `claim_refs`; a mixed set of card decisions is never guessed into update. `authored_units` and `preview_card_decisions` retain the complete exact inputs. A supplied `dispositions` list may only equal the mechanical result; P6 cannot replace the authored decision.

  Independent legacy `scan_ref` plus explicit `dispositions` remains a business-data utility without a review assertion. `lint_ref` and `skip_sample` are optional supporting data, not passing-step prerequisites. Each disposition has `unit_id`, action/reason, observed/adopted fingerprints, progress, card_refs and claim_refs. Include explicit coverage, pending and next_step when incomplete. P6 does not run lint or ask another Skill to review content. The proposed JSON-compatible YAML contains the sealed inventory so another clone can understand it without local `.build/`. Returns `ingest_record_ref`, `record_ref`, digest and formal `record_path`; P7 alone applies the formal record in the same batch as knowledge.

  A new return round may adopt the original scan without changing its bytes or operation identity. P6 requires the new view's exact previous-view/revision, semantic and material references and digests, and copies `origin_scan_operation_id` from the actual original inventory. An origin label alone cannot authorize cross-operation adoption. The record belongs to the new operation and embeds the unchanged original inventory; after final application, the original raw obligation is closed by that new record. Local status can identify the explicit predecessor as `adopted_by_new_round`; consuming clones need no producer-private artifacts.

  When context Claims are affected, pass the bound `semantic_plan_ref`; P6 copies its separate `maintenance_units` into shared `maintenance_dispositions` and preserves defer/failure/uncovered pending facts. Each uses `maintenance:<card>#<claim>` and binds the exact `scan.current_context.affected_claims` set. These do not become raw units; code-only work can have an empty raw list.

- `status`: optional `target_operation_id`; returns `operations[].facts`, `stage_status`, `completion` and top-level `catalog_gaps`, plus explicit unverified submission/CI/merge state. Saved facts include scan/materials, semantic plan/plan/view, content review/local check/lint, records/apply, candidate index, representative regression and activation. Missing or unexamined stages remain `unknown`; old-rule facts are `historical_rules`. Completion is `complete`, `pending`, `unknown` or `not_applicable` (observation-only), with an explicit `next_action` and exact available references. It never repairs, resumes, activates or writes files.

  Top-level `complete` only describes whether the saved-fact collection had readable, valid records; it is false on `catalog_gaps` or operation gaps and is not content health or workflow completion. A corrupt unrelated history record is reported by its exact reference without hiding the readable operations. Scan history reconciliation still rejects invalid shared processing records rather than using them to authorize skipping sources.

  Local finalization observes exact view-bound reports and the view's frozen queries (legacy views require explicit representative coverage of every changed target), the saved fixed-index verification result and the actual active pointer or saved activation observation. It does not read every index blob, hash the database or run `verify_database` during discovery. `verification: saved_facts_only` and `index_health: not_examined` distinguish execution completion from fresh index health. P7 performs the exact database and query validation when resuming. Reports/indexes may belong to independent operation IDs. A passing arbitrary query is insufficient; the regression report precedes activation and alone cannot prove it occurred. Saved observations retain exact generation/manifest/pointer bindings even after a later activation. They are local facts, never upstream approval or cross-machine credentials.

  New P7 persists `.build/operations/<op>/batch-intent.json`, `batch-build.json`, and `batch-complete.json`. Status reports the real stop: intent without transaction → `resume_batch`; uncommitted journal → `recover_transaction`; committed content without build → `rebuild_index`; saved build without completion → `resume_queries` with the original `expected_active`, including null. Record-only completion needs no index/query activation. A consistent saved completion with phase `completed` or `recorded` is a terminal observation. The P7 resume action itself revalidates exact bytes and boundaries; source-scan never executes recovery.

  `resume_queries` includes the candidate manifest's original `expected_active`, including a genuine null. Missing saved baseline, ambiguous candidates, stale rules, changed content or already-active generations without a bound report require `inspect_finalization` / `inspect_context`, not replaying apply or replacing the original CAS baseline. Formal-only history recommends `check_local_index`; it cannot prove this consumer's local index state.

  A verified `rolled_back` journal is terminal, with `completion.scope: rolled_back`; resuming the user's content request means `prepare_material` in a new operation, never recovering or reapplying the rolled-back transaction. An unreadable local journal instead requires `recover_transaction` inspection and remains unknown.

Observed fingerprints and adopted versions are distinct. Unchanged input with unfinished processing or current-context restrictions remains actionable. Substantive skip uses `kind: substantive`; scan skips use `kind: scan_unchanged`. A record reports actual progress and does not itself approve the content or authorize Git publication. History follows explicit record predecessors per covered path; a narrow scan never erases earlier observations outside its scope, and conflicting branches remain unfinished.

Legacy independent-Skill compatibility: inspection can also discover an explicit local apply journal that lacks a P6 record, because the lower-level apply contract historically permits that input. Its source scope is matched from actual adopted raw paths or code maintenance, and superseded formal operations are not resurrected. This compatibility does not make a no-P6 branch part of the normal ingest Workflow, does not authorize arbitrary node skipping, and is not evidence of a normal Workflow defect.
