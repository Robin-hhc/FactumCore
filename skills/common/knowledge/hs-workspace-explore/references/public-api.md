# Workspace binding 2.0

Invoke `scripts/cli.py --input request.json --output response.json`. Request:

```json
{"operation_id":"bind-session","target_path":"<explicit existing code/workspace path>","target_id":"chip12-host"}
```

`target_id` is optional and selects a logical chip/side combination. Module labels do not prove a build or enabled macros. Use explicit trusted process arguments `--rules-digest SHA256`, or `--catalog CATALOG.json` / `--registry workspace-registry.json` from the isolated installer. An explicit request `config_path` limits discovery to that config; otherwise search target ancestors and registered workspaces. Multiple workspace matches block. Running from another current working directory does not change a resolved mapping.

No pin means `phase: resolved` with `trusted_rules_digest_required`, not context loaded. A trusted pin permits only verified domain contract bytes to execute. A successful discovery returns `phase: context_loaded`, `context_ref` and `context_digest`. The immutable record contains actual AGENTS bytes/hashes, the original config hash, resolved module paths and labels, internally derived scope IDs and explicit gaps. `repos` is a dictionary of logical file scopes keyed by stable IDs; the name does not imply repository-manager integration. Chip/side relationships are derived for internal checks without user-written Target/pair tables. File-workspace discovery does not read Git/mm/manifest metadata or execute their commands; commit, identity, dirty state, build and enabled macros remain unknown. P2/P4 bind the actual selected source hashes and conditions separately.

The public module shape is `code_root: main` plus `modules: [{path: relative/directory, chips: [chip12], sides: [host], features: [], description: purpose}]`. `code_root` is relative to the config directory; module `path` is relative to `code_root`. Only path is required per module. Empty modules allow document work without implicitly authorizing all code. Specific nested modules own their files; a parent identity cannot borrow them. No expected Git URL or duplicate `catalog.code_policy` is required. A file capture still uses the catalog's installed workspace registration and the exact original config bytes. Legacy explicit repository configuration remains readable for historical compatibility.

For a real Workflow node pass `workflow: {run_id,node_id,attempt_id}` with three safe unique identifiers. The program writes the actual per-attempt Markdown manifest and JSON into K/logs/workflows. Reentry cannot replace a different artifact. Exit 0 means the request was handled; inspect phase/data. Exit 2 is invalid input and 3 is a missing prerequisite.

Explicit installation is `scripts/install_catalog.py --source-root REPO --destination NEW_PRIVATE_DIR --python LOCKED_PYTHON [--workspace-config CONFIG]`. It reads capabilities from repository-root `skills/common/knowledge/` and `workflows/common/knowledge/`, and copies exactly 20 Skills and one ingest Workflow after verification, writes a private catalog/registry, rejects existing destinations/links/private keys, and validates installed dependency versions. It does not invoke pip or install into a host's global Skill registry. Implicit host triggering requires the actual host installation and separate acceptance.

Repository-root `install.ps1` / `install.sh` provide dependency preparation before this explicit installer. Both call `scripts/install_environment.py` using existing Python 3.11 (also supports 3.12), merge the runtime locks from the 20 packages, create an external private venv with copied interpreters, install binary wheels, run `pip check`, and invoke the catalog installer with the root workspace config. The default uses existing pip configuration; `--wheelhouse` is offline and `--index-url` selects an internal index. Existing destinations are rejected. `installation.json` records interpreter, catalog, registry, capability directories and exact runtime versions; no host registration or knowledge workflow is triggered.
