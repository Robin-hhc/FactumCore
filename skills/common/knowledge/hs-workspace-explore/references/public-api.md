# Workspace binding 2.0

Invoke `scripts/cli.py --input request.json --output response.json`. Request:

```json
{"operation_id":"bind-session","target_path":"<explicit existing code/workspace path>","target_id":"chip12-host"}
```

`target_id` is optional and selects a logical chip/side combination. Module labels do not prove a build or enabled macros. Use explicit trusted process arguments `--rules-digest SHA256`, or `--catalog CATALOG.json` / `--registry workspace-registry.json` from the isolated installer. An explicit request `config_path` limits discovery to that config; otherwise search target ancestors and registered workspaces. Multiple workspace matches block. Running from another current working directory does not change a resolved mapping.

No pin means `phase: resolved` with `trusted_rules_digest_required`, not context loaded. A trusted pin permits only verified domain contract bytes to execute. A successful discovery returns `phase: context_loaded`, `context_ref` and `context_digest`. The immutable record contains actual AGENTS bytes/hashes, the original config hash, resolved module paths and labels, internally derived scope IDs and explicit gaps. `repos` is a dictionary of logical file scopes keyed by stable IDs; the name does not imply repository-manager integration. Chip/side relationships are derived for internal checks without user-written Target/pair tables. File-workspace discovery provides file scopes and labels; repository identity, dirty state, build and enabled macros remain unknown without separate evidence. P2/P4 bind the actual selected source hashes and conditions separately.

The public module shape is `code_root: main` plus `modules: [{path: relative/directory, chips: [chip12], sides: [host], features: [], description: purpose}]`. `code_root` is relative to the config directory; module `path` is relative to `code_root`. Only path is required per module. Empty modules allow document work without implicitly authorizing all code. Specific nested modules own their files; a parent identity cannot borrow them. No expected Git URL or duplicate `catalog.code_policy` is required. A file capture still uses the catalog's installed workspace registration and the exact original config bytes. Legacy explicit repository configuration remains readable for historical compatibility.

For a real Workflow node pass `workflow: {run_id,node_id,attempt_id}` with three safe unique identifiers. The program writes the actual per-attempt Markdown manifest and JSON into K/logs/workflows. Reentry cannot replace a different artifact. Exit 0 means the request was handled; inspect phase/data. Exit 2 is invalid input and 3 is a missing prerequisite.

Deployment tools belong to `K/tools/deploy/`, outside every Skill package. `install.ps1` / `install.sh` prepare a private runtime using existing Python 3.10–3.12 and the tools' own `requirements.runtime.lock.txt`. They do not require repository-root capability sources. Default environment-only preparation returns `status: runtime_ready`, a Python interpreter and workspace registry; catalog/skills/workflows remain empty until actual capabilities are registered. The default uses existing pip configuration; `--wheelhouse` is offline and `--index-url` selects a package index.

After the 18 Skills and one ingest Workflow are in their final Agent directories, use the runtime interpreter with `K/tools/deploy/install_catalog.py --register-existing --skills-root S --workflows-root F --workspace-config CONFIG --python LOCKED_PYTHON --destination NEW_PRIVATE_DIR`. CLI paths may be relative to the current directory and are resolved to actual absolute locations before registration. Registration reads existing packages in place, validates metadata/dependencies and exact hashes, and writes catalog/registry pointing directly to final locations; it does not copy packages or alter the host registry. Environment preparation can also receive paired `--skills-root` / `--workflows-root` options and register after preparing dependencies. Existing destinations, links and private keys are rejected. Move capabilities or the interpreter only with a fresh registration; nodes use the catalog, not a fixed project-root or sibling directory.

`install_catalog.py --source-root REPO ...` remains a separate development distribution interface for copying verified source packages into a new private destination. It is not a deployment prerequisite. Deployment tools never become runtime dependencies of this Skill. Host triggering and independent reviewer contexts still need the actual host setup and separate acceptance.
